# Restore retained local configuration and document recovery boundaries

## Outcome

Editors can select retained configuration on this server and publish it again as
a newly validated local snapshot. Operators can distinguish configuration restore
from full-installation recovery and use verified procedures for each.

## Requirements

- Add rollback actions to retained-history detail and protected management APIs for
  editors/admins, including editors who do not own the lease. Viewers remain read-only.
  Any retained snapshot, including failed/pending/current content, may be copied to a
  new candidate. Clearly show source status; it neither proves destination validity
  nor changes the original historical outcome. An expired/pruned source produces an
  explicit conflict/absence and refreshed history, without destructive side effects.
- Freeze the selected source content for the accepted operation. Every rollback
  receives a fresh local ID with source provenance, preserving the original snapshot
  and destination history under normal retention. Never simply repoint SQLite at
  old history or reuse an old framework generation. Rollback of current content is
  still a fresh preparation/publication attempt.
- Reuse PR 1.5.2's validated destructive update path: validate the complete candidate
  against current framework/REST/destination URL bindings; display source summary,
  validation feedback, current lease owner and explicit loss-of-drafts warning.
  Require confirmation tied to the source candidate, specific lease grant/absence
  and runtime snapshot; reject stale confirmation before mutation. Replacement
  grants require reconfirmation, even for the same owner; renewal alone does not.
- Serialize with import/ordinary publication and defer competing lease/draft
  operations through completion. Prepare afresh with public `prepare()` and stage
  matching REST resources before discarding drafts; then persist the new snapshot/
  intended pointer and `publish()` through the existing database-first policy.
  Invalid content/bindings or failed preparation/staging leaves editing state intact
  subject to normal expiry. Destructive cutover discards drafts even if later steps
  fail. Notify invalidated sessions using existing responses/status refresh.
- Accepted rollback cannot be cancelled by disconnect/logout/session or lease expiry.
  Continue execution using existing generation capture/retirement and shutdown rules.
  Preserve failure/pointer-reversion, mutation-fault and unknown-bookkeeping semantics
  from import: never undo successful activation for a later status-write failure,
  and never equate pending status with failed activation. Reconnect uses local history,
  not a new job system or blind automatic retry.
- Enforce roles/CSRF server-side, separate execution JWT access, preserve idle-session
  behavior, render configuration as text, and provide keyboard/textual feedback.
- Document and verify the distinction between current-configuration ZIP backup/
  import, local retained-history rollback and stopped-instance full database backup/
  recovery. Configuration bundles exclude accounts, private drafts and deployment
  settings and preserve sensitive literals; full database backups include persisted
  installation data and require protected handling. Refine the existing stopped
  backup procedure, including SQLite companion files, writable ownership, committed
  pointer startup behavior and post-restore inspection. Do not add online database
  backup APIs, scheduling, backup encryption or automatic fault reconciliation.
- Explain that retention can remove rollback sources, defaults to ten snapshots
  including failed attempts/current production with existing protection rules, and
  is not a guaranteed recovery archive. Configuration import cannot bypass a mutation
  fault; document the existing operator recovery route and verify a known-good stopped
  backup restores a usable installation. Phase 6 still owns integrated deployment and
  release readiness, not this ticket's rollback/recovery correctness.

## Acceptance criteria

- [ ] Browser/API workflows restore published, failed, pending and current retained
  content as newly validated local snapshots with fresh identities/provenance;
  original content/status remains unchanged and normal retention applies. Missing/
  pruned sources fail clearly without destructive changes or mixed source content.
- [ ] Viewer rejection, editor/admin access without lease ownership, CSRF, safe
  rendering and keyboard feedback are covered. Changed source selection, lease
  grant or runtime snapshot requires refreshed confirmation; renewal alone does not.
- [ ] Invalid destination bindings/content and preparation/staging failure preserve
  drafts. Accepted cutover invalidates drafts/leases and notifies affected sessions;
  concurrent publication/editing cannot bypass serialization, and disconnect/expiry
  cannot cancel an accepted rollback. Execution continues with correct generations.
- [ ] Failure injection verifies post-cutover draft loss, pointer reversion,
  mutation faults and activation-versus-bookkeeping outcomes. Reconnect/history and
  restart behavior remain accurate; no source status is treated as new publication.
- [ ] A stopped full database backup/restore exercise verifies the documented file
  set, permissions, startup selection and management/configuration recovery using
  the installed snapshot. Documentation distinguishes that procedure from ZIP import
  and local rollback, including sensitive data, retention and fault restrictions.
- [ ] Relevant Sidecar regressions pass; this ticket supplies its own browser,
  integration and recovery evidence. No online/scheduled backup or history-transfer
  feature is introduced, and remaining Phase 6 deployment checks are identified.
