Apply the [design lens](../design-lens.md#simplicity-and-technical-debt). Choose the

## Outcome

Allow async applications to reuse a lifespan-scoped Sidecar client without blocking
request processing, with the same protocol outcomes and limits as the synchronous
client and native Python cancellation.

## Requirements

- Add an async counterpart to PR 10.1 for discovery, submission, status and waiting.
  Reuse its typed models, opaque credential type, validation and error categories;
  avoid duplicated protocol policy or a second settings hierarchy.
- Preserve Java defaults: 2-second connect, 10-second total response, 8 MiB response
  limit, 60-second wait budget and 250 ms poll interval. Bound the full exchange
  and body, streamed data and remaining wait budget, including trickling responses.
- Keep one request attempt, no redirect/retry/auth-rechallenge/cookie persistence/
  automatic decompression, per-call credential isolation, verified TLS/SSL contexts,
  local URL construction and exact results/optional diagnostic fidelity from 10.1.
- Async context management/aclose owns connection resources, is idempotent and
  rejects calls after closing. Release in-flight resources on errors/cancellation
  without unbounded draining. Do not run sync I/O or a private event loop as the
  async implementation. Select public library facilities from evidence; HTTPX and
  AnyIO remain candidates rather than mandated dependencies.
- SDK wait timeout, HTTP and protocol exceptions carry execution ID/last valid
  snapshot. External native cancellation propagates unchanged after cleanup; do
  not wrap it, suppress it, attach snapshot state or convert it to SDK wait expiry.
  Outer application timeouts retain their own semantics. No WaitState, execution
  handle or background polling; waiting runs only while explicitly awaited.
- A cancelled submission after possible dispatch may have been accepted without
  a reliable ID. Document that uncertainty while preserving native cancellation;
  never infer an ID or replay. Ordinary failed submission responses preserve Java's
  acceptance-unknown/known-HTTP distinction, including unusable or oversized bodies.
- Ending a wait or closing a client does not cancel Sidecar work. Callers retaining
  an acceptance ID may explicitly read status later. No automatic recovery/refresh.
- Own async examples, cancellation documentation and focused parity/lifecycle tests;
  core still imports without web dependencies. Declare any directly used runtime
  libraries directly and preserve package/support choices established in 10.1.

## Acceptance criteria

- [ ] Async operations match sync outcomes, validation, fields, defaults and limits
  using shared models and protocol policy, with no event-loop blocking transport.
- [ ] Deadline, stalled/trickling body, oversized response and concurrent-user checks
  demonstrate bounded work, resource cleanup and single-attempt credential isolation.
- [ ] Cancellation during polling sleep and network/body reads propagates natively;
  task/application timeout handling works without swallowed cancellation or replay.
- [ ] Cancellation after possible submission is documented and verified without
  inferred acceptance IDs; SDK errors retain the appropriate wait context.
- [ ] Idempotent close and error cleanup reject new work after close and do not
  cancel remote work. Async installed examples/docs and focused tests pass review.
