# PR 11.1: Simplify Java SDK signing to PEM and ephemeral colocated keys

## Development constraints

**Sidecar is still in development. Destructively replace superseded contracts,
code and schemas; no compatibility shims, legacy adapters, parallel legacy APIs
or migration machinery solely to preserve obsolete development behavior.**

Apply the [design lens](../design-lens.md#simplicity-and-technical-debt). Choose
the simplest complete solution, minimize technical debt, and keep tests and
documentation proportional. No development-data reset is expected. Document any
required reset and its impact; this ticket does not authorize deleting deployed
data, regenerating persisted credentials or relabeling identities.

## Outcome

The Java SDK uses the agreed common signing contract for future Python, Go and
.NET SDKs: operator-provided unencrypted PKCS#8 PEM or an ephemeral colocated
signer. Remove keystore and signing-certificate complexity while preserving
signed execution tokens, Sidecar RBAC and authenticated callbacks.

## Requirements

- Implement the [shared PEM design](../phases/sdk-pem-signing-design-notes.md).
  Retain explicit `colocated` and `provided` modes and reject mixed-mode settings.
- Provided mode requires `loomspan-sdk.signing.provided.key-location` and
  `jwks-export`. Load exactly one unencrypted `PRIVATE KEY` PEM block containing
  a valid RSA PKCS#8 key of at least 2048 bits. Allow surrounding whitespace and
  standard line endings; reject encrypted PEM, PKCS#1, certificate/public-key
  bundles, multiple blocks, non-whitespace extra content, malformed/non-RSA/weak
  material. Missing or invalid material fails startup without generating a key.
- Keep `colocated.key-directory`: generate a fresh in-memory RSA key at startup,
  export only public material, and do not persist the private key. One process
  owns the export location; provided identity serves multiple workers/replicas.
- Remove JKS/PKCS12 signing loaders, aliases, password-reference configuration,
  signing certificates/chains, expiry warnings and `x5c` export. Remove obsolete
  supported core APIs directly. Reject obsolete Spring signing properties
  (`format`, `key-alias`, `keystore-password-reference`, `key-password-reference`,
  `certificate-location`, and literal password options) with safe actionable
  startup errors rather than silently ignoring them. Do not add conversion code.
- Retain RS256, RFC 7638 `kid`, issuance claims/defaults and exact role intersection.
  Derive public RSA JWKS directly from the signer. Provided keys change by restart.
- Export directories must already exist; the SDK does not create directories or
  manage permissions. Reject export paths overlapping private input, including
  equivalent existing-file paths. Publish atomically or fail startup, with no
  non-atomic fallback. Never expose private material/passwords in diagnostics.
- Update affected Java documentation, examples and maintained-suite configuration
  or fixtures. Preserve existing signing identity where required; no incidental
  credential regeneration, business-input/result/reference-pack changes or resets.
- Preserve Sidecar's public-JWKS trust, reload, JWT/RBAC and callback-forwarding
  contracts. No Sidecar production-code change is currently expected; prove
  interoperability rather than infer it. TLS/mTLS certificates, SSL bundles and
  their JKS/PKCS12 support are outside this removal.

## Acceptance criteria

- [ ] Helpers, code paths, test fixtures and dependency declarations made unused
  by this ticket are removed. Confirm remaining production and test consumers
  before removal; preserve anything required by TLS/mTLS, SSL bundles or other
  retained features. Verify affected builds and tests after cleanup, without
  expanding into unrelated cleanup.
- [ ] Core and Spring provided signing accept the required PEM form and reject
  each forbidden input/settings category with safe errors and no fallback key.
- [ ] Colocated restart generates a new signer; provided restart retains identity
  with unchanged material. Public exports contain neither private data nor x5c.
- [ ] Missing export parents, publication failures and input/output collisions
  fail safely without overwriting input or using non-atomic publication.
- [ ] Same-key public fields/kid and signed-token behavior remain correct; actual
  Sidecar validation and SDK callback validation accept the revised exports/tokens.
  Shared synthetic fixtures are usable by later SDK implementations.
- [ ] Affected maintained consumers use the new settings successfully, preserving
  their identity and business contracts. TLS/mTLS behavior remains covered.
- [ ] Obsolete signing code/tests/configuration and stale documentation are replaced;
  required checks and independent review have their own current evidence.

## Context

Parent work item: GitHub PR 11. Execute this series in order: **PR 11.1 PEM signing → PR 11.2 submission uncertainty → PR 11.3 callback trust startup**. Complete final combined verification before the series is ready to sync.

The earlier full JKS/PKCS12 Python-parity goal was explicitly superseded by this
shared contract. Python is unimplemented; this ticket does not build other SDKs.
Java-to-Python SDK interoperability must be proved during Python delivery, not
claimed here from a nonexistent implementation. The suite is an early customer,
not an authority on security design.

Keep own-key plus optional overlap trust, operator-owned rotation, and existing
shared-Sidecar trust boundaries. No central issuer, namespace isolation, key
manager or restart cancellation machinery is requested. The independent
[submission fix](PR-11.2-java-sdk-submission-uncertainty.md) and
[callback startup fix](PR-11.3-java-sdk-callback-trust-startup.md) have separate
acceptance evidence. Coordinate edits if their work overlaps; none is a prerequisite
for writing this plan. Publication, paid-provider calls and release changes are
not part of this ticket. Follow repository snapshot/dependency policy.
