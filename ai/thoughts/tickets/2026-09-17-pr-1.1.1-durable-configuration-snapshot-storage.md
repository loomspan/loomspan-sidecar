# Persist complete managed configuration snapshots in SQLite

## Outcome

Sidecar can durably store and recover a complete authored configuration without
mixing skill declarations and REST configuration. This establishes the shared data
contract for runtime publication, history and later configuration transfer.

## Requirements

- Managed content consists of complete named YAML skill documents and the REST
  routes and targets required by the fixed `RestSkillHandler`. Preserve original
  YAML and the full framework-supported model-backed and REST authoring surface.
  Do not host Java skills or create a second skill-validation authority.
- Give each stored snapshot a fresh, stable local identity independent of
  process-local framework generation IDs. Snapshot identity and authored content
  are immutable. Publication status is separate mutable bookkeeping: `pending`,
  `published` or `failed`; pending means outcome unknown. Preserve submission
  ordering for later oldest-first history pruning. A source snapshot identity is
  provenance only; repeated imports or rollback copies must never overwrite a
  local snapshot or reuse its identity.
- Preserve diagnostic document labels and original text. Labels must be nonblank
  and exactly unique, and documents and YAML must be non-null, matching the public
  `SkillDocument` contract. An empty document collection is valid. Store authored
  REST configuration, never a serialization of resolved clients or runtime resources.
- Define and document the logical snapshot/bundle data contract: complete managed
  content, local identity, optional source identity, and version metadata. Transfer
  uses independent integer `formatVersion: 1` and informational producer application
  and framework versions, not Flyway or application-version compatibility rules.
  Keep publication bookkeeping local rather than treating imported status as proof
  of local activation. Concrete schema and representation are implementation-plan
  decisions; ZIP/archive layout, integrity checks and import/export operations
  belong to Phase 5 and must reuse this content boundary.
- Exclude accounts, sessions, leases, deployment URL-variable declarations and
  environment values, model-connection settings, identity-provider settings and
  arbitrary Spring settings from managed snapshots and configuration bundles.
  Preserve literal sensitive values and authored references without sanitization,
  encryption or substitution. In particular, `${NAME}` in REST `base-url` remains
  authored text. Destination allowlist/environment resolution belongs to Phase 2
  staging and Phase 5 transfer validation, not persistence.
- Use embedded file-backed SQLite, Flyway and small Spring JDBC repositories
  using `NamedParameterJdbcTemplate` and Spring transactions. No JPA, external
  database support, generic multi-engine layer or distributed transaction.
  Flyway owns schema creation, versioned DDL and required reference data; application
  services own user content and publication state. Use one migration runner and
  finish migration/validation before loading configuration or allowing writes.
- A genuinely new database receives an empty current configuration through the
  application initialization path. Creation of that snapshot, its intended-production
  pointer and the state distinguishing an initialized store must be atomic. Do not
  claim it is runtime-published before activation. Reopening an initialized store
  must not reseed it; missing or invalid current configuration is an error. Storage
  initialization is distinct from completion of first-administrator setup in Phase 3.
- Support one Sidecar instance owning its database on a writable persistent volume
  with reliable local filesystem locking. Document the database location setting,
  writable directory requirements including SQLite auxiliary files, non-root
  permissions, contention behavior and chosen durability settings. No shared
  database across replicas or network-filesystem deployment. Select exact settings
  during planning; Sidecar-owned settings use `loomspan-sidecar.*`.
- Replace the old development storage assumptions directly. No mounted-skill/route
  adoption, legacy readers, compatibility shims or migration of discarded development
  databases. Tests must use real SQLite and cover fresh migrations and any schema
  upgrades explicitly supported by this implementation.

## Acceptance criteria

- [ ] Real SQLite tests recover exact named YAML and matching REST content together
  after closing/reopening the store, including empty content, placeholders and
  literal sensitive values. Labels and null-content constraints are enforced.
- [ ] Snapshots have distinct stable local IDs, retain source provenance separately,
  and cannot have content changed by later caller mutations or status updates.
  Runtime generation identity is not used as durable identity.
- [ ] The documented logical contract identifies included/excluded data, format 1
  metadata, authored-content preservation and the Phase 5 packaging boundary.
- [ ] Fresh migration and initialization create exactly one complete empty current
  configuration atomically. Reopening does not replace it; initialized-store
  corruption cannot silently become a fresh installation. Migration failure prevents
  storage use, and any explicitly supported upgrades preserve required data.
- [ ] Transaction failure cannot leave a partial snapshot or initial pointer.
  Real SQLite contention and persistence checks support the documented settings.
- [ ] Storage/deployment documentation specifies the selected configuration,
  permissions and single-instance restrictions. Production and test dependencies
  retain the supported framework boundary and its ArchUnit enforcement.
