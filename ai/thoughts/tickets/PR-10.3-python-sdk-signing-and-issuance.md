# PR 10.3: Issue Java-compatible execution credentials from trusted Python identity

## Development constraints

**Sidecar is still in development. Destructively replace superseded contracts,
code and schemas; no compatibility shims, legacy adapters, parallel legacy APIs
or migration machinery solely to preserve obsolete development behavior.**

Apply the [design lens](../design-lens.md#simplicity-and-technical-debt). Choose the
simplest complete solution and minimize technical debt. Keep implementation,
tests and documentation proportional. No data reset is expected; preserve existing
credentials, identities, operational data and reference packs. Document any newly
required development-data reset and its impact; this is not permission to delete
deployed data or regenerate operator keys.

## Outcome

Replace application-owned signing/JWT construction with a small typed Python API
that captures authenticated identity, issues the common execution credential and
exports public trust in colocated or provided mode.

## Requirements

- Use the credential/public package foundation from 10.1. Core issuance runs
  independently of FastAPI, Sidecar/Framework internals or an original login token.
  Identity is an immutable/copying trusted subject/authority snapshot supplied by
  application authentication, never deserialized business/model inputs.
- Retain independent lifetime: issuer `loomspan-app`, 15 minutes, positive
  representable duration, warning above one hour, no policy maximum or source-login
  expiry cap. Audiences include `loomspan-sidecar`, issuer and deduplicated extras.
  Roles are the exact deduplicated intersection with a default-empty allowlist;
  reject blank/non-string authority names and never map ROLE_ prefixes.
- Issue RS256 with RFC 7638 kid, typ `loomspan-execution+jwt`, token_use
  `loomspan_execution`, iss/sub/aud/iat/exp/unique jti and string-array roles.
  Preserve fractional NumericDate precision and reject overflow. Establish Java
  nanosecond/accepted timestamp behavior using fixtures; do not silently coerce to
  integer seconds. Raise a concrete representation tradeoff before substantial
  bespoke machinery or any parity reduction.
- Explicit signing modes: colocated generates fresh 2048-bit RSA in memory at
  startup; provided loads one operator-owned unencrypted PKCS#8 RSA private key of
  at least 2048 bits once at startup. Restart changes colocated identity; unchanged
  provided material retains identity. Missing/invalid provided material never
  falls back to generated keys; private-key changes require restart.
- Follow strict shared PEM input contract and current Java fixtures: one complete
  PRIVATE KEY block, ordinary whitespace/line endings, valid complete PKCS#8,
  including supported optional attributes/embedded public-key consistency. Reject
  encrypted PEM, PKCS#1, non-RSA/weak keys, bundles/multiple blocks, malformed and
  trailing content. Use established crypto/library primitives, not bespoke crypto.
- Export only public RSA JWKS without private members/x5c. Parents must exist;
  reject output/private-input overlap including equivalent existing files. Publish
  atomically with no non-atomic fallback, fail startup safely on publication error
  and preserve private input/prior public export on failure. Never create directories
  or manage permissions. One process owns each export path in either mode.
- Reject mixed-mode/unsupported settings; no keystores, aliases, passwords,
  certificates, conversion, rotation manager, worker coordinator or compatibility
  adapter. Ordinary strict Python configuration rejection is sufficient. TLS
  configuration is separate. Keep private material/tokens out of default outputs,
  serialization, exceptions and logs. Application introspection is not preventable.
- Own issuance/signing docs and tests with synthetic keys. Demonstrate Python-issued
  credentials accepted by actual Java SDK/Sidecar validators and equivalent public
  identity for the same key. PR 10.4 owns Java-to-Python callback verification;
  PR 10.6 owns composed consumer proof. PyJWT/cryptography are candidates, not
  assumed compliant dependency choices.

## Acceptance criteria

- [ ] Trusted identity capture, default profile, exact roles/audiences, unique jti,
  fractional lifetime and overflow behavior match Java without cross-user leakage.
- [ ] Both signing modes have required startup/restart behavior; valid/invalid PEM
  fixtures establish strict acceptance, safe failure and no fallback generation.
- [ ] Public exports preserve kid/JWKS equivalence, contain no private/certificate
  material, and fail atomically without overwriting private or prior public files.
- [ ] Invalid/mixed settings and failures remain safe; configuration/docs retain
  operator-owned files/rotation and independent TLS without legacy options.
- [ ] Actual Java/Sidecar validation accepts Python issuance; focused tests and
  installed usage docs pass review, with temporal/dependency choices evidenced.
