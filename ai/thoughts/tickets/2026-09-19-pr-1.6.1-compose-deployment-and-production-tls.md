# Deploy Sidecar through a verified Docker Compose configuration

## Outcome

Operators can deploy the v1 management console and execution service through one
documented Docker Compose path with persistent configuration, non-root operation,
production HTTPS and customer-provided SMTP. Concentrating on this deployment path
keeps the initial support commitment small while customer use cases develop.

## Requirements

- Make Docker Compose the documented and verified v1 deployment target. Remove the
  Kubernetes example and current deployment instructions/references that imply
  Kubernetes support. Record Kubernetes deployment support as deferred pending
  customer requirements; do not add restrictions preventing the container from
  running elsewhere. Historical ticket/evidence records need not be rewritten.
- Supply a usable production Compose configuration and operator instructions for
  writable persistent SQLite storage, ownership/permissions under the non-root
  container user, execution JWT configuration, model connections, one-time setup
  credentials, REST URL-variable allowlists/environment values, and console access.
  Preserve single-instance storage with reliable local filesystem locking; do not
  introduce shared-database replicas or automatic adoption of mounted skill files.
- Document and verify one production TLS configuration. Planning selects the TLS
  termination arrangement and tooling. Cover HTTPS console access, secure session
  cookies, the trusted external HTTPS URL used in emailed links, certificate/key
  provisioning, and the intended exposure of execution and health endpoints.
  Do not require operators to choose among several unfinished alternatives. Local
  loopback HTTP remains permitted for development, with its configuration clearly
  distinguished from production.
- Production email uses the customer's configured SMTP service. Document sender,
  SMTP credentials/settings and email-link URL requirements for first administrator
  setup, invitations and recovery. A local SMTP capture service is a test/developer
  fixture only, excluded from the released runtime image and production Compose
  deployment. Do not introduce another account-recovery mechanism or real email
  recipients into automated checks.
- Preserve database-first startup activation and dispatch gating, readiness/liveness,
  bounded shutdown and management-lock isolation from authenticated execution.
  An initialized installation must restart without requiring the setup credential;
  a missing credential on a new installation locks management rather than execution.
- Update deployment and operational documentation alongside the packaging changes,
  including how to stop/restart the deployment and access persistent state for the
  existing stopped-instance backup/recovery procedure. Configuration bundles remain
  separate from full database recovery; neither includes deployment settings as a
  substitute for operator configuration. Do not add online/scheduled backup,
  automatic reconciliation or compatibility bridges.
- Supply this ticket's deployment evidence against the developer-installed framework
  beta 5 snapshot. Build Sidecar's runtime image from its locally built artifact;
  do not rebuild the framework, add a snapshot repository, publish images or tag a
  release as part of this ticket.

## Acceptance criteria

- [x] Following the documented Compose path starts the real Sidecar container as
  non-root with writable persistent state; container recreation preserves stored
  configuration and management accounts, and initialized startup works without a
  setup credential. No mounted skills/routes are silently adopted.
- [x] The documented production TLS arrangement is exercised successfully: console
  login uses HTTPS and secure cookies, emailed setup/recovery links use the configured
  external URL, and endpoint exposure and certificate provisioning match the guide.
- [x] JWT/model/setup/SMTP/URL-variable configuration is documented coherently;
  destination URL variables resolve through the declared allowlist. Automated
  deployment checks use controlled fixtures without contacting real mail recipients.
  Production packaging contains no SMTP capture service.
- [x] Deployment checks demonstrate management-lock isolation, activation before
  execution dispatch, meaningful health probes and bounded shutdown without changing
  the framework's execution or shutdown authority.
- [x] Operators can locate and preserve the database volume and follow the existing
  stopped-instance recovery instructions with correct ownership. Deployment examples
  and documentation agree; Kubernetes examples/support instructions are removed and
  the support deferral is explicit.
- [x] Ticket-specific checks and documentation are complete using the installed
  snapshot, with actual outcomes recorded rather than inferred from framework tests.
  No framework rebuild, hosted release check, image publication or tagging occurs.
