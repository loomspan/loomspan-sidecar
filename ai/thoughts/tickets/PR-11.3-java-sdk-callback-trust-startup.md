# PR 11.3: Fail Java SDK startup on invalid callback trust and report trust transitions

## Development constraints

**Sidecar is still in development. Destructively replace superseded contracts,
code and schemas; no compatibility shims, legacy adapters, parallel legacy APIs
or migration machinery solely to preserve obsolete development behavior.**

Apply the [design lens](../design-lens.md#simplicity-and-technical-debt). Choose
the simplest complete solution, minimize technical debt, and keep tests and
documentation proportional. No development-data reset is expected. Document any
required reset and its impact; no deployed-data deletion is authorized.

## Outcome

A Spring application configured with unusable initial callback overlap trust
fails startup with an actionable safe diagnostic. After successful startup,
operators can diagnose callback-trust withdrawal and recovery without leaking
security material or receiving repetitive polling logs.

## Requirements

- If an explicitly configured callback overlap-JWKS file is missing, unreadable,
  malformed, empty or invalid under existing public-RSA validation rules at
  security initialization, fail initialization and Spring application startup.
  Do not leave a refresh task or other owned resource running after failure.
- With no overlap file configured, startup succeeds using the signer's own
  public key, assuming other required settings are valid. Do not require a file
  for this case or alter signing modes.
- After successful startup, unusable configured overlap withdraws all callback
  trust, including the own key. Keep the application running; restore acceptance
  automatically when valid trust returns. No stale-key fallback, grace period,
  private-signer reload or restart requirement is introduced.
- Preserve atomic complete trust snapshots, existing polling/unknown-kid refresh
  limits, operator-managed rotation, and independent request authentication.
  Withdrawal affects new authentication, not already-admitted callback work.
- Report safe unavailable/invalid/restored state transitions. Repeated identical
  failure on polling or unknown-key lookup must not flood logs. Do not log bearer
  tokens, key contents, passwords or raw parser exceptions; callers retain generic
  authentication errors rather than receiving operational details.
- Update SDK documentation with initial failure, runtime withdrawal/recovery and
  atomic trust-file replacement expectations. Do not add an elaborate health,
  rotation or historical trust subsystem.
- Scope this startup rule to SDK callback security. Preserve Sidecar's own
  trust startup behavior, including waiting for a colocated application's first
  public export; do not apply this rule to Sidecar's verification-file loader.

- [ ] Helpers, code paths, test fixtures and dependency declarations made unused

  before removal; preserve anything required by TLS/mTLS, SSL bundles or other
  retained features. Verify affected builds and tests after cleanup, without
  expanding into unrelated cleanup.
- [ ] Each unusable configured initial-trust condition fails security/Spring
  startup with a safe useful diagnostic and no surviving refresh task.
- [ ] No-overlap configuration still starts and authenticates own-key callbacks.
- [ ] After valid startup, file failure rejects new callbacks for all keys;
  valid restoration recovers automatically while the application remains running.
  Already-admitted work is not cancelled by trust withdrawal.
- [ ] Repeated unchanged failures do not repeatedly log; withdrawal and recovery
  are distinguishable without secrets or raw parser output. Concurrent readers
  observe complete trust states and refresh limits remain enforced.
- [ ] Sidecar colocated startup/reload behavior is unchanged. Documentation,
  required checks and independent review provide current implementation evidence.
