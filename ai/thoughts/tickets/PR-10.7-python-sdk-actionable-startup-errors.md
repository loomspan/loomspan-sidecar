# Make Python SDK signing startup failures actionable without exposing secrets

## Development constraints

**Sidecar is still in development. Changes must destructively replace superseded
behavior; no compatibility shims, legacy adapters, parallel legacy APIs, or
migration machinery solely to preserve obsolete development contracts.**

Apply the [design lens](../design-lens.md#simplicity-and-technical-debt). Choose the
simplest solution that fully meets the requirements and minimize technical debt.
Keep implementation, tests and documentation proportional. Replace the ambiguous
diagnostics directly; do not retain old messages through a compatibility layer.
No development-data reset is required or authorized. Preserve existing keys,
credentials, operational data and unrelated uncommitted work.

## Outcome

A Python or FastAPI developer whose SDK signing initialization fails can tell
whether to fix the private-key input, the colocated signing directory, or the
public JWKS export. The startup error identifies the failing stage and a practical
corrective action without exposing private material or underlying parser errors.

Today the Python SDK can collapse these failures into:
`Unable to initialize RSA RS256 signing material or publish its public JWKS`.
This protects secrets but makes ordinary setup mistakes unnecessarily hard to
diagnose. Improve that developer experience without changing signing behavior.

## Requirements

- Scope executable changes to Python SDK signing initialization and public JWKS
  publication, including propagation through the existing FastAPI lifespan.
  Cover both `ProvidedSigning` and `ColocatedSigning`. This is not a general
  redesign of SDK errors, callback trust, execution errors or health checks.
- Distinguish these actionable setup failures: a missing provided private-key file;
  an unreadable or non-file private-key input; invalid or unsupported key material;
  a missing or invalid colocated key directory; and failure to publish the public
  JWKS, including an unavailable export directory or insufficient filesystem access.
  A key-generation or signing-self-check failure must be identified as signing
  initialization rather than mislabeled as a public-export problem.
- Name the relevant configuration concept (for example, `key_location`,
  `key_directory` or `jwks_export`) and the corrective action. It is enough to group
  malformed, encrypted, wrong-type and insufficient-strength keys into one safe
  invalid-key diagnostic describing the existing supported key requirements.
  Do not add detailed ASN.1 or cryptographic-parser diagnostics.
- Retain the existing public `LocalFailure` exception category. No new public
  exception hierarchy, error-code registry, configuration switch or preflight API
  is required. Exact wording is an implementation choice; distinct actionable
  meanings are required. Retain existing useful errors such as signing-input/export
  path collision diagnostics.
- Preserve secret redaction in exception messages, displayed exception chains and
  SDK-emitted logs. Do not interpolate private-key bytes, supplied file contents,
  bearer credentials or raw backend exception text. Use configuration field names
  rather than echoing caller-supplied paths. Keep a sanitized fallback for failures
  that cannot be classified reliably; do not guess a misleading cause.
- Preserve all existing key validation, signing identity, path-alias protection,
  public-only export, atomic-publication and failure cleanup behavior. Failed startup
  must still fail closed; prior public exports and private inputs must remain intact
  on failure according to their existing guarantees. Successful startup, issuance,
  shutdown and callback authentication must remain unchanged. No automatic key
  replacement, directory provisioning, permission relaxation, retry or recovery is
  introduced.
- Update the Python SDK documentation with a short troubleshooting guide that maps
  these startup failures to remedies. Explain that these are local initialization
  failures, not failed execution reads or failed skill executions. Do not promise
  that application-side startup checks can diagnose Docker bind-mount setup before
  the application starts.
- Keep verification provider-free and proportional: reuse signing and FastAPI
  lifecycle coverage, add focused evidence for diagnostic distinctions and redaction,
  and verify that a representative failure reaches FastAPI startup unchanged.
  Existing successful signing and publication behavior must remain covered. Do not
  require the entire business replay or TLS recipe matrix solely for message changes.

## Acceptance criteria

- [x] Missing, unreadable/non-file and invalid provided keys; invalid colocated
  directories; signing initialization failures; and JWKS-publication failures produce
  distinct, actionable diagnostics through the existing `LocalFailure` boundary.
  A developer can identify the configuration field and next corrective action.
- [x] Focused negative checks demonstrate that messages, formatted exception chains
  and SDK logs do not expose supplied private content, credentials, caller-supplied
  paths or raw backend diagnostics. Unclassified failures remain sanitized.
- [x] Existing invalid-key rejection, path collision protection, atomic export and
  prior-file preservation continue to hold. Valid provided and colocated startup
  and issuance still succeed without new filesystem or lifecycle behavior.
- [x] FastAPI startup surfaces a representative improved SDK diagnostic and still
  fails closed with its existing cleanup guarantees. No additional application
  exception translation is necessary to understand the failure.
- [x] SDK documentation explains the supported diagnostic categories and remedies;
  implementation, tests and documentation stay within the bounded scope above.
