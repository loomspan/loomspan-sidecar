## Outcome

Provide the callback verification and trust lifecycle that FastAPI can consume,
without each application implementing JWT parsing or maintaining a trust cache.
Invalid startup trust fails initialization; runtime trust withdrawal blocks new
credentials and recovers safely when valid trust returns.

## Requirements

- Build on PR 10.3 startup signer/profile. Keep verification/trust logic testable
  independently of routing; do not expose a new public plugin/SPI just to stage the
  implementation. PR 10.5 owns ASGI enforcement and composed application lifespan.
- Trust own startup public key plus optional local overlap JWKS. No overlap means
  own-key-only trust and no file polling. Configured initial missing/unreadable/
  malformed/empty/invalid overlap fails initialization safely before a refresh task
  can leak. Runtime invalidity withdraws all keys, including own, until valid trust
  returns; no stale fallback, historical key cache or private signer reload.
- Validate complete UTF-8 public RSA key sets: nonempty keys, unique nonblank kids,
  no private members, valid >=2048-bit modulus/exponent and compatible use/alg if
  supplied. Own/overlap kid conflicts reject the whole set; identical own key is
  allowed. Atomically publish snapshots, never skip invalid entries.
- Support lifecycle-owned one-second polling and unknown-kid refresh at most once
  per second across the trust instance, not per supplied kid. Use current content,
  not metadata alone. Stop owned refresh work on close and initialization failure;
  keep file I/O off async request processing. Integration starts work explicitly,
  never as an import/configuration-construction side effect.
- Log only safe unavailable/invalid/restored state transitions, not repeated poll
  failures, raw parser exceptions or key/token contents. Withdrawal affects new
  authentication; admitted callbacks keep their verified identity and may finish.
- Validate RS256 signature, exact typ/purpose/issuance issuer, nonblank kid/subject,
  role shapes, receiver audience and timestamps with 60-second skew. Audience
  defaults to issuer, with an explicit nonblank override. Accept matching string or
  string-array audience. exp is required; iat/nbf/jti need not be present, but must
  have Java-compatible types when present. Reject bool/nonfinite/overflow numeric
  values and preserve fractional precision; do not infer validation rules from
  every claim emitted by the issuer or from JWT-library defaults.
- Return verified issuer/subject/exact authorities without exposing bearer bytes
  in normal serialization. Generic safe invalid-credential errors; no live account
  lookups, business authorization engine, remote JWKS discovery or token refresh.
  Expiry governs new admission, not cancellation of already-admitted business code.
- Own profile/trust docs and focused tests, including actual Java-issued tokens
  validated in Python. Use fixed clocks and synthetic keys where appropriate;
  neither self-verification nor historical Framework results prove interoperability.

## Acceptance criteria

- [ ] Java-issued and Python-issued credentials validate through the Python
  verifier; malformed headers/claims/signatures, wrong audience/issuer, timestamp
  boundaries and fractional values demonstrate Java-compatible acceptance rules.
- [ ] Initial invalid overlap fails safely without refresh leakage; runtime
  withdrawal/recovery includes own key and yields only complete trust snapshots.
- [ ] Duplicate/conflicting/invalid public-key candidates fail as a whole; unknown-kid
  floods are globally throttled and corrected file content restores current trust.
- [ ] Refresh lifecycle, concurrent reads and shutdown are bounded; no-overlap mode
  performs no file reads/polling; transition logs expose no sensitive content.
- [ ] Verified identity is immutable/request-usable and errors are safe; focused
  tests and documentation pass review without a general trust/plugin subsystem.
