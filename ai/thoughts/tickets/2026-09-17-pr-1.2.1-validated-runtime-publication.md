# Activate complete configuration snapshots safely without restart

## Outcome

Sidecar starts from its database-selected configuration and can validate and
publish a complete replacement without restart. Every execution uses matching
skill definitions and REST resources for its captured generation, including nested
work that outlives a publication. Operators can distinguish intended, running and
failed configuration and recover from publication faults without silent fallback.

## Requirements

### Candidate validation and publication

- Build on the Phase 1 immutable snapshots, transactional store and ephemeral
  draft/candidate model. Managed content remains complete named YAML skill documents
  plus authored REST configuration. Preserve the full supported model-backed and
  REST declaration surface, authored placeholders and literal values. No Java skills.
- Explicit Validate freezes the candidate, calls public
  `SkillReloader.prepare(Collection<SkillDocument>)`, validates REST routes against
  the candidate catalog and stages its HTTP clients. Return source-labelled errors
  with available locations. Release temporary Sidecar resources on success or
  failure; do not retain prepared updates or clients awaiting a user's Publish.
  Validation does not publish, change intended production or create submitted history.
- Ordinary Publish must reject a candidate without successful validation associated
  with that exact frozen draft candidate. Preserve Phase 1 edit invalidation,
  including equal-content edits and late results. Check the runtime-published base,
  freeze accepted content and prepare/stage it afresh. Validation success is not a
  guarantee of publication success or future model/remote-service outcomes.
- Serialize publication attempts from admission/base checks and freezing through
  preparation, staging and all success/failure handling. Waiting requests have not
  started and must be checked when their turn arrives. Once accepted, an update
  cannot be cancelled or changed by later edits, discarded draft references,
  disconnect, logout, session/lease expiry, takeover or account changes. Do not add
  cancellation, a durable job service or another shutdown drain budget.
- After preparation/staging, atomically persist pending B and switch intended
  production from A to B through the store's guarded transaction. Only then publish
  B through the framework. Commit failure leaves runtime A unchanged and releases
  the unpublished candidate. Successful publication makes B authoritative for
  runtime reads and records B as published. Never mix A's skills with B's routes.
- Rejected publication attempts restore the intended pointer to A and mark B failed,
  retaining its immutable submitted content. Clean up never-published resources.
  Failure before persistence need not create history. A pointer change/revert alone
  is not a runtime transition or a reason to invalidate drafts.
- If reversion fails, enter an explicit configuration-mutation fault state: execution
  continues on A, intended production remains B, and inspection exposes both IDs and
  the failure. Reject further configuration mutations. If status recording fails
  after successful publication, keep runtime/resources and intended production on B,
  surface the bookkeeping failure and likewise stop mutations. Never undo a
  successful publication or destroy its resources because a later write failed.
  Pending remains outcome-unknown; do not invent historical outcomes.

### Startup and current configuration

- Keep execution admission/dispatch closed until migrations, selected snapshot load,
  preparation, REST staging and publication succeed. Configure ordinary framework
  startup discovery with documented `loomspan.skills.locations` pointing at a
  controlled empty source; an empty list alone is insufficient. Prove the baseline
  is empty. Register retirement notification before publishing managed generations.
- A new database activates its Phase 1 empty snapshot. An initialized database must
  activate the committed intended pointer regardless of recorded status. Preserve
  the durable snapshot ID across restart, assign a new process-local generation,
  and record successful activation as published before opening execution. A crash
  after B's commit but before publication/reversion intentionally selects B on restart.
- Any load, preparation, staging, activation or required startup bookkeeping error
  fails startup with actionable, secret-free diagnostics. Do not substitute empty
  or older content or run a management-only recovery server.
- Replace startup-catalog use in discovery and execution request checks with current
  public catalog snapshots. Generation capture remains at the existing worker
  handoff, not HTTP acceptance. Queued work can therefore see a later generation;
  framework invocation validation/authorization remains authoritative.
- Remove obsolete mounted skill/route loading and deployment assumptions directly.
  No adoption, legacy reader or compatibility bridge. Update affected examples and
  documentation so mounted content cannot accidentally become an alternate source.

### REST resources, URL variables and diagnostics

- Retain one fixed `RestSkillHandler` bean. Stage matching routes, clients and the
  generation-to-durable-snapshot mapping before publication; select resources using
  the trusted invocation's generation ID. Route-only changes also publish a complete
  replacement. Existing JWT propagation, REST limits and standard SSL-bundle behavior
  remain supported; do not replace framework beans or parse skills independently.
- Implement deployment setting `loomspan-sidecar.url-variables`, defaulting to no
  allowed variables. REST `base-url` accepts a literal valid URL or whole-value
  `${NAME}` resolved from the process environment only. Require an exact allowlist
  entry, an existing nonblank value and normal REST URL validity. Reject composed
  templates, fragments and defaults. Unused declarations require no value. Existing
  placeholder behavior in other REST fields is unchanged. Never persist resolved
  URLs in place of authored references. Deployment allowlist/environment changes
  require restart; selecting another available declared variable uses publication.
- Retain old generation resources and mappings until public retirement notification
  establishes safe release, including pending admissions and physically running
  nested work. A callback may run concurrently or before publish returns; it must
  be prompt and thread-safe. Slow cleanup must not block framework callback threads.
  Clean up validation-only, partially staged and rejected unpublished candidates
  directly; they receive no retirement callback.
- Resource cleanup is bounded by ownership: no cache of validated candidates, no
  retention of retired clients, and no arbitrary TTL/count eviction of resources
  still used by live generations. Use idempotent cleanup. On shutdown stop dispatch
  promptly, preserve resources until framework completion/cutoff, then close all
  remaining resources, including active generations that receive no callback.
  Do not introduce a second drain period or rely on callbacks after shutdown begins.
  Planning must specify bounded cleanup execution using the actual HTTP client API.
- Add nullable `configurationSnapshotId` to the retained execution record and
  `GET /v1/executions/{id}` response, independently of observer diagnostic selection.
  Populate it immediately after successful worker handoff using
  `AdmittedSkillInvocation.generationId()` and the staged mapping, before invocation.
  It remains absent/null before capture or when capture cannot be resolved. Preserve
  the ID after completion and resource retirement, including model-only executions.
  Log unresolved mapping as an explicit execution failure and release an abandoned
  admission; never substitute the current pointer/catalog or wait for an observer.
- Supply live-generation and in-flight-update IDs to history protection and
  coordinate pruning with publication so required snapshots cannot disappear.
  Prune at startup and after completed attempts when the database is usable. Retain
  the existing default of ten, oldest-eligible pruning and protected overflow.
  Retirement releases protection/resources but does not prune the database.
  Expired history is reported absent; retained execution IDs do not pin it forever.

### Recovery and later management integration

- Provide runtime inspection of published/intended IDs, stored outcome and mutation
  fault state through the internal service for later management APIs, with
  secret-free operator logs now. Add no unauthenticated management endpoints.
- Document and verify the minimal recovery procedure: stop the sole instance,
  preserve a consistent copy of its database set, correct the storage problem, and
  restart to activate the committed pointer when that intended content is wanted.
  Explain explicitly that unreverted A/B failure restarts onto B, not A. To recover
  prior configuration instead, restore a known-good stopped-instance full database
  backup using the existing procedure, then restart and verify activation/readiness.
  Recovery rolls all database state back to the backup point. Successful startup
  records the selected snapshot as published; historical pending rows remain unknown.
  No online repair endpoint, manual live SQL, journal or automatic reconciliation.
- Phase 3 will perform real authorization, session/tab ownership and lease checks
  inside serialized update admission. Its draft/lease operations must coordinate
  with the short successful publish-and-invalidate transition: invalidate prior-base
  drafts and cancel leases only after framework publication succeeds, including when
  later outcome recording fails. Ordinary rejection preserves valid drafts/leases.
  Other sessions may edit A during preparation of B; execution dispatch continues.
  Do not prebuild a session registry, fake authorization or speculative callback
  framework here. Keep this phase's service boundary usable for the concrete Phase 3
  integration and explicitly document those remaining obligations.
- Phase 5 owns import/rollback packaging, confirmation and destructive cutover. It
  must reuse this preparation/staging and serialized publication path, validating
  before discarding drafts and assigning fresh local IDs with source provenance.
  Ordinary Publish's prior-validation requirement must not become a bypassable
  public management option. No import/export endpoint or UI belongs in this ticket.

## Acceptance criteria

- [ ] Real Sidecar integration tests with the installed framework snapshot and real
  SQLite demonstrate empty/new startup, selected snapshot activation, additions,
  updates, deletions, empty replacement, route-only changes and current discovery/
  execution checks. Actual dispatch stays closed until startup activation succeeds.
  Invalid selected content and activation/bookkeeping faults fail startup.
- [ ] Validation has no production/history side effects and releases temporary
  resources. Invalid YAML, route/catalog mismatch, client staging failures and
  invalid URL bindings preserve active configuration. Exact-candidate validation,
  edit invalidation, late results and fresh preparation on Publish are enforced.
- [ ] URL tests cover literals, multiple declared variables, absent/empty allowlists,
  undeclared/missing/blank/invalid values, unsupported forms and unused declarations.
  Stored authored references remain unchanged; arbitrary Spring properties cannot
  supply environment values. Phase 5 owns actual export/import round-trip evidence.
- [ ] Integration tests prove matching old/new nested REST routing, pending-admission
  protection, prompt/concurrent retirement handling, unpublished cleanup and shutdown
  cleanup under the existing framework budget. No resource is closed while its
  generation still requires it before framework completion/cutoff.
- [ ] Serialized competing updates recheck their bases at acceptance; accepted frozen
  content survives later draft edits/discard. Rejected or failed attempts do not
  alter running configuration. Phase 3 completes real session/lease/account-event
  non-cancellation and invalidation race coverage using this coordinator.
- [ ] Commit failure, publication failure plus successful revert, failed revert and
  failed status recording after successful publication produce the specified pointer,
  runtime, history, resource and mutation-gate states. Inspection remains available;
  execution continues on A or B as specified. No successful publication is undone.
- [ ] Restart/process-interruption evidence across commit and publication/reversion
  proves actual runtime activation of the committed selection. Operator recovery
  for both fault states is exercised; Phase 1 storage-only tests are not sufficient.
- [ ] Model-only and REST executions record the captured durable snapshot ID across
  concurrent publication, including publication before handoff returns. Pre-capture
  failures, missing mappings, admission release and subsequent resource/history
  cleanup do not cause false correlation or ownership leaks.
- [ ] Runtime/pruning race tests protect live generations and updates, including
  overflow beyond the retention target, then permit later pruning. Failed history
  remains inspectable until eligible cleanup; retirement does not delete history.
- [ ] Affected README/configuration/deployment guidance describes database-authoritative
  startup, URL variables, publication faults, recovery, correlation and cleanup.
  Relevant execution/security/shutdown regressions and public-boundary architecture
  checks pass. Later-phase checks are explicitly assigned, not claimed as completed.
