## Requirements

Resolve installation-specific fixed headers and skill routes through Framework at file startup. The annotated HTTP executor consumes captured settings, validates targets and operations at invocation, and obtains passthrough credentials from each authorized request.

In a target's `headers` map, a fixed `Authorization` value may be literal or supplied by a whole-node variable. The value includes any authentication scheme and prefix:

```yaml
auth: { mode: fixed }
headers:
  Accept: application/json
  Authorization: { $var: service.authorization }
```

Header names are case-insensitive. Apply these ownership rules at invocation before dispatch:

- `none` sends no `Authorization` header and rejects one declared by the target.
- `fixed` permits the target to supply the complete `Authorization` value. The header is optional, including for services using a custom header such as `X-API-Key`. Sidecar does not classify custom headers as credentials.
- `caller-passthrough` takes `Authorization` exclusively from the current request's authorized, unexpired JWT and rejects a target-declared `Authorization` header.

## Acceptance criteria

- [ ] In file mode, boot with a namespace HTTP target using literal Accept and an X-Region header whose value is `{ $var: app.region }`. Give an executor-backed skill a `config.path` marker for `records.lookup-path`. Set the host properties to west and /v2/records/{recordId}. An actual request sends both headers and fills the record ID from invocation inputs. A different installation can run the same skill documents with different values.
- [ ] Fixed service headers use ordinary values in the captured target settings. Remove HTTP executor credential-record lookup and decryption on requests. Preserve invocation-time validation of targets/operations. Successful preparation need not prove route validity or reachability.
- [ ] Verify a real fixed-mode request sends exactly one `Authorization` header containing the resolved value verbatim. For both `none` and `caller-passthrough`, verify an authored lowercase `authorization` fails at invocation and the receiver gets no request.
- [ ] Caller-token passthrough continues to use the current request's authorized, unexpired token. Verify this separately from fixed headers, including two callers and absent/expired credentials. Never capture caller tokens as installation settings.
- [ ] Update HTTP configuration examples, file-mode consumer fixtures and executor tests for the new syntax. Coordinate the paired managed change before releasing the resulting Sidecar build.
