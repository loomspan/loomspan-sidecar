# Validate, inspect and publish configuration through protected management APIs

## Outcome

Authorized management users can inspect published/submitted snapshots, validate their
private draft with the new framework API, and explicitly publish an exact validated
candidate. Responses distinguish stale editing, invalid content and post-activation
bookkeeping faults so the console never misrepresents what is running.

## Requirements

- Build on real accounts/sessions from PR 1.3.1, private drafts/leases from PR 1.3.2
  and Phase 2's durable publication coordinator. Provide protected management APIs
  for current configuration, retained snapshot history/detail, runtime/intended/fault
  status, explicit draft validation and explicit publication. Preserve execution JWT
  authentication independently. Require management CSRF protection for mutations.
- Viewers may inspect runtime-published configuration and all retained submitted
  snapshots, including pending/failed authored content and literal sensitive values.
  Editors/admins additionally validate and publish their own session's draft subject
  to current editing ownership. Administrators do not gain access to others' drafts
  or validation results. No implicit activation from reading, saving or validating.
- Current configuration means the runtime-published snapshot, not the intended
  SQLite pointer. Capture consistent IDs/content under real publication/pruning
  coordination; avoid mixed or disappeared reads. Expose runtime and intended IDs,
  known publication status and mutation fault separately. History preserves submission
  order, immutable content and local/source identity. Pending is outcome-unknown;
  expired history is explicitly absent. Do not infer past success or failure.
- Replace editor use of `prepare()` with the delivered public
  `SkillReloader.validate(Collection<SkillDocument>)` against the complete frozen
  proposed skill set. Consume `SkillValidationResult.valid()`, structured issues and
  immutable `ValidatedSkill(name, SkillKind)` metadata. Warnings do not block a valid
  result; any error means candidate metadata is unavailable. Never use the active
  catalog to validate draft routes or independently parse framework skill YAML.
- Sidecar still checks authored REST routes/targets, URL-variable allowlists and
  resolved URLs, and relevant client preparation. Use successful validation metadata
  to reject missing REST routes and routes referencing unknown/non-REST skills.
  Keep existing supported REST/SSL/auth constraints. Release temporary clients after
  validation; do not stage a generation, retain a publishable candidate, change the
  pointer or create submitted history. Framework validation itself allocates no
  generation ID; explicit Publish still prepares and stages afresh.
- Preserve issue severity, source label, skill name and available field/location
  information for the owning session. Adapt the Phase 1 result model where needed;
  a generic error string must not erase the new framework diagnostics. Never disclose
  another draft or resolved deployment secrets. Associate the result with the exact
  frozen candidate; edits clear it and a late result cannot advertise newer edits as
  valid. Responses identify stale/discarded results clearly. The API supports future
  automatic checking; Phase 4 chooses debouncing/presentation. Polling/automatic
  validation is not login or lease activity.
- Ordinary Publish requires successful complete validation of that exact candidate.
  Serialize admission with the real runtime update lock: recheck current authenticated
  account/role, valid session, tab and lease grant, healthy configuration state,
  runtime base and validation before accepting/finally freezing an update. A request
  waiting for serialization has not started; revoked credentials or stale ownership
  while waiting must prevent acceptance. A controller check before waiting is not
  sufficient, and holding all editing operations through preparation is not allowed.
- After acceptance, run the frozen update through success or failure handling
  regardless of later logout, session/lease expiry, takeover, account disable/role
  change, draft edits/discard or browser disconnect. No cancel endpoint, durable job
  service or extra shutdown drain period. Operational failure and process interruption
  retain Phase 2's existing policies; do not promise completion across a crash.
- Preserve database-first publication: prepare/stage, commit pending B and intended
  pointer, then publish. Commit failure leaves A; publication failure attempts revert
  to A and retains failed B. Failed revert faults mutations while execution stays on
  A and intended remains B. Successful publication invalidates old drafts/leases via
  PR 1.3.2, even if later outcome recording fails. In that latter case execution and
  intended stay B, bookkeeping is unknown and further mutations stop. Never map all
  thrown exceptions to a claim that activation failed or retry publication blindly.
- Provide actionable, documented responses for authentication/authorization failure,
  lease/base/candidate conflicts, validation issues, unavailable history and mutation
  faults. Distinguish a rejected/failed activation from activation followed by failed
  bookkeeping. History and runtime inspection let a reconnecting user determine
  current state without a separate durable operation-status subsystem. Choose exact
  URI/payload/status-code contracts in planning consistent with existing API style.
- Configuration faults gate draft/validation/publication mutation paths consistently
  while preserving authorized inspection and session/private-state cleanup. Account
  administration stays distinct from managed-configuration mutations, subject to its
  own storage availability and authorization. Execution continues per Phase 2 policy.
- Keep source content as authored, including URL placeholders. Accounts, email settings,
  sessions, leases and arbitrary deployment properties are outside managed snapshots.
  Import/export, rollback, destructive confirmation/cutover and browser editor UI
  remain Phase 5/4 work. Do not add a public unchecked-validation publication bypass.

## Acceptance criteria

- [ ] Real authenticated management HTTP tests prove role hierarchy, CSRF, draft/result
  privacy and isolation from execution JWT permissions across all new operations.
  Read/save/validate cannot activate configuration.
- [ ] Published content/history inspection remains consistent during concurrent
  publication/pruning, distinguishes runtime/intended/status/fault, includes pending
  and failed submitted content, and reports expired history without inventing outcomes.
- [ ] New validation integration uses only supported public framework types and
  validates complete candidate skills plus matching REST content without `prepare()`
  or generation staging. Tests cover additions/removals/kind changes, warnings,
  labelled errors, route mismatches and URL binding failures. Temporary resources
  are released; authored placeholders, active state and submitted history are unchanged.
- [ ] Editing during validation, equal-content edits, lease/session loss and stale
  responses cannot mark a different draft valid or leak discarded private results.
  Automatic checks/status requests do not extend inactivity timers.
- [ ] Publish rejects missing/failed/stale validation and rechecks account, session,
  role, tab, grant and base after waiting for serialization. Accepted updates retain
  their frozen content through logout, expiry, takeover, account change and disconnect.
  Real session/account races extend the earlier Phase 2 frozen-content evidence.
- [ ] Real SQLite/framework integration through the management API proves successful
  activation and invalidation, commit failure, publish/revert success, failed revert
  and failed outcome recording after activation. Responses/status inspection describe
  actual execution state, preserve required resources and enforce mutation faults.
- [ ] Concurrent draft operations cannot escape successful invalidation; failed
  ordinary publication preserves valid drafts/leases. Execution dispatch remains
  available during updates and the existing shutdown budget is preserved.
- [ ] API and operator documentation explains payloads, conflicts, validation severity,
  unknown outcomes, recovery and later-phase boundaries. Relevant execution,
  publication, session/security and architecture regression checks pass against
  the installed snapshot; no framework-only evidence substitutes for Sidecar tests.
