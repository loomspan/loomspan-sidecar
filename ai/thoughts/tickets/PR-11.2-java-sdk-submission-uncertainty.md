# PR 11.2: Preserve acceptance uncertainty for Java SDK submission failures

## Development constraints

**Sidecar is still in development. Destructively replace superseded contracts,
code and schemas; no compatibility shims, legacy adapters, parallel legacy APIs
or migration machinery solely to preserve obsolete development behavior.**

Apply the [design lens](../design-lens.md#simplicity-and-technical-debt). Choose
the simplest complete solution, minimize technical debt, and keep tests and
documentation proportional. No development-data reset is expected. Document any
required reset and its impact; no deployed-data deletion is authorized.

## Outcome

Callers can distinguish an uncertain submission from local failure or a status
wait ending. If work may have been submitted but no reliable acceptance response
is available, the Java client reports acceptance unknown so applications do not
mistake that outcome for proof that work never began.

## Requirements

- Correct `SidecarClient` submission classification: oversized successful
  submission responses must yield `AcceptanceUnknownException`, including
  declared-length and streamed overflow. Never infer an execution ID from partial
  content, headers or Location.
- Interruption after a request may have been sent must preserve the interrupt
  flag and report acceptance unknown rather than a generic wait-termination
  outcome. Interruption detected before dispatch must send no request and be
  represented as a local pre-send failure, preserving the interrupt flag.
- Keep known HTTP error status in `HttpFailureException` even if the error body
  exceeds the response bound or is unusable. HTTP errors do not prove absence of
  execution effects. Preserve safe available problem details only within bounds.
- Keep local validation/closed-client failures distinct from possible-send
  outcomes. When transport evidence cannot prove no send, classify conservatively.
- Retain one attempt, disabled redirects/replay, resource cleanup, existing total
  deadlines and bounds. Never automatically retry or cancel server execution.
- Preserve status-read and wait behavior, including requested execution IDs,
  last valid snapshots and interrupt handling. Update documentation and the test
  currently expecting ProtocolException for an oversized 202 submission response.

## Acceptance criteria

- [ ] Helpers, code paths, test fixtures and dependency declarations made unused
  by this ticket are removed. Confirm remaining production and test consumers
  before removal; preserve anything required by TLS/mTLS, SSL bundles or other
  retained features. Verify affected builds and tests after cleanup, without
  expanding into unrelated cleanup.
- [ ] Oversized fixed-length and streamed success responses after submission
  produce acceptance unknown without a fabricated ID or additional attempt.
- [ ] Before-dispatch interruption sends nothing and is a local failure;
  interruption after possible dispatch reports uncertainty. Both preserve the
  thread interrupt flag and release request resources.
- [ ] Known HTTP error statuses survive oversized/unusable error bodies, without
  exposing out-of-bound or sensitive diagnostic content.
- [ ] Existing lost/malformed-response uncertainty, local failures, status-read
  context, wait termination and bounds remain correct under focused regression tests.
- [ ] Documentation accurately distinguishes these outcomes; required checks and
  independent review supply fresh evidence with provider-free fixtures.
