# Recover intended configuration and retain bounded snapshot history

## Outcome

Sidecar's durable store reliably identifies the complete configuration to activate
after restart, preserves inspectable publication attempts, and retains bounded
history without deleting configurations still needed by execution or publication.
Operators have a verified database backup and recovery procedure.

## Requirements

- Build on PR 1.1.1's SQLite/Flyway/Spring JDBC store and immutable authored
  snapshots. Provide the storage operations needed by the database-first publication
  policy, without implementing the framework publication coordinator in this ticket.
  After candidate validation/staging, one transaction stores candidate B as pending
  and switches intended production from A to B. Failure leaves A selected and no
  partial B. Retain A; never mix its skills with B's REST configuration.
- Support recording B as published after successful runtime activation, and restoring
  the pointer to A and recording B as failed after rejected publication. Keep B as
  inspectable history on failure. Surface transaction/outcome-recording errors to
  the caller; do not hide them through fallback or automatic reconciliation.
  Operations must not silently overwrite an unexpected current pointer.
- Restart loading follows the committed pointer regardless of recorded status.
  A crash after committing B but before publication/reversion selects B; a completed
  revert selects A. Pending means outcome unknown, not proof of failure. Successful
  startup activation later records the selected snapshot as published; other pending
  history stays unknown. Provide this storage behavior without inventing past outcomes.
- Distinguish a genuinely new store from an initialized store with missing, malformed
  or unreadable current content. Only the former gets the empty initial configuration.
  The loader must return one complete selected snapshot or fail with actionable,
  secret-free diagnostics. Do not silently select older history or empty content.
  Complete migrations before load. Do not adopt the old mounted configuration.
- Distinguish intended production from the runtime-published snapshot in the storage
  contract and documentation. Reading the pointer does not establish what an
  execution used or what should be exported. Runtime mapping, export capture and
  diagnostics are later consumers, not alternate database pointers to introduce here.
- Retain the latest ten stored snapshots by default, including pending/failed
  submissions and current production. Use positive
  `loomspan-sidecar.snapshots.max-retained` with default `10`. Protect the current
  pointer and snapshots needed by in-flight publication or live generations. These
  count toward the target and may exceed it; prune oldest eligible records first.
  The pruning operation accepts a set of protected snapshot IDs supplied by its
  caller and always protects the current database pointer in its transaction.
  Do not add a storage-owned live-generation registry or reference-counting service.
  Phase 2 owns runtime protection and coordinates publication with pruning so the
  supplied set remains sufficient throughout the operation.
- Prune at startup and after completed update attempts when the database is usable.
  This ticket provides the pruning operation and storage-startup invocation; Phase 2
  supplies runtime protection and completed-update invocation. Retirement releases
  runtime resources/protection but never directly deletes database history. Excess
  history can remain until the next pruning opportunity. An expired snapshot lookup
  reports absence; traces do not pin snapshots forever.
- Document and verify a minimal consistent full-database backup/restore procedure
  for the supported single-instance local persistent-volume deployment. A stopped
  instance procedure is sufficient for v1; no online backup service is required.
  Account/session configuration transfer is not introduced. Full installation backup
  is distinct from Phase 5 authored-configuration export, excludes no database data
  by redaction, and adds no encryption. Account loss recovery belongs to Phase 3.
- Document and verify storage recovery from a consistent database backup when the
  selected state is unreadable or invalid, and explain committed-pointer restart
  selection. Do not interpret pending as failed or automatically rewrite outcomes.
  Phase 2 owns concrete runtime publication-fault recovery procedures and their
  verification alongside the actual coordinator. No recovery journal, automatic
  reconciliation service or speculative repair framework.

## Acceptance criteria

- [x] Real SQLite tests prove atomic A-to-B submission, complete selected-content
  loading, successful reversion retaining failed B, and independent status recording
  without changing immutable content or identity. Unexpected pointer state is rejected.
- [x] Reopening after interrupted/uncommitted writes selects A; reopening after B's
  commit selects B even when status remains pending; reopening after reversion selects
  A. No recovered snapshot mixes skill and REST versions. Include actual interrupted
  write/process evidence, not only repository mocks.
- [x] Initialized-store load failures surface errors without reseeding/fallback or
  secret-bearing diagnostics. Historical pending outcomes are not fabricated.
- [x] Retention tests cover the default/configured positive limit, rejection of
  invalid limits, failed/pending records, oldest-eligible pruning, protected records
  exceeding the target, current-pointer protection even when omitted by the caller,
  and pruning on a later call when an ID is no longer supplied as protected.
  Deleted history is explicitly absent. Runtime protection races belong to Phase 2.
- [x] Backup/restore is verified against real SQLite on the supported deployment
  model and recovers the same complete intended configuration and retained history.
  Operator documentation includes concrete database restore steps and explains
  intended versus runtime state, backup scope and absence of v1 encryption.
- [x] Documentation and tests clearly distinguish this ticket's storage evidence
  from the deferred runtime failure, restart-gating and retirement checks below.

## Context

Planning identifier: **PR 1.1.2**, not a GitHub pull-request number.

Depends on [PR 1.1.1](2026-09-17-pr-1.1.1-durable-configuration-snapshot-storage.md).
Follow the [roadmap](../phases/2026-09-16-management-console-roadmap.md) and
[design lens](../design-lens.md). This is one focused storage lifecycle unit for
GPT 5.6 Sol. It adds no browser workflow, management API, account administration,
import/rollback execution or framework publication coordinator.

Phase 2 must serialize accepted updates through failure handling, prepare complete
documents with the public framework API, stage matching REST resources/mappings,
commit B and publish it. Failed publication attempts revert to A. Failed revert
stops configuration mutations, exposes A/B and keeps execution on A. Failed outcome
recording after successful publication stops mutations but keeps execution/resources
on B. It must not undo successful publication. Inspection remains available.
Phase 2 must document and verify operator recovery for both runtime fault states;
Phase 1 database restore tests do not establish those procedures. Phase 2 also owns
the protected-ID set and coordination needed to prevent pruning a snapshot needed
by a live generation or update, with real integration race coverage.

Phase 2 also owns actual startup dispatch gating: ordinary framework discovery must
be empty using documented `loomspan.skills.locations` with a controlled empty source
(an empty list alone can fall back to scanning). Register retirement before staging,
load the selected snapshot, prepare/stage/publish, then open dispatch. Any load or
activation error fails startup; no management-only recovery server. Only public
`ai.loomspan.api` types are allowed in application/tests, with ArchUnit enforcement;
preserve the existing single framework shutdown budget.

Use the installed beta 5 snapshot and matching local framework checkout; no framework
rebuild, snapshot repository, release or tag. Hosted CI awaits published beta 5.
