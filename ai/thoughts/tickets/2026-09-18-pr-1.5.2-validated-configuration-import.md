# Import current configuration through validated local publication

## Outcome

Editors can restore an exported configuration or promote it to another instance
without restarting. Every import is a new preparation/publication attempt on the
destination, whose history continues to describe only that server's own operations.

## Requirements

- Add management API and embedded-console import for editors/admins; viewers may
  export/inspect but cannot import. Enforce roles and CSRF server-side, keep execution
  JWT authorization separate and preserve idle-session/draft privacy rules.
- Read only PR 1.5.1 format-1 current-configuration bundles, enforcing its 100 MiB
  compressed, 512 MiB expanded and 10,000-entry inclusive limits end to end. Configure
  upload handling so incidental smaller defaults do not defeat these bounds; bound
  and clean temporary data without creating durable upload/job storage. Import is
  complete replacement, never merge, history transfer or a private-draft import.
- Show incoming source identity/producer versions, skill/route counts and validation
  feedback before destructive confirmation. Bind reviewed content to the exact
  candidate accepted for import; changing the upload requires a new review. No
  detailed configuration diff is required. Render content/errors as text.
- Validate the full destination candidate with supported framework validation and
  Sidecar route/target checks. Preserve authored placeholders in stored content;
  resolve whole-value `${NAME}` REST base URLs only through the destination's exact
  allowlist and process environment. Reject missing, undeclared, blank or invalid
  bindings before destructive cutover. Literal URLs remain supported. Deployment
  configuration, accounts and other excluded installation state remain untouched.
- Before accepting an update, show the current lease owner's identity when present
  and explicitly warn that all session drafts will be discarded and editing leases
  broken. Editors need not own the lease or obtain admin takeover. Require explicit
  confirmation bound to the specific lease grant (or absence) and runtime-published
  snapshot. Recheck both under update serialization; replacement grants, even for
  the same owner/tab/session, require refreshed confirmation. Renewal alone does
  not. A conflict leaves drafts intact and refreshes the confirmation information.
- Serialize import with ordinary publication and rollback. Freeze content on
  acceptance; call public `prepare(Collection<SkillDocument>)` afresh and validate/
  stage complete matching REST resources before discarding drafts. Earlier validation
  is not a retained prepared update. Preparation/staging failure leaves editing state
  intact subject to normal expiry. Defer competing lease/draft operations from the
  confirmation check through completion so new ownership cannot arise mid-update.
- Once preparation/staging succeeds, discard drafts/break leases, persist a fresh
  local snapshot and intended pointer through the existing database-first policy,
  and call `publish()`. Every import, including identical repeated imports, gets a
  fresh local ID; source ID is provenance only. Preserve destination history under
  normal retention; never import source history/status or overwrite local identities.
  Notify invalidated sessions through existing management responses/status refresh.
- Accepted updates are non-cancellable by browser disconnect, logout, session/lease
  expiry or later management actions. Existing shutdown/process-failure policies
  still apply. Execution dispatch continues; admitted work retains its generation.
  Do not add a job system, automatic retry or a cancel action.
- Reuse publication failure semantics: failed database commit does not publish;
  failed activation attempts pointer reversion and records a failed submitted snapshot
  when persisted. Already discarded drafts stay discarded. Reversion failure stops
  configuration mutations for operator recovery while inspection/existing execution
  remain available. Successful activation followed by bookkeeping failure is not
  activation failure and must not be undone. Pending means outcome unknown; restart
  follows the committed pointer. Reflect these distinctions in UI and documentation,
  using local history for reconnect/outcome inspection.

## Acceptance criteria

- [ ] Browser/API round trips and two-instance transfers preserve complete authored
  skills/routes/targets while publishing a fresh destination snapshot without restart.
  The same placeholder resolves to each destination's URL. Repeated identical imports
  create distinct local IDs, retain provenance and do not import source history/status.
- [ ] Invalid format/checksum/content, unsupported format, excessive uploads and
  missing/undeclared/blank/invalid bindings fail before destructive changes. Valid
  large uploads within the stated bounds reach validation without smaller upload
  defaults; literal URLs and empty complete configurations are supported.
- [ ] Authenticated browser tests cover viewer rejection, editor/admin import without
  lease ownership, CSRF, safe review/feedback and explicit disruption confirmation.
  Changed content, runtime snapshot or replacement lease cannot use stale confirmation;
  lease renewal alone does not invalidate it. Rejected confirmations preserve drafts.
- [ ] Concurrent publication and lease/draft requests cannot cross the confirmed
  update boundary. Preparation/staging failure preserves drafts; successful cutover
  clears them and notifies other sessions. Disconnect/logout/expiry cannot cancel an
  accepted attempt, and execution continues with correct generation resources.
- [ ] Database/activation/reversion/bookkeeping failure evidence proves the existing
  pointer, history, fault and restart policies; post-cutover failure does not resurrect
  drafts. UI distinguishes success, failure and unknown outcome and links to history.
- [ ] Destination installation settings/accounts stay unchanged. Temporary upload
  data is cleaned on completion/rejection with bounded handling; user/operator docs
  explain promotion, destination requirements, limits and recovery boundaries.
