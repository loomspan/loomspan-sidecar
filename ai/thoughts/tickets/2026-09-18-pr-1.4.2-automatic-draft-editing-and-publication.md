# Author configuration with quiet automatic saving and validation, then publish

## Outcome

Editors can create, change and remove complete skill and REST configuration in the
browser, with unobtrusive saving and validation feedback. They explicitly publish
the validated candidate without restarting Sidecar, while concurrent sessions and
tabs cannot overwrite each other's work.

## Requirements

- Build on PR 1.4.1's embedded console and the completed Phase 3 draft, lease,
  validation and publication APIs. Support the full framework-supported YAML skill
  surface, including model-backed and REST skills, through a full YAML text editor;
  provide complete REST route/target editing. Preserve authored URL placeholders.
  Do not add Java skill hosting, a structured skill editor, arbitrary Spring/model
  connection editing or console-managed destination bindings.
- Editors/admins begin from runtime-published configuration and edit their own
  session's draft. Viewers remain read-only. Show editing ownership and offer
  acquisition, release, discard, resume and explicit admin takeover. A second tab
  in the same session may read but cannot silently take over the writable tab.
  No user, including an admin, inherits or reads another session's private draft.
- Automatically save edits to the session draft. Show subtle lower-left status-bar
  feedback such as "Saving..." and "Saved", with accurate unsaved/save-failure
  states. "Saved" means the server acknowledged the current content, not that it is
  published or recoverable after logout. Late acknowledgements cannot mark newer
  unsaved text saved. Preserve editable local text during transient save failures
  while its session/base remain valid; do not blindly retry stale writes.
- Validate the complete draft automatically after a pause in editing and coalesce
  requests. Above the editor show a compact green "Valid" or red "Validation errors"
  indicator with details users can expand. Keep details collapsed until requested;
  no interrupting dialogs, unsolicited expanded error lists or focus stealing for
  automatic checks. Show quiet checking/out-of-date states, and use text alongside
  color. Expanded feedback preserves severity, source labels and available skill,
  field/location information. Warnings do not turn a valid result into an error.
- Saving, checking and publication are separate effects. Check the exact complete
  candidate represented by the draft; edits invalidate old validation immediately.
  Late save/validation responses must not overwrite new text or mark a different
  candidate valid. Exact editor component and save/validation timing belong in
  implementation planning, preserving the low-key user experience.
- Renew ownership at most every 30 seconds while meaningful activity occurs:
  typing, paste, clicks, scrolling or explicit Continue editing. Mouse movement,
  background polling, automatic save/validation traffic and an open tab alone do
  not count as activity. Use the configured lease/login inactivity limits (defaults
  15 and 30 minutes); warn two minutes before lease expiry. Distinguish user activity
  from background requests so login and editing cannot remain alive indefinitely.
- Lease expiry/loss or release preserves the session draft and local editor text
  while the session/base remain valid, but disables stale writes. Resumption needs
  the unchanged runtime base and a new lease. Explicit admin takeover starts from
  production; the former owner retains only its own still-valid draft. Discard,
  logout/session expiry and a changed runtime-published base clear affected edits
  under the agreed policy; explain invalidation and require starting over. No
  cross-session recovery or browser persistence that bypasses these rules.
- Provide explicit Publish for the exact successfully validated candidate, subject
  to current role, session, tab, lease, base and healthy configuration state. Pending
  autosaves cannot cause older content to be silently published as current edits.
  Server admission remains authoritative. Explain rejected/stale attempts and
  validation failures without silently losing valid edits.
- An accepted update uses frozen content and cannot be cancelled by later edits,
  lease loss, takeover, logout, account changes or disconnect. Provide no cancel
  operation or blind retry after an uncertain response. Successful publication
  clears old-base drafts/leases; ordinary failed publication preserves them subject
  to their lifecycle. Distinguish activation failure from successful activation with
  failed bookkeeping; show runtime/intended mismatch and mutation faults accurately.
  A disconnect or pending outcome is not proof of failure. PR 1.4.3 supplies retained
  history for later outcome inspection; this ticket owns accurate immediate results.
- Deliver keyboard-operable controls and feedback, safe text rendering, browser
  workflow evidence and authoring documentation. Use the real public management
  contracts; do not move framework YAML validation into the browser.

## Acceptance criteria

- [ ] Browser workflows create, modify and remove supported skills and REST
  routes/targets, preserving full YAML and placeholders. Automatic draft saves do
  not alter execution; explicit successful publication updates the catalog without
  restart. Unsupported deployment settings and Java skills are outside the editor.
- [ ] Save feedback is subtle and accurate for in-flight, acknowledged, failed and
  newer unsaved edits. Delayed/out-of-order responses and transient failures neither
  overwrite text nor falsely report it saved or valid.
- [ ] Complete-draft checking follows an editing pause, coalesces work and produces
  quiet expandable Valid/Validation errors feedback with labelled details and
  warning semantics. Editing makes prior results out of date immediately; automatic
  checks do not interrupt typing or open error details without user action.
- [ ] Two-user and same-session/two-tab browser scenarios prove private drafts,
  exclusive editing, role restrictions, ownership display, release/discard/resume
  and explicit admin takeover. Lease loss preserves still-valid text and prevents
  stale writes; changed base/logout/session expiry invalidate the affected edits.
- [ ] Meaningful activity renews within the agreed cadence, the expiry warning is
  shown, and background autosave/validation/polling or mouse movement alone cannot
  sustain login or ownership. Configured inactivity limits govern the workflow.
- [ ] Publish cannot silently use older saved/validated content. Stale admission
  and validation failures have accurate feedback. Successful publication invalidates
  old drafts; ordinary failure preserves valid edits. Accepted updates continue
  through later session/lease changes without a cancellation control.
- [ ] Browser-visible results distinguish failed activation, active configuration
  with bookkeeping failure, runtime/intended mismatch and unknown outcomes. Mutation
  faults disable affected operations; execution remains available under existing
  policy. No uncertain response triggers blind republication.
- [ ] Keyboard use and safe content rendering work; this ticket's browser/API
  integration and relevant execution/security/shutdown regressions pass against the
  installed snapshot, and saving, validation, publication and edit-loss rules are
  documented without deferring correctness to Phase 6.
