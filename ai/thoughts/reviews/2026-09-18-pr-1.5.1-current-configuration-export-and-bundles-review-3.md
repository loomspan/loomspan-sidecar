## Findings

### [P2] Allocate from actual ZIP payload bytes
- Location: `src/main/java/ai/loomspan/sidecar/bundle/ConfigurationBundleV1.java:211` (before fix)
- Scenario: A small ZIP claims a near-512 MiB uncompressed entry size in its central directory but contains a short payload.
- Impact: Reading an invalid bundle allocates a near-512 MiB byte array before validating any payload bytes, risking avoidable heap exhaustion and process disruption.
- Evidence: `readEntry` previously constructed `new byte[(int) entry.getSize()]`; the expanded-byte check occurred only after allocation. The entry-size upper bound permits claims through 512 MiB. The new regression test for exaggerated central-directory metadata passes after the fix.
- Fix: Buffer bytes as they are actually decompressed, reject data beyond the claimed size or total expanded bound, and validate final size and CRC.

## Findings Resolved in This Context

- Applied the `readEntry` change and added the forged near-512 MiB size case to `rejectsMisleadingCentralDirectorySizeAndDuplicateEntryNames`. Re-reviewed the change for size, CRC, cleanup, and exception behavior. No other actionable findings remain in this context.
