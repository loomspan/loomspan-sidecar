## Findings

### [P2] Prove runtime history protection across the retention limit
- Location: `src/test/java/ai/loomspan/sidecar/configuration/RuntimeConfigurationIntegrationTest.java:313`
- Scenario: A generation remains admitted while multiple complete snapshots are published and the database exceeds `max-retained`; a later publication runs pruning after that generation retires.
- Impact: Storage-only pruning tests could pass even if the runtime supplies the wrong live-generation IDs or drops them too early, allowing a still-required snapshot to be deleted.
- Evidence: Before this review, the runtime tests exercised publication and retirement but did not drive actual publication pruning across the retention target with live admissions. The ticket explicitly requires this interaction.
- Fix: Added `publicationPruningProtectsAdmittedGenerationsThenRemovesEligibleHistory` with real framework admissions and SQLite. It verifies protected overflow, subsequent retirement, and deletion at the next publication while other live snapshots remain.
