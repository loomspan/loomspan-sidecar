## Findings Resolved in This Context

### [P2] Anchor the overlap JWKS to the startup working directory

- Location — `sdks/python/src/loomspan_sdk/_callback_trust.py:91` and `:120`.
- Scenario — An application opens a verifier using the documented relative
  path, changes its process working directory, and receives a credential signed
  by a key in another file at that relative path. A miss-triggered read before
  this fix published keys from the other directory. Periodic polling had the
  same path behavior.
- Impact — A callback can authenticate under an unintended set of keys, and a
  process directory change can also withdraw the intended keys.
- Evidence — `test_relative_overlap_keeps_startup_directory` reproduced
  authentication under the second directory before the fix. It now rejects
  that credential, retains the original configured trust, and still adopts a
  replacement at the original pathname.
- Fix — Capture the absolute path at initialization without resolving symlinks,
  map a working-directory lookup failure to the safe unavailable category, and
  preserve that pathname for subsequent reads. Document startup path anchoring
  in the SDK README.

## Open Questions and Assumptions

- Refresh operates on local regular files. Context shutdown waits for a read
  already in progress and discards its result. The API makes no deadline
  guarantee for a stalled operating-system filesystem call.
- The SDK profile specifies valid RSA public numbers and a minimum modulus
  size. Java and Python crypto providers can impose different implementation
  limits for unusually large keys or exponents. The installed interoperability
  run uses the production Java issuer's standard colocated keys.
