## Findings

### [P2] Preserve inspection when a mutation fault also prevents SQLite reads
- Location: `src/main/java/ai/loomspan/sidecar/configuration/RuntimeConfigurationService.java:202`
- Scenario: A submitted B cannot be reverted because SQLite becomes unavailable. `inspect()` immediately called `store.current()` and threw the same storage exception before returning its known running A, intended B, pending status and mutation fault.
- Impact: The operator loses the required internal fault-state inspection at the moment it is needed for stopped-instance recovery.
- Evidence: The service already knows B from the successful submit and A from `publishedId`, but previously kept no fallback intended selection. The fault-matrix test only injected a revert hook while SQLite remained readable.
- Fix: Retain the last confirmed intended ID/status through startup and each transaction outcome. On an inspection read failure, return that state with a mutation fault and stop further mutations. A real temporary SQLite test now makes the selection table unreadable after a failed revert and checks both IDs, pending status and fault.

### [P2] Prove nested REST routing after publication
- Location: `src/test/java/ai/loomspan/sidecar/rest/RestGenerationIntegrationTest.java:57`
- Scenario: The existing generation test held a direct REST admission across publication; the separate nested test completed without publication. Neither would catch a regression that routed a model's later nested REST call through the new generation.
- Impact: A primary acceptance condition, generation matching for nested work, lacked executable evidence despite the direct-call tests passing.
- Evidence: The old test invokes the REST handle directly after B is published; the nested API test never publishes B. The fixed handler relies on `RestSkillInvocation.generationId()` for the later nested lookup.
- Fix: Added a model-response gate and an authenticated integration test that publishes route-only B after the old root is admitted but before its nested REST action. It asserts the nested call reaches A, a new root reaches B, and the old execution retains A's durable ID.

### [P2] Treat a failed generation binding as a post-commit publication rejection
- Location: `src/main/java/ai/loomspan/sidecar/configuration/RuntimeConfigurationService.java:161`
- Scenario: If generation binding fails after `store.submit()` has committed B, such as when resource shutdown clears the mapping concurrently, the former commit catch reported a pre-commit failure and left B selected without a revert or mutation fault.
- Impact: The reported outcome could say A remained intended while a restart would select B.
- Evidence: `resources.bind()` formerly shared the `store.submit()` catch, which only discarded resources and pruned. Binding is a separate operation after the durable transaction.
- Fix: Moved binding into the post-commit publication try block, so failure follows the guarded B-to-A revert path and establishes the specified fault state if revert itself fails.
