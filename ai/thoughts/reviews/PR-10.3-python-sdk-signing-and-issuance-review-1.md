## Findings

### [P2] Reject malformed identifiers inside open PKCS#8 values

- Location `sdks/python/src/loomspan_sdk/_signing.py:88`, complete BER decode.
- Scenario. A provided PEM contains an optional attribute with an OID value
  ending in an unterminated continuation octet, or a tag encoded using a
  forbidden long form. This also occurs inside a constructed open value.
- Impact. Startup accepts malformed PKCS#8 and replaces the prior export.
  The same synthetic key with these malformed encodings fails Java signing
  initialization. This violates the strict input contract.
- Evidence. The ASN.1 structural decoder accepts the truncated OID
  `06 02 2A 81` and the small tag encoded as `1F 02 01 01`. Typed decoding
  leaves open attribute values opaque. A scratch probe through the actual
  Java `SigningKeys.initialize` rejected both. Four Python regression cases
  failed before the fix because initialization returned a signer.
- Fix. Use the existing libraries to walk the validated BER children and
  apply the typed OID check and the BER minimum identifier form before
  canonicalization. Preserve normal long tags and indefinite-length values.

### [P3] Explain POSIX permissions after replacing a public export

- Location `sdks/python/README.md:49`, signing operations.
- Scenario. An application replaces an existing readable JWKS that a
  separate OS account uses for verification.
- Impact. The receiver loses file access on the next startup if its access
  depended on the old file's mode.
- Evidence. On a Linux scratch filesystem the actual colocated issuer
  replaced a `0644` export with a `0600` file. The original wording said
  operators provision permissions but omitted the per-publication effect.
- Fix. Document owner-only replacement and the operator's responsibility for
  receiver access or public-file distribution after publication.

## Open questions and assumptions

Atomic replacement depends on the destination filesystem supporting atomic
same-directory replacement. Current Java readers can round exact issued
NumericDates, including expiry collapse or overflow at the documented
boundaries. That is the same limitation for Java-issued credentials.
