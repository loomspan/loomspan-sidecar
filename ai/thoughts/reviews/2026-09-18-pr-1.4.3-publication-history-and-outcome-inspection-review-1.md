## Findings

### [P2] Do not claim an expired snapshot's refresh succeeded when it failed
- Location: `src/main/resources/static/management/assets/console.js:165`
- Scenario: A selected detail returns `history_not_found`, then the automatic current/history refresh fails (for example, transient inspection/storage failure).
- Impact: The page had cleared the list/current state but asserted they were refreshed, giving a misleading recovery instruction after an uncertain publication.
- Evidence: `loadHistory(false)` caught errors without returning success/failure, while the detail handler unconditionally overwrote its status with “were refreshed.” The new browser route test reproduces the failing refresh.
- Fix: Return a refresh result and report the failure accurately; preserve revision gating if a newer refresh supersedes this one.

### [P2] Assert the actual retained row positions in the ordering test
- Location: `src/test/java/ai/loomspan/sidecar/management/ManagementHistoryBrowserIntegrationTest.java:81`
- Scenario: The test's assumed `Sequence 1` row is absent or the expected published row is absent.
- Impact: `indexOf` returns `-1`, allowing the oldest-first assertion to pass without proving either relevant row is rendered in order.
- Evidence: The assertion compared `indexOf("Sequence 1")` directly to the published sequence position and never established that both searched strings existed.
- Fix: Find the unique failed/published sequence-plus-UUID labels, assert the failed label exists, then assert the published label follows it.
