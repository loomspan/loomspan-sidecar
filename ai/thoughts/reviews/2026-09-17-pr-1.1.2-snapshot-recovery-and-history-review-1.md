## Findings

### [P1] Isolate application tests from the persistent default database

- Location: `src/main/java/ai/loomspan/sidecar/storage/StorageConfiguration.java:58` and full-context test startup sites, including `src/test/java/ai/loomspan/sidecar/LoomspanSidecarApplicationTest.java:22` before the fix.
- Scenario: Routine `mvn verify` starts the complete Sidecar application in multiple integration tests without a database-path override. The application default resolves to `C:\sidecar\data\sidecar.db` on this Windows host, and the new startup path prunes that database with an empty protected set.
- Impact: A test run can delete historical snapshots from a persistent database outside the test workspace if it has more than the configured retention target.
- Evidence: The initial full run passed 121 tests but logged repeated Flyway access to the default path. The file existed at review time with creation and last-write timestamps of 21:01:34, before the first review run at about 21:08; no pre-run contents or row-count baseline was captured, so the effect on its rows is unknown. A second run after a partial isolation fix still logged 38 default-path accesses, proving the issue extended beyond `@SpringBootTest` classes.
- Fix: Give every test that starts `LoomspanSidecarApplication` a per-class or per-test JUnit temporary database path. The final full run logged zero default-path accesses.

## Findings Resolved in This Context

- Added JUnit temporary database paths to four `@SpringBootTest` classes and eight programmatic application-startup test classes. Existing temporary directories were reused. A source scan of all test references to the application class and `@SpringBootTest` found no remaining startup test without an override; the only unmatched class is an ArchUnit test that does not start the app.
- Re-reviewed the resulting test arguments and Spring property precedence. The first attempt used `SpringApplicationBuilder.properties` in one class, which application YAML overrode; it was replaced with explicit command-line arguments. Another test relied on `arguments[0]` being the skill location; the database argument was moved after it. Focused and full runs then passed with zero default-path log entries.
