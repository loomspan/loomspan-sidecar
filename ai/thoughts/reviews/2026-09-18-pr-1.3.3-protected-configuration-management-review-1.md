## Findings Resolved in This Context

### [P1] Keep resolved route names out of validation diagnostics
- Location: `src/main/java/ai/loomspan/sidecar/rest/RestRouteCatalogValidator.java:34`; `src/main/java/ai/loomspan/sidecar/rest/RestRouteLoader.java:108`
- Scenario: An editor submits REST YAML with a route key `${SENSITIVE_ROUTE}` where the Spring environment resolves that property to a deployment secret. The route names an unknown skill or target, so explicit validation returns a route error.
- Impact: The new validation HTTP response could disclose the resolved deployment value to a management editor. The ticket explicitly prohibits disclosure of resolved deployment secrets.
- Evidence: `RestRouteLoader` resolves route keys through `ConfigurableEnvironment` and stores the resolved name as the route map key. The prior route binding errors interpolated that key into both the location and message; the loader's unknown-target check interpolated `route.skillName()` into its location. `RuntimeConfigurationService.validationIssue` returns that message and location to the owning session.
- Fix: Retained the authored route key in the parsed route and used it for route binding diagnostics. Resolved names still select candidate skill metadata and targets. Added `routeBindingDiagnosticsUseAuthoredNameInsteadOfResolvedProperty` to cover both unknown-skill and unknown-target errors. No framework parser or new configuration contract was added.
