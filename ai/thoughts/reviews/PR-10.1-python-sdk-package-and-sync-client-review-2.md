## Findings

### [P2] Reject server-role TLS contexts before dispatch

- Location `sdks/python/src/loomspan_sdk/_sync_transport.py:27`.
- Scenario. An application passes an `SSLContext` constructed with
  `PROTOCOL_TLS_SERVER`, sets `verify_mode=CERT_REQUIRED`, and enables
  `check_hostname`. CPython accepts these configuration values. The SDK
  accepted the context as a verifying client context and opened a TCP socket.
- Impact. Wrapping the socket as a TLS client necessarily fails. A submission
  was reported as `AcceptanceUnknown`, incorrectly attributing a local
  configuration defect to possible dispatch and opening a needless connection.
- Evidence. A loopback probe reproduced `AcceptanceUnknown` with one connection
  and zero HTTP requests. The new constructor regression failed on the reviewed
  implementation with `DID NOT RAISE LocalFailure`.
- Fix. Check the TLS context role alongside verification and EOF options, then
  report invalid contexts during construction before opening a connection.

## Findings Resolved in This Context

The verifier now rejects `PROTOCOL_TLS_SERVER` for HTTPS and the public error
and README identify the required client context. The regression asserts
`LocalFailure` with no low-level exception context and zero peer connections.
Private CA, mutual TLS, hostname mismatch, authenticated EOF, and concurrent
close scenarios still pass. No actionable findings remain after the rerun.

## Active Project Guardrails

- The package communicates through existing HTTP routes. It introduces no
  Java or Framework dependency, schema migration, compatibility path,
  signer, or trust material management.
- h11 owns framing. The transport owns socket lifecycle and deadlines, and
  shared protocol logic owns mapping and errors. The runtime dependency and
  tests stay within the isolated Python package.
- Credential and business data boundaries are separate. Tests use synthetic
  bearer values and ephemeral certificates. The example avoids putting the
  credential on the command line or printing it. Docs describe the installed
  client and explain the limits of resolver cancellation and remote recovery.
- Verification used loopback fixtures, disposable artifact directories, and
  standard dependency resolution. No operational data or deployment changed.

## Open Questions and Assumptions

None that prevent the scoped review. The system hostname resolver can outlast
the deadline on the calling thread. Its elapsed time is charged and the SDK
prevents dispatch after expiry. Actual connected I/O is deadline-bounded.
