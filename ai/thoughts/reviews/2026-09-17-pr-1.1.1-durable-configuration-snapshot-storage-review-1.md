## Findings

### [P1] Reject an existing database without migration history before seeding
- Location: `src/main/java/ai/loomspan/sidecar/storage/StorageConfiguration.java:61`
- Scenario: An existing database file is truncated to zero length, or an existing SQLite file has no Flyway history. On restart, SQLite opens it, Flyway sees an empty schema, applies V1, and the store creates a new empty current snapshot.
- Impact: A damaged initialized store can silently appear to be a new installation, losing the prior current configuration identity and masking corruption. This violates the fresh-install and corruption acceptance criterion.
- Evidence: Before the fix, `dataSource` connected and `migrate` ran without distinguishing an absent file from an existing file. The existing tests covered missing pointer/status and changed Flyway checksums but no existing file without history.
- Fix: Record whether the database path was absent before connecting. For an existing file, reject zero length without modifying it and require a Flyway history table before migration. Add zero-length and unmigrated SQLite regression cases and document the startup failure.

## Findings Resolved in This Context

- Implemented the preflight in `StorageConfiguration`, added `existingEmptyDatabaseIsNotReseededAsFreshInstallation`, and updated the README. Re-reviewed the resulting source and tests. No actionable finding remains in the ticket-scoped change.
