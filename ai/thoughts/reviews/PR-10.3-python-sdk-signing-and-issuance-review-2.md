## Findings

### [P2] Resolve validation scope for optional PKCS#8 attribute values

- Location `sdks/python/src/loomspan_sdk/_signing.py:67` and
  `sdks/python/src/loomspan_sdk/_signing.py:88`.
- Scenario. A provided key has a normal RSA private key and a valid attribute
  envelope containing an open ASN.1 value whose tag and length are complete but
  whose payload violates its universal type encoding. The typed PKCS#8 schema
  leaves the value opaque. The structural parser accepts these contents and the
  identifier pass does not validate their type-specific payloads.
- Impact. Python can start and publish trust for an input the Java SDK rejects.
  It is an operator-input correctness and fail-startup contract gap. These
  ignored attributes do not change the loaded RSA key, exported JWKS or
  authorization claims.
- Evidence. In a scratch directory, wrap each hex value in the standard
  synthetic RSA key using `pem(with_open_attribute(value))` from
  `sdks/python/tests/test_signing.py:64`. For each PEM, start the current Python
  issuer in provided mode and separately call the actual Java `SigningKeys`
  with the same key, using the locally built Java SDK and Surefire classpath.
  A second Java scratch probe called the Bouncy Castle 1.86 outer ASN.1 reader
  directly to locate the difference. The results below are from current
  editable Python source, independently of the cached wheel finding.

  | Open value bytes | Encoding | Python | Java SDK and outer reader |
  | --- | --- | --- | --- |
  | `17 01 41` | Invalid UTCTime containing only A | Accepts | Rejects invalid UTCTime |
  | `17 02 32 36` | UTCTime with only a two-digit year | Accepts | Rejects invalid UTCTime |
  | `18 04 32 30 32 36` | GeneralizedTime with only a four-digit year | Accepts | Rejects invalid GeneralizedTime |
  | `1e 01 41` | BMPString with an incomplete two-octet character | Accepts | Rejects malformed BMPString |
  | `09 00` | Valid ASN.1 REAL encoding for positive zero | Accepts | Rejects unknown universal tag 9 |
  | `0d 02 2a 81` | Truncated RELATIVE-OID | Rejects | Rejects |

  Properly encoded UTC and GeneralizedTime values and a complete two-octet
  BMPString passed both signers. REAL positive zero has no content octets under
  [ITU-T X.690 §8.5.2](https://www.itu.int/rec/T-REC-X.690-202102-I).
  The REAL result is a Java decoder support limit for an ignored attribute
  value, separate from the malformed cases.
- Recommended scope. Retain strict complete PEM and PKCS#8/RSA decoding,
  including typed algorithm, versions, complete lengths and containers,
  attribute OIDs and nonempty value sets, and embedded public-key agreement.
  Keep the current BER and identifier checks, including the existing valid and
  invalid Java fixtures. Treat arbitrary ignored attribute values as open data
  whose payload validation is delegated to the BER libraries. Under that
  boundary, the three malformed payload types shown above and valid REAL can
  be accepted when the libraries accept them. Truncated lengths, trailing
  elements and invalid structures, identifiers and used fields still fail
  startup. Document the parser boundary and its possible Java differences.
- Stricter option. Require Java-equivalent acceptance of arbitrary optional
  attribute values. Select and verify a parser with that surface on supported
  Python targets, or implement and maintain a Java-specific universal-type
  validation policy around the existing parsers with a differential fixture
  suite. Date decoding and BMP string widths are immediately affected. Even
  standard-valid values such as REAL would need Java-specific rejection.
  Individual tag checks can repair the examples but leave the policy open as
  new decoder differences appear. The current libraries have no demonstrated
  public mode that provides this policy as a unit.
- Status. Open. The ticket requires strict malformed-input rejection and
  escalation before a material parity reduction or substantial bespoke
  machinery. The recommended boundary requires a developer decision.

## Resumption after developer decision

The developer approved delegating validation of unused PKCS#8 attribute
payloads to the BER libraries and documenting the differences from Java. The
implementation plan records the governing decision. The README now states
which parts of the PKCS#8 structure the SDK validates and explains that the
two SDKs can differ on optional ASN.1 time and string payload encodings.

The original probe remains an observation about the libraries. It no longer
represents an open acceptance criterion under the approved boundary. The
tests continue to require identical public identity for a supported key with
well-formed optional values and rejection of malformed BER structure,
identifiers and value sets. A case with an empty attribute identifier and
valid value directly checks rejection of the malformed attribute structure
while preserving the prior public export and input. The suite does not
require a particular library version to accept malformed unused payloads.

Conformance for both startup modes, the strict PEM envelope, supported
optional fields, embedded public-key consistency and fail-startup behavior is
complete under the approved scope. The operator-owned key and public output
contract is unchanged. The implementation, tests, usage docs and verification
changes remain isolated to the ticket.
