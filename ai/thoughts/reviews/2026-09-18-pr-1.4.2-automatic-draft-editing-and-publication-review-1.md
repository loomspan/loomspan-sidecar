## Findings Resolved in This Context

### [P1] Distinguish activated configuration from failed activation in Publish feedback

- Location: `src/main/resources/static/management/assets/editor.js:252`
- Scenario: The server returns `outcome_recording_failed` or `history_pruning_failed` after successfully switching the runtime, or `activation_failed` before the switch. The old browser handler displayed the same generic “Publish did not complete normally” text for both.
- Impact: An editor could treat an active new configuration as unpublished, or fail to recognize that the old runtime remains active. This fails the ticket's immediate outcome requirement and can prompt an unsafe manual repeat.
- Evidence: `RuntimeConfigurationService.publish` sets `published` before outcome recording and returns distinct failure codes; the prior browser catch block only interpolated a generic failure sentence. Browser coverage had success and transport uncertainty but no phase-failure assertion.
- Fix: Map known publication codes to phase-accurate messages, inspect runtime/intended state, and apply the returned mutation fault to local control gating. Added Chromium tests for activation failure and active runtime with failed bookkeeping.

### [P3] Reset REST-only publications between browser tests

- Location: `src/test/java/ai/loomspan/sidecar/management/ManagementEditorBrowserIntegrationTest.java:61`
- Scenario: A browser test publishes only REST YAML, leaving no skill documents. The fixture reset previously checked only for skill documents, so the next test inherited the published REST YAML.
- Impact: Browser tests depended on method order and could validate or compare against another test's runtime configuration.
- Evidence: The browser suite publishes REST-only content in `validDraftPublishesOnlyAfterValidation`; the reset guard used `skillDocuments().isEmpty()` alone.
- Fix: Reset when either skill documents or REST YAML differs from the test baseline.
