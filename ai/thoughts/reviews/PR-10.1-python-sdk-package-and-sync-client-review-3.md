## Findings

### [P2] Handle peer resets during intentionally rejected TLS handshakes

- Location `sdks/python/tests/wire_fixture.py:83` and
  `sdks/python/tests/test_sync_client.py:635`.
- Scenario. The private-CA and client-identity test deliberately rejects TLS
  handshakes. On Windows a peer can see a TCP reset before it receives or
  processes the TLS alert. The server fixture expected `ssl.SSLError` only.
- Impact. The test can fail even though the client produces a safe protocol
  failure, sends no HTTP request for the rejected connection, and otherwise
  supports authenticated HTTPS. This makes the required Windows SDK check flaky.
- Evidence. The first independent native Windows run passed 192 tests and failed
  `test_verified_private_ca_and_client_identity` on server `wrap_socket` with
  `ConnectionResetError: [WinError 10054]`. The SDK's own negative assertions
  completed. Linux passed all 193 in the same pre-fix state.
- Fix. Treat `ConnectionResetError` like `ssl.SSLError` only in the fixture's
  initial TLS handshake. Keep all post-handshake fixture failures visible.

## Active Project Guardrails

- The Python SDK consumes only the public HTTP contract. Java SDK, Sidecar,
  Framework, credentials, and operational data are outside the diff. No data
  reset, compatibility adapter, or parallel obsolete API is needed.
- Standard sockets, TLS, and one maintained HTTP/1.1 framing dependency keep
  responsibilities local. The synchronous transport has no worker or event loop.
  Shared parsers and models carry no synchronous transport state.
- Credentials stay in a per-operation Authorization header. Public status and
  wait errors preserve requested identity and observed business diagnostics.
  Optional HTTP problem fields redact token occurrences in keys and strings.
- Product docs describe the installed client, real deadline and resolver behavior,
  and ordinary verified TLS. Certificates and identities remain operator-owned.
