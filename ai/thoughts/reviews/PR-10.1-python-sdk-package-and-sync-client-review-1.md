## Findings

### [P1] Require authenticated EOF to complete close-delimited HTTPS

- Location — `sdks/python/src/loomspan_sdk/_sync_transport.py:161`
- Scenario — A peer sends a close-delimited 202 with valid-looking JSON and ends
  TCP without a TLS closure alert. The standard socket default converted this
  unexpected EOF into an ordinary read end. A verifying context can also opt
  into ignoring the unexpected EOF through an OpenSSL option.
- Impact — The SDK reported an acceptance ID from an incompletely framed HTTPS
  message. A similarly truncated 503 exposed the problem despite incomplete
  framing.
- Evidence — The real TLS loopback probe returned `AcceptedExecution` and the
  focused 503 regression showed a populated problem. HTTP/1.1 requires a TLS
  closure alert when message length depends on EOF.
  [RFC 9112 section 9.8](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.8)
- Fix — Preserve TLS EOF errors, reject contexts configured to ignore them, and
  exercise both successful framing methods and known-status preservation.

### [P2] Keep TLS socket disposal with the active request

- Location — `sdks/python/src/loomspan_sdk/_sync_transport.py:75`
- Scenario — A concurrent `close()` ran after CPython checked the TLS object
  and before it dereferenced it for a read. Closing the wrapper cleared that
  object from the active socket.
- Impact — An in-flight read could raise a raw `AttributeError` and lose the
  requested execution context.
- Evidence — A synchronized trace of the real Windows TLS read produced
  `AttributeError`. A peer-backed regression held the caller at a read boundary
  and demonstrated that the old code disposed of its live TLS descriptor.
- Fix — Shut down connected I/O from `close()` and let the request dispose of
  the wrapper in its existing cleanup. Treat local EOF as aborted framing and
  keep a fallback close for an unconnected socket.

### [P2] Accept valid additive numbers outside float range

- Location — `sdks/python/src/loomspan_sdk/_protocol.py:162`
- Scenario — A valid acceptance envelope has a new numeric field such as
  `1e999`. The prior decoder rejected the whole document when Python float
  conversion overflowed.
- Impact — A complete response with the expected ID could raise
  `AcceptanceUnknown` solely because of an additive field.
- Evidence — The focused acceptance regression failed in the float hook.
  The SDK's Java Jackson version parsed the same numeric token.
- Fix — Retain a finite `Decimal` when float overflows. Keep nonstandard
  numeric constants invalid and document the resulting diagnostic value type.

### [P3] Describe possible acceptance after native interruption

- Location — `sdks/python/README.md:68`
- Scenario — A caller catches `KeyboardInterrupt` from a submission after
  Sidecar received it. The README explained cleanup and uncertainty in SDK
  errors separately, leaving the native interruption case implicit.
- Impact — A caller can interpret native interruption as proof of nonacceptance
  and resubmit an operation that may have already been admitted.
- Evidence — The native interruption regression observes a POST and then a
  native interrupt without an acceptance ID.
- Fix — Document that Sidecar may accept the request after dispatch even when
  native interruption prevents the caller from receiving its ID.

after the changes on Windows and Linux. The re-review found no additional
