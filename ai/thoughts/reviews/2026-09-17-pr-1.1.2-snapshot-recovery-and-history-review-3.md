## Findings Resolved in This Context

### [P2] Name the actual Kubernetes deployment in the backup procedure

- Location: `README.md:165,206`
- Scenario: An operator follows the documented stop or restart command for `examples/kubernetes/deployment.yaml`.
- Impact: `deployment/loomspan-sidecar` does not exist in that sample, so the backup cannot begin or the restored installation cannot restart as documented.
- Evidence: The sample Deployment metadata names `example-with-loomspan-sidecar`.
- Fix: Use `deployment/example-with-loomspan-sidecar` in both commands.

### [P2] Give a recovery action when the store-state row is missing

- Location: `src/main/java/ai/loomspan/sidecar/storage/ConfigurationSnapshotRepository.java:135`
- Scenario: A migrated, previously initialized database loses its singleton store-state row.
- Impact: Startup fails with only a structural error, leaving the operator without the required recovery action for an unreadable selected state.
- Evidence: V1 migration always inserts the state row; `initialize()` reads it before any selection or pruning. The prior exception was only `Missing configuration store state`.
- Fix: State the stopped-instance consistent-backup restore action without including authored content or a cause chain; add a real SQLite missing-row assertion in `ConfigurationSnapshotStoreTest`.
