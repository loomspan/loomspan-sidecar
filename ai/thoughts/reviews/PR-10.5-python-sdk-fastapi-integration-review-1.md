## Findings Resolved in This Context

### [P2] Clear verified identity when downstream middleware copies the scope

- Location: `sdks/python/src/loomspan_sdk/fastapi.py:181` and `:306`.
- Scenario: Ordinary ASGI middleware shallow-copies the scope before dispatch.
  The handler receives that copied scope through its FastAPI `Request`.
- Impact: Removing the principal tuple from the original dictionary leaves
  verified identity accessible through the SDK on the copied `Request` after
  success, error or cancellation.
- Evidence: Reproduced with a real FastAPI route and a scope-copying layer.
  The public principal dependency returned the original identity after the
  callback exited. The updated concurrent regression failed on the old code.
  Scope copying is expected middleware behavior. [ASGI middleware specification](https://asgi.readthedocs.io/en/latest/specs/main.html#middleware)
- Fix: Pass an admitted copy of the scope carrying a private, per-request
  binding. Clear its principal in `finally` so shallow copies share the same
  cleanup. The handler still receives the original immutable verified value.

### [P2] Preserve business headers supplied as an iterable

- Location: `sdks/python/src/loomspan_sdk/fastapi.py:255` and `:291`.
- Scenario: The server supplies the raw header collection and pairs as
  one-shot iterables, which the ASGI HTTP scope allows.
- Impact: Inspecting Authorization consumes the collection, so callback
  handlers receive no business headers despite successful authentication.
- Evidence: Reproduced with an iterator-backed FastAPI HTTP request. The
  strengthened streaming request regression failed on the old code.
  [ASGI HTTP connection scope](https://asgi.readthedocs.io/en/latest/specs/www.html#http-connection-scope)
- Fix: Snapshot the pairs once. Authenticate from the snapshot and pass it
  downstream, retaining case, value bytes, duplicates and order. The original
  body channel and response channel pass through directly.

## Open Questions and Assumptions

The app or proxy must deliver callback requests to the guard. The supported
parent-owned mount setup installs it before parent browser middleware. With a
child-owned guard the parent enters its lifespan explicitly and forwards the
callback path. Raw path checks depend on server visibility of original bytes.
