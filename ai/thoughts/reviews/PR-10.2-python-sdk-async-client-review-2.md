## Findings Resolved in This Context

### [P2] Bound simultaneous system trust loads per client

- Location — `sdks/python/src/loomspan_sdk/_async_transport.py:173`.
- Scenario — A system trust load stays blocked after the first HTTPS call
  reaches its connect deadline or the caller cancels it. A subsequent request
  acquires the async lock and submits another trust load while the first worker
  still runs.
- Impact — One client could accumulate blocked workers without a bound. A
  sustained series of connect deadlines while an OS trust source is stalled can
  keep increasing thread usage. None of these requests reaches HTTP.
- Evidence — AnyIO's worker limiter and the client's async lock were both
  released when the awaiting call was cancelled. A gated trust factory observed
  five simultaneous worker threads after five sequential public calls timed
  out. The regression test failed with two trust loads after two timed-out
  calls before the production fix.
- Fix — Keep the async lock for normal callers and guard the physical load
  with a nonblocking worker lock that survives abandonment. A caller reaching
  the loader while an abandoned load is pending gets the existing connection
  failure category before dispatch. The verified context can still be cached
  by the original worker. The regression test holds the first load, checks that
  the second call creates no duplicate load or dispatch, and verifies a later
  explicit status read over verified TLS after the worker completes.
