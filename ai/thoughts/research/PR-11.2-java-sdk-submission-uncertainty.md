# Java SDK submission uncertainty research

## Research Question

How does the blocking Java SDK distinguish a local failure, unknown submission
acceptance, an HTTP error, an unusable read response and a terminated wait?
What source and provider-free tests establish where the distinctions break down?

## Summary

`SidecarClient.request` shares transport and bounded body handling across
submission, discovery and execution reads. The two overflow checks throw
`ProtocolException` before classifying the status or operation. The initial
interrupt check already prevents an HTTP attempt but reports
`WaitTerminatedException`. After invoking the transport, the I/O catch checks the
interrupt flag before submission uncertainty and observed HTTP error status.

## Current Behavior and Data Flow

1. `submit` validates/encodes the skill name, checks that the object input exists,
   and serializes the input before calling `request` with `submission=true`, no
   wait deadline, and null execution context. `request` validates client and
   credential state before its first interrupt check. An already interrupted
   caller exits before request creation, without clearing its flag. Scheduler
   rejection while closing also exits locally before transport invocation.
2. The request attaches one credential as `Authorization`, sets JSON response
   preference, and disables authentication handling. The HTTP client disables
   automatic retries, redirects, cookies, authentication caching and compression.
   The SDK does not consult `Location` or response headers for an execution ID.
   The server admits work before returning a `202` with both `Location` and a
   JSON `id`. The SDK returns an ID only after it parses the completed response
   and validates the JSON field as a UUID.
3. The effective request budget is the response timeout capped by the remaining
   wait budget, where applicable. A daemon scheduler checks the caller flag and
   monotonic deadline as often as every 5 ms and cancels the local request.
   There is a window between the initial flag check and `http.execute`. The
   source has no subsequent caller-side check immediately before that invocation.
4. After `http.execute` returns, the status becomes observable and is saved in
   `observedStatus`. Declared oversize fails before opening the body. For streamed
   responses the client reads at most the remaining limit plus one byte, then
   throws on overflow. Both throws bypass the `IOException | IllegalStateException`
   handler because the SDK's `ProtocolException` extends `SidecarException`.
5. A complete bounded non-2xx response yields `HttpFailureException`. The optional
   problem is a parsed JSON object. Invalid/non-object bodies yield no details.
   String values and property names are recursively redacted for the supplied
   credential before the exception stores a copy. The exception message contains
   the status only and does not retain the original cause or raw body. The byte
   limit governs source bytes read. The existing redaction replacement may change
   the size of the resulting JSON representation.
6. A bounded but unexpected 2xx, invalid JSON, invalid `id`, or I/O loss with no
   known HTTP error already produces acceptance unknown for submission, unless
   the I/O handler sees an interrupt. That handler currently chooses
   `WaitTerminatedException` first for a caller interrupt or elapsed explicit
   wait deadline, then returns an observed non-2xx status without a problem,
   then distinguishes submission from other operations. An I/O exception before
   a response is handed back does not establish that the peer saw no request.
7. The `finally` cancels the watchdog, cancels the request before closing the
   response immediately, and applies to any path inside the transport block.
   The ordering avoids draining a partially read body for reuse. Client close
   immediately closes the owned pool and shuts down the watchdog executor once.
   These actions affect local resources. The client has no server cancellation
   call or retry/recovery path.
8. Status reads carry the requested ID and `await` passes its most recent valid
   snapshot. `await` polls only successful nonterminal reads and stops on the
   first read failure. Its sleep catch explicitly reasserts the interrupt flag.
   Its loop and transport checks use `isInterrupted()`, which leaves the flag set.

## Affected Areas

| Area | Current behavior and evidence |
| --- | --- |
| Local submission failure | Input, credentials, known closed state and scheduler rejection fail locally. An already interrupted request sends nothing but has the wait exception type today. |
| Successful submission response | Both overflow branches throw the protocol exception. An invalid complete acceptance envelope already produces acceptance unknown with null context. |
| HTTP error | Complete bounded responses and ordinary post-header I/O failures retain status. Overflow bypasses that classification. A transport interrupt or expired wait currently outranks HTTP status in the I/O catch. |
| Status read and wait | Expected `200`, bounded response, requested UUID and last valid snapshot where applicable. The wait has its own pre-read and sleep termination paths. |
| Documentation | `sdks/java/README.md:58–85` describes one attempt, ignored `Location`, status context and local wait behavior. The generic overflow row does not distinguish submission, reads or known HTTP errors. |

  its active dependency. `InternalExecRuntime.cancel()` can discard the endpoint
  immediately. These are observations of the pinned transport, not public SDK
  contracts or application dependencies on internal Apache classes.

## Open Questions

- Planning needs to make outcome precedence explicit when a known non-2xx status
  is followed by interruption or a wait deadline. The ticket protects known
  HTTP status and preserves read/wait behavior. The current I/O catch prioritizes
  wait termination whenever the flag is set or the explicit wait has elapsed.
- The current tests do not combine a received POST, a blocked response and a
  caller interrupt, or distinguish reading beyond the body bound from discarding
  a connection. Those paths need fresh executable evidence in later stages.
