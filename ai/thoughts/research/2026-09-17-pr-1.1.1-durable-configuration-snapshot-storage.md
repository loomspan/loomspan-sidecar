# Durable Configuration Snapshot Storage Research

## Research Question

What configuration and storage behavior exists in Sidecar today, and which code, framework contracts, tests, and deployment assumptions bound the proposed durable complete snapshot?

## Summary

Sidecar currently has no durable configuration store, migration, JDBC repository, or snapshot identity. The framework discovers YAML skills from configured file patterns while Sidecar independently reads one REST routes YAML file, resolves placeholders, builds runtime target/route objects and HTTP clients, then checks the routes against the startup catalog (`src/main/resources/application.yml:1`, `src/main/java/ai/loomspan/sidecar/rest/RestRouteLoader.java:46`, `src/main/java/ai/loomspan/sidecar/rest/RestRouteCatalogValidator.java:21`). The current runtime route model contains resolved URIs, durations and compiled paths, so it does not preserve original authored route text (`src/main/java/ai/loomspan/sidecar/rest/RestRouteConfiguration.java:8`, `src/main/java/ai/loomspan/sidecar/rest/RestRouteLoader.java:119`). The matching framework's public `SkillDocument` supplies a diagnostic source label and YAML text for a complete replacement set; the framework owns skill validation and process-local generation IDs (`C:/opendev/code/loomspan-framework/agent-skills/loomspan-docs/references/java-api/skill-reload.md`, `C:/opendev/code/loomspan-framework/src/main/java/ai/loomspan/api/SkillDocument.java:4`).

## Current Behavior and Data Flow

1. `src/main/resources/application.yml:1` configures framework skill discovery from `/sidecar/skills/**/*.yaml` and `.yml`. `src/main/resources/application.yml:8` configures Sidecar's separate `/sidecar/rest-routes.yaml` input. `src/main/java/ai/loomspan/sidecar/config/RestRoutesProperties.java:7` supplies that route default.
2. On Spring bean construction, `RestRouteLoader` requires the route resource to be readable, parses YAML with duplicate-key detection, requires `targets` and `routes` objects, and constructs its in-memory configuration (`src/main/java/ai/loomspan/sidecar/rest/RestRouteLoader.java:46-116`). It resolves string placeholders through the Spring environment while parsing targets, routes and headers (`src/main/java/ai/loomspan/sidecar/rest/RestRouteLoader.java:119-195`, `:325`). Its target values become URI, authentication, SSL-bundle selection, durations and byte limits; route paths become compiled parts (`:119-180`). The output is an immutable-copy map of runtime records, with no original YAML field (`src/main/java/ai/loomspan/sidecar/rest/RestRouteConfiguration.java:8-32`).
3. `RestTargetClients` creates an Apache-backed `RestClient` per parsed target and closes them during handler shutdown (`src/main/java/ai/loomspan/sidecar/rest/RestTargetClients.java:23-52`, `:58-106`). `GenericRestSkillHandler` is the single fixed public `RestSkillHandler` bean. It selects its current parsed route by skill name and uses a target client to make the request (`src/main/java/ai/loomspan/sidecar/rest/GenericRestSkillHandler.java:26-56`). These clients and resolved URLs are runtime resources, not authored configuration.
4. After singleton creation, `RestRouteCatalogValidator` compares the framework's REST skill descriptors with Sidecar routes and rejects missing, unknown, non-REST or unknown-target routes (`src/main/java/ai/loomspan/sidecar/rest/RestRouteCatalogValidator.java:21-39`). Existing route-file errors stop startup, and no target is contacted merely by loading configuration (`README.md:136-149`). The current catalog and route inputs remain startup snapshots until restart (`README.md:133-134`, `:347-351`).
5. There is no `src/main/resources/db/migration` directory and `pom.xml:31-90` has neither SQLite, Flyway nor Spring JDBC dependencies. `LoomspanSidecarApplication` only registers execution, JWT and REST-route property classes (`src/main/java/ai/loomspan/sidecar/LoomspanSidecarApplication.java:9-16`). No current-configuration pointer or initialized-store marker exists.

## Dependencies and Operational Constraints

- The ticket requires one file-backed SQLite store, Flyway-owned migrations, `NamedParameterJdbcTemplate` repositories and Spring transactions. None is yet declared in `pom.xml:31-90`. The ticket permits no old development-database migration and delegates runtime activation to Phase 2.
- The matching framework `skill-reload.md` states `SkillDocument(sourceName, yaml)` labels must be nonblank and exactly unique, YAML and collection elements non-null, and empty collections valid. It states source label is diagnostic text rather than a path or callable skill name; `prepare(Collection<SkillDocument>)` validates complete YAML sets, and generation IDs are process-local. Its ordinary configured generation starts before application restore; the application owns readiness and persistence.
- Framework-authored REST skill YAML includes `rest: true` but no endpoint or credentials. The fixed handler owns those (`C:/opendev/code/loomspan-framework/agent-skills/loomspan-docs/references/skill-authoring/rest-skills.md`). Model-backed and REST YAML share one framework validation authority.
- `README.md:125-134` currently recommends environment-supplied credentials and restart after file edits. `RestRouteLoaderTest.java:73-119` demonstrates authored `${NAME}` values being resolved on load. These observations distinguish raw authored references and literal values from resolved runtime values.
- `Dockerfile:11-14` and `examples/kubernetes/deployment.yaml:78-99` show a non-root image and read-only ConfigMap mounts. Database durability depends on a writable persistent directory; the existing examples do not provide one.
