# Python SDK signing and issuance research

## Research question

What Java issuance, private-key loading, and verification behavior must Python
match? Which existing fixtures and library primitives establish feasible
nanosecond NumericDate and PKCS#8 handling?

## Summary

The Python SDK already carries opaque execution credentials across both clients.
Java owns the profile baseline, with exact fractional JSON numbers in its
issuer and double-based parsing in both current Java receivers. Synthetic
Python signatures and public-key extraction interoperate with the current Java
receivers and public JWK fixture. The stock cryptography outer-key loader alone
does not accept the valid RFC 5958 embedded-public-key fixtures. Typed ASN.1
schemas and the cryptography RSA loader handle the tested forms together.

## Current behavior and data flow

### Python client boundary and phase ownership

`sdks/python/src/loomspan_sdk/_credential.py:4` accepts an existing nonempty
visible-ASCII token. It redacts repr, refuses state serialization, and provides
the private authorization and replacement methods used by transport and error
redaction. Public imports are maintained in `sdks/python/src/loomspan_sdk/__init__.py`.
`_http.py:76` sets the bearer header per request from the explicit credential
passed to the sync or async client. There is no issuer, private-key loading, or
implicit login context in Python today. The package metadata requires Python

credentials from the calling application.

PR 10.3 consumes the PR 10.1 credential shape. PR 10.4 owns the reverse
Java-to-Python direction and callback trust and verification. PR 10.5 owns
FastAPI lifespan, middleware and trusted dependency integration. PR 10.6 owns
maintained-suite adoption, composed proof and aggregate platform evidence.

### Java identity and issuance

- `sdks/java/core/src/main/java/ai/loomspan/sdk/AuthenticatedIdentity.java:7`
  and `IssuanceSettings.java:8` validate nonblank values using Java
  `String.isBlank()` and copy collections. Capture contains only subject and
  authorities. `SpringExecutionTokenIssuer` adapts authenticated application
  context to core issuance without passing a login token or its expiry.
- `ExecutionTokenIssuer.java:18` checks lifetime representability at
  construction and warns once per issuer above one hour. It checks expiry again
  when issuing. The default is `loomspan-app`, 15 minutes and empty role and
  audience configuration. One clock read supplies both dates. The allowed
  timestamp range is Java `Instant`, with epoch seconds from
  `-31557014167219200` through `31556889864403199` and a nanosecond component.
- `ExecutionTokenIssuer.java:24` builds audiences in first-seen order,
  beginning with `loomspan-sidecar` and the issuer. It filters identity
  authorities against the exact allowlist, deduplicating in identity order.
  The JWT header carries RS256, `loomspan-execution+jwt` and the public-key
  thumbprint. Claims include the configured issuer, captured subject, audience
  array, dates, unique UUID JTI, `loomspan_execution` token use and a roles array.
  No state tracks a current user. Signed output is an opaque `CredentialSnapshot`.
- `ExecutionTokenIssuer.java:45` uses `Instant.plus(Duration)` and exact
  `BigDecimal` epoch seconds with scale nine. The wire is a JSON number. The
  existing `ExecutionTokenIssuerTest.positiveDurationsKeepPrecisionAndWarnOnlyAboveOneHour`
  checks raw payload text for a one-nanosecond duration, fractional seconds,
  one hour, longer durations and overflow.

### Java receiver timestamp behavior

`src/main/java/ai/loomspan/sidecar/security/ExecutionJwtDecoder.java:25` and
`sdks/java/spring-boot-starter/src/main/java/ai/loomspan/sdk/spring/CallbackJwtDecoder.java:26`
read raw claims with Nimbus `JSONObjectUtils`, check shapes, floor whole
seconds and convert the remaining fraction into nanos before building Spring's
`Jwt`. Expiration is required and `iat` and `nbf` are optional. The callback
decoder validates an exact configured issuer and receiver audience. The Sidecar
decoder uses the issuer as signed ownership and checks its receiver audience.
Both validate RS256, the signing key and token purpose and use 60-second
timestamp skew. Spring's token constructor requires expiration strictly after
issuance when both are present. [Spring Security 7.1.0 source](https://github.com/spring-projects/spring-security/blob/7.1.0/oauth2/oauth2-core/src/main/java/org/springframework/security/oauth2/core/AbstractOAuth2Token.java#L56).

The Maven test classpaths for both receivers resolve Nimbus 10.9. Its raw
JSON parsing returns a `Double` for decimal literals. Precision can be lost
before either decoder constructs a `BigDecimal`. A scratch probe used the
repository synthetic private key with Python cryptography 48.0.0 to sign
otherwise identical RS256 tokens containing the exact expiration literals
below. Both compiled production Java decoders used the same fixed clock and
an integer `iat` of `1792324800`. The Sidecar decoder read the fixture JWKS
through `CurrentFileJwtTrust`. The callback decoder used
`SigningKeys.initialize` with the same key through `CallbackJwtTrust`.

| Exact JSON expiration | Result in both Java receivers |
| --- | --- |
| `1792324800.000000001` | Rejected. Nimbus rounds to `iat`, and Spring rejects equal instants. |
| `1792324800.123456789` | Accepted at second `1792324800`, nano `123456700`. |
| `1792324800.999999999` | Accepted at second `1792324801`, nano zero. |
| `1792324800.125` | Accepted at second `1792324800`, nano `125000000`. |
| `31556889864403199` | Accepted at that second, nano zero. |
| `31556889864403199.000000000` and `31556889864403199.999999999` | Rejected after the decimal path rounds beyond the Java Instant range. |
| `31556889864403200` | Rejected as outside the Java Instant range. |

This is a difference between Java's own exact issuance and receiver behavior.
The Python research probe signed the wire literally to isolate receiver
behavior. It did not exercise a shipped Python issuer. Acceptance of practical
fractional credentials is established independently of preserving the original
nanoseconds in a Java receiver's resulting `Instant`.

### Java signing material and public trust

- `sdks/java/core/src/main/java/ai/loomspan/sdk/SigningSettings.java` requires
  one mode and the corresponding paths. `SigningKeys.java:31` creates
  ephemeral 2048-bit RSA in an existing colocated directory and exports
  `jwks.json`. Provided mode loads the configured input once at startup and
  publishes to the explicit output. It rejects overlap by normalized path and
  by existing-file identity using the original paths. Private input is never
  used as the export destination.
- `SigningKeys.java:84` consumes the entire PEM and requires a newline before
  the end boundary and complete Base64 quanta. Its body permits ASCII space,
  tab, CR and LF. Surrounding whitespace additionally permits form feed and
  vertical tab. The anchored labels exclude encrypted and traditional
  `RSA PRIVATE KEY` PEM, certificates and additional blocks. Bouncy Castle
  consumes the whole outer ASN.1 object, validates the attribute structure and
  disallows non-null rsaEncryption parameters. The RSA KeyFactory loads
  the PKCS#8. If the optional public field is present, Java parses it and
  compares its modulus and exponent to the loaded key.
- `SigningKeys.java:51` checks strength and signs and verifies a fixed
  challenge. Nimbus exports an RFC 7638 thumbprint as `kid`; the JWK members
  are exactly `kty`, `n`, `e`, `alg`, `use` and `kid`. The scratch Python
  probe matched `public-jwks.json` as a JSON object using the synthetic key's
  public numbers, minimal unsigned big-endian encoding, Base64url and the
  SHA-256 hash of the ordered canonical JWK thumbprint members. This probe
  did not use any operator input. [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638).
- `SigningKeys.java:133` creates a temporary file in the target directory,
  writes the complete public set and uses one atomic replacement move. Errors
  abort initialization and clean up temporary output. It never creates
  directories or changes permissions. `JwtSecurityConfiguration.java:36`
  wires the current file trust into Sidecar's receiver. Sidecar consumes the
  public JWK only. The private key and TLS/mTLS configuration remain independent.

## Dependencies and operational constraints

### Private-key parsing probes

Windows CPython 3.13.13 with cryptography 48.0.0 directly loaded the fixed
fixture, valid v1 attribute fixture and absent RSA algorithm parameters. It
rejected the matching RFC 5958 v2 public field as well as the mismatched
public field. The API is a generic DER loader and type checks remain the
caller's responsibility. [cryptography serialization API](https://cryptography.io/en/48.0.0/hazmat/primitives/asymmetric/serialization/).

A scratch test used `pyasn1` 0.6.5 with the shipped
`pyasn1-modules` 0.4.2 `rfc5958.OneAsymmetricKey` and `rfc8017` RSA
private/public schemas. It consumed each relevant structure fully, checked
version and algorithm, examined attributes and public-key alignment, and
used cryptography's validated RSA loader for the parsed inner key. The
embedded public component was compared using the loaded public key. This
combination reproduced the Java fixture accepts and rejects for supported
optional fields, missing and non-null algorithm parameters, duplicate
attributes, unknown outer fields, malformed or mismatched public key,
incorrect inner shape, and trailing inner or outer bytes. Both Java and the
probe allowed v2 without an embedded public component and rejected a v1 key
with an embedded public component. The RSA loader, ASN.1 codec and schemas
are library primitives. [pyasn1](https://pypi.org/project/pyasn1/0.6.5/),
[pyasn1-modules](https://pypi.org/project/pyasn1-modules/0.4.2/).

Complete BER variants matter even though normal operators use DER PEM. Java's
loader accepted indefinite-length outer, RSA inner and embedded RSA public
sequences, independently wrapped around the synthetic key. The same
schema-based probe accepted all three with the BER decoder and passed
library-serialized inner RSA DER to cryptography. The plain DER decoder or
outer byte-for-byte DER round trip would reject the BER outer sequence.
RFC 5958 permits BER and identifies DER as the usual output format.
[RFC 5958 §2](https://www.rfc-editor.org/rfc/rfc5958.html#section-2).

### Time and JSON representation

Integer nanosecond clock reads and arithmetic can represent Java's entire
timestamp range without a Python `datetime` boundary. Python's `timedelta`
has microsecond resolution, and epoch floats cannot retain adjacent
nanoseconds at today's dates. A public lifetime parameter using only those
types would lose the Java one-nanosecond case. Integer nanosecond units or
exact decimal seconds can express it. A Decimal-aware JSON encoder preserves
the numeric wire representation without converting values into strings.
`simplejson` 4.2.0 emitted distinct unquoted `1792324800.000000001` and
`1792324800.000000002` in isolated probes on Windows and Linux. PyJWT's
high-level encoder uses an optional JSON encoder and its datetime convenience
path is second-resolution. The documented inputs do not by themselves
establish exact Decimal serialization. [Python time.time_ns](https://docs.python.org/3/library/time.html#time.time_ns),
[Python timedelta](https://docs.python.org/3/library/datetime.html#datetime.timedelta),
[simplejson](https://simplejson.readthedocs.io/en/latest/),
[PyJWT API](https://pyjwt.readthedocs.io/en/stable/api.html).

## Historical context

The shared PEM design superseded Java keystores, signing passwords and
certificate configuration. Current Java PEM, acceptance-uncertainty and
callback-trust behavior came from separate completed Java changes. Current
source and the local tests above establish this ticket's baseline. No
development-data reset or operator-key change is in scope.

## Open questions

- Exact lifetime API units and the JSON serialization dependency are planning
  choices. No observed issuer parity requires writing a general-purpose JSON or
  ASN.1 parser or lowering precision. The reader's existing rounding is
  observable even for Java-issued tokens. Guaranteeing that every
  Java-representable issuance is accepted and decoded at full precision by
  both Java receivers would require separate Java parsing changes. This ticket
  asks for receiver acceptance evidence and exact issuance. The fixture
  results above delimit what the current receivers can demonstrate.
- The permanent interop test invocation and fixture handoff are planning
  choices. Tests can reach the actual package-local Sidecar decoder and the
  Java SDK's callback decoder through their existing test modules without
  framework internals or provider calls. The scratch probes are research
  evidence only.
