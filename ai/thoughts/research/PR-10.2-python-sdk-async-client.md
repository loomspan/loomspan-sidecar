# PR 10.2 Async Python SDK Research

## Research Question

Which existing Python and Java behaviors define async parity, and what evidence
do public async networking facilities provide for the required deadlines,
single-attempt requests, strict TLS, cancellation and resource ownership?

## Summary

PR 10.1 supplies reusable Python protocol parsing, models, opaque credentials
and failure classification. The blocking client and transport still own settings
validation, request orchestration, HTTP/1.1 framing, deadlines and lifecycle.
Loopback probing on Windows distinguished strict TLS closure behavior in AnyIO
4.16.0 from CPython's standard asyncio streams. AnyIO's byte streams also released
stalled TCP and TLS connections under both native cancellation and scoped timeouts.

## Current Behavior and Data Flow

1. The blocking client validates the parsed HTTP(S) origin, positive finite
   timeouts and bounded positive integer response limit. HTTPS uses a standard
   verified client context, including hostname checks and unexpected EOF detection.
   A private CA and client identity can be supplied by context. The TCP hostname
   for a scoped IPv6 literal keeps the scope, and TLS verification strips it.
2. Discovery and execution routes are built from a configured origin, encoded
   skill segment and UUID. Submission validates and encodes a JSON object before
   dispatch. Status never uses a response Location. The request uses explicit
   per-call bearer bytes and Accept, with Content-Type and Content-Length only
   for POST. There is no shared mutable authentication state.
3. The blocking transport creates one connection and one h11 client per HTTP
   attempt. Its absolute response deadline begins before resolution and is
   narrowed by the wait deadline. The connect budget includes DNS, TCP and TLS.
   The synchronous system resolver can run past the deadline, but the next
   deadline check prevents dispatch. A final response header records status before
   body reads. An advertised oversize body is rejected early, and streaming
   accounting independently bounds actual bytes. Incomplete framing never yields
   usable body bytes. A length- or chunk-framed TLS body can complete by framing.
   A close-delimited TLS body needs an authenticated TLS closure alert.
4. The protocol decoder takes an observed status and optional complete body.
   A usable 202 acceptance supplies the only ID. Possible-dispatch failures with
   absent status, unexpected success status or unusable 2xx body yield
   `AcceptanceUnknown`. An observed non-2xx yields `HttpFailure` even when
   the body cannot be used. Only a complete bounded JSON object can become problem
   details, with credential occurrences redacted. Reads require HTTP 200 and
   a valid envelope. Result text, original timestamps and optional diagnostics
   survive parsing. A valid FAILED snapshot is a normal terminal result.
5. The wait loop reads immediately, stops on the first failure, and only sleeps
   after successful nonterminal status. Every read sees the remaining wait budget.
   SDK status and wait failures retain the requested ID and the last valid
   snapshot when one exists. The Python decoder prioritizes a recorded non-2xx
   status over the fallback wait-deadline check. Java also preserves observed
   status for ordinary oversized and unusable bodies, while its I/O catch
   specifically maps an expired wait to wait termination.
6. Sync close marks the client closed and unblocks tracked active sockets. Per-call
   cleanup closes owned resources. A local shutdown cannot complete a pending
   close-delimited body. `KeyboardInterrupt` bypasses ordinary error mapping and
   propagates after cleanup. Neither a local wait nor close sends remote
   cancellation. The ticket applies the same separation to async cancellation.

## Dependencies and Operational Constraints

### Public transport facilities and observed behavior

| Facility | Source evidence and implications |
| --- | --- |
| CPython asyncio streams | `asyncio.timeout()` scopes a timeout to the current task. Its owner converts cancellation to `TimeoutError` when the scope exits. Public asyncio transports offer immediate abort. CPython's TLS protocol can process transport EOF without requiring unwrap after underlying EOF. The probe below observed no public distinction between abrupt and authenticated closure. [Python timeouts](https://docs.python.org/3/library/asyncio-task.html#timeouts), [CPython 3.12 TLS protocol](https://github.com/python/cpython/blob/v3.12.12/Lib/asyncio/sslproto.py#L420-L447), [TLS shutdown](https://github.com/python/cpython/blob/v3.12.12/Lib/asyncio/sslproto.py#L595-L615) |
| HTTPX 0.28.1 and httpcore 1.0.9 | AsyncClient extracts cookies after every response, even without a redirect. The default asyncio network backend in httpcore deliberately wraps TLS in non-strict mode, which can surface missing closure alerts as EOF. Raw response iteration and disabled redirects do not change those two behaviors. [HTTPX AsyncClient source](https://github.com/encode/httpx/blob/0.28.1/httpx/_client.py#L1598-L1618), [httpcore network backend](https://github.com/encode/httpcore/blob/1.0.9/httpcore/_backends/anyio.py#L51-L76) |
| aiohttp 3.13.3 | ClientSession provides a cookie-jar argument and auto-decompression flag. This version enables a private retry flag used for idempotent requests, including discovery and status GETs. The constructor does not expose this flag. [aiohttp ClientSession source](https://github.com/aio-libs/aiohttp/blob/v3.13.3/aiohttp/client.py#L259-L296), [retry selection](https://github.com/aio-libs/aiohttp/blob/v3.13.3/aiohttp/client.py#L584-L590) |
| AnyIO 4.16.0 byte streams | Public `connect_tcp` can use a supplied verified context and strict TLS. It may race address candidates before any HTTP request. `TLSStream` exposes the wrapped stream and ALPN; it surfaces ragged EOF as a broken resource and authenticated close as end of stream. Immediate raw stream close avoids waiting on a peer TLS shutdown or pending writes. The library is byte-oriented and adds no HTTP policy. [AnyIO API reference](https://anyio.readthedocs.io/en/stable/api.html), [TLS stream source](https://github.com/agronholm/anyio/blob/4.16.0/src/anyio/streams/tls.py#L76-L117), [asyncio byte stream close](https://github.com/agronholm/anyio/blob/4.16.0/src/anyio/_backends/_asyncio.py#L1364-L1373) |

AnyIO 4.16.0 fixes a connected socket leak when cancellation arrives just before
the connection task group exits, and fixes a cancelled TCP receive leaving
underlying reads enabled. The connect cleanup is absent from the 4.15.1 source.
The 4.16.0 distribution is a universal Python wheel whose metadata declares
Python >=3.10 and lists 3.12–3.15. This is upstream compatibility evidence.
An SDK range still needs local implementation and installation verification.

On asyncio, AnyIO delegates DNS resolution to the event loop. CPython uses its
executor for the system lookup. Cancellation can end the caller's await without
stopping an OS lookup already running. Such a lookup holds no SDK HTTP connection
and cannot proceed to dispatch once the connect await is cancelled. For default trust
loading, AnyIO's TLS wrapper calls
`ssl.create_default_context()` synchronously when no context is supplied. With
an ordinary already-created standard context, its MemoryBIO TLS setup and
handshake use async transport operations. [AnyIO DNS backend](https://github.com/agronholm/anyio/blob/4.16.0/src/anyio/_backends/_asyncio.py#L2777-L2798),
[CPython DNS API](https://docs.python.org/3/library/asyncio-eventloop.html#asyncio.loop.getaddrinfo),
[AnyIO TLS context creation](https://github.com/agronholm/anyio/blob/4.16.0/src/anyio/streams/tls.py#L120-L168)

### Loopback probe

Used an isolated uv environment with AnyIO 4.16.0 and trustme 1.2.1 on Windows
x86-64 CPython 3.13.13. A temporary script outside the checkout used the existing
`WirePeer` fixture and a generated localhost trust chain. The script was removed
after the probe. Only loopback service traffic occurred.

| Probe | Observed outcome |
| --- | --- |
| Verified TLS, close-delimited response, peer closes TCP without a TLS alert | AnyIO strict stream reported `BrokenResourceError`. Asyncio stream reported ordinary EOF. |
| Same response with TLS closure alert | AnyIO reported `EndOfStream`. Asyncio reported ordinary EOF. |
| TCP and verified TLS, stalled response body after an HTTP request | Calling `Task.cancel("caller cancellation")` preserved `CancelledError` with the original message through AnyIO scoped deadline and forceful raw stream cleanup. A shorter outer `asyncio.timeout` produced its native `TimeoutError`. A shorter AnyIO `fail_after` produced its own `TimeoutError`. All six scenarios saw peer-observed closure and exactly one HTTP request. |

The probe covers transport facilities. SDK deadline classification, close races,
credential isolation and a packaged async example remain implementation checks.
The checkout can exercise Windows CPython 3.13.13 with uv and Linux
x86-64 CPython 3.12.16 via WSL. The WSL uv binary used in PR 10.1 remains
available at `/tmp/tmp.BAtdz0ltv1/uv`. Other required release matrix cells
remain separate from this probe.

## Historical Context

The PR 10.1 clean review records Windows and Linux verification of the installed
blocking client and the authenticated EOF rule. The agreed design in
`ai/thoughts/phases/python-sdk-design-notes.md:315` distinguishes native Python
cancellation from Java thread interruption and limits context guarantees to SDK
errors. Its packaging section keeps web dependencies outside core and separates
focused ticket checks from final combined coverage. PR 10.2 scopes this work to
local implementation and verification.

## Open Questions

- Planning owns the shared settings and framing boundary, the async owner for
  pending connection and polling lifecycles, and where default trust initialization
  happens outside request-loop synchronous I/O.
- Async implementation evidence must distinguish budget expiry, SDK close and
  external cancellation when they overlap, including close-delimited responses
  and cancellation while a TCP/TLS connection is still being established.
- Whether a dependency range has distinct minimum and current cells depends on
  versions available at verification. The observed Windows probe alone does not
  establish the Linux, macOS or final phase support matrix.
