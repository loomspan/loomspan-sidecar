# Java SDK Callback Trust Startup Research

## Research Question

How does the SDK construct and refresh callback trust, how does the servlet application consume it, and which executable evidence covers the SDK and Sidecar trust boundaries and the final Java SDK series?

## Summary

The servlet starter creates `CallbackJwtTrust` as a bean dependency of its independent security filter chain. The constructor uses the same reload path as polling, so an unreadable or invalid configured file currently leaves the application with an empty snapshot and starts a one-second poller. Runtime reload already fails closed and recovers without restarting, but it discards all diagnostic information. Sidecar has a distinct loader and intentionally starts in a waiting state while its colocated signer creates the first export.

## Current Behavior and Data Flow

### Startup and resource ownership

1. The SDK starter registers `SidecarClientAutoConfiguration`, `ExecutionTokenAutoConfiguration`, and `CallbackSecurityAutoConfiguration` through `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`. The callback configuration is servlet-only and ordered after token auto-configuration. Outbound-only non-web consumers therefore do not instantiate callback trust.
2. `ExecutionTokenAutoConfiguration.signingKeySource` resolves signing configuration and calls `SigningKeys.initialize`. `SigningKeys` generates an ephemeral RSA key for colocated mode or reads provided PEM, proves the signer and atomically exports its public JWKS before returning. The callback trust bean takes that already initialized source. A failure during callback-trust bean creation occurs after the signer can have written the public export. The signer itself owns no poller or closeable resource.
3. `CallbackProperties.overlapPath()` returns `null` when the property is absent. Explicit blank or invalid path syntax already throws an `IllegalArgumentException` naming the property without echoing its value. With no configured overlap, `CallbackJwtTrust.reload()` initializes a snapshot from the signer's key. That constructor path allocates no executor and performs no overlap-file read.
4. With a configured path, the same constructor synchronously calls `reload()`. Read failure yields empty trust and validation failure does the same. The constructor then allocates the daemon executor named `loomspan-sdk-callback-trust` and schedules fixed-delay reload with initial delay and interval both one second. The Spring bean's destroy method is `close`; `close()` marks the instance closed under synchronization, interrupts scheduled tasks, and further reloads return without reading. The starter does not declare a dedicated eager-initialization override.

### Reload, snapshots and request boundary

- `CallbackJwtTrust.reload()` is synchronized across polling and request-triggered reloads. It compares bytes and read availability to the last result and skips publication and validation when both are unchanged. Valid candidates must be complete UTF-8 JWKS objects with a nonempty list of public RSA keys. Existing rules cover RSA parameters, required nonblank unique `kid`, optional `use=sig` and `alg=RS256`, and reject private members. The merge preserves the own key, accepts an identical own-key duplicate, and rejects an own-`kid` conflict. Unavailable or invalid content replaces the entire snapshot with an empty map. The immutable map is published in one write to a volatile snapshot. The last file bytes are cloned for comparison.
- `forKid` returns its current snapshot immediately for absent configuration, a blank/null `kid`, or a known key. A miss rechecks under the reload monitor, then permits a globally throttled immediate reload at most once per second using a monotonic ticker. Polling has its own fixed delay and is independent of the miss timestamp. Consequently an invalid configured runtime file removes own-key acceptance after detection, and valid restored bytes can be loaded by either trigger. No last-valid key store exists.
- `CallbackJwtDecoder.decode` validates the raw profile and uses one current trust snapshot to resolve and verify the request's signature. It catches exceptions and creates `BadJwtException("Invalid callback execution credential")` without chaining the original cause. The filter chain converts failure to HTTP 401 with `WWW-Authenticate: Bearer`. A successful request carries verified identity and exact roles through the callback chain. The trust class has no reference to controller work or any cancellation hook, so refresh changes future key resolution and cannot cancel work already admitted by the chain. This last conclusion follows from source, without a baseline in-flight callback regression.
- Neither the unavailable branch nor the invalid branch currently logs. `previousUnavailable` differentiates read failure from bytes for caching, and `Snapshot` exposes keys only. The SDK README describes immediate load, polling, and withdrawal in one paragraph and does not distinguish initial failure from post-start failure. The trusted-group remote recipe already describes atomically replacing operator-owned public trust files.

### Independent Sidecar trust

`JwtSecurityConfiguration` wires `CurrentFileJwtTrust` to Sidecar's own execution decoder and readiness indicator. `SidecarTrustProperties.resolve` validates trust configuration and listener boundaries. For a valid configuration with missing/unusable file content, `CurrentFileJwtTrust` publishes an empty `waiting` state and starts polling. The readiness indicator reports down until trusted keys are present. This provides the colocated startup order in which Sidecar can be running while the application first exports its public JWKS. The loader has its own snapshot, scheduler, miss limit, and logging. The SDK Maven reactor cannot depend on Sidecar or Framework, and no callback trust implementation path calls the Sidecar loader.
