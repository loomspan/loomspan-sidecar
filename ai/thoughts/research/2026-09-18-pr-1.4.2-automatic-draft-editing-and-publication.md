# Automatic Draft Editing and Publication Research

## Research Question

What browser, management API, draft, lease, validation and publication behavior exists for PR 1.4.2, and where are its executable and operational boundaries?

## Summary

The embedded browser console currently supports login, account administration and read-only inspection of the runtime configuration. Its JavaScript reports deliberate activity and renders authored configuration as text, but it has no editing screen, draft save/validation scheduler or publish action (`ManagementPagesController.java:91-112`, `:142-153`; `console.js:1-65`, `:65-89`, `:138-163`). Phase 3 already supplies session-private drafts, one instance-wide editing lease tied to a tab UUID and grant, candidate revisions, complete-draft validation and explicit publication APIs (`ManagementEditingController.java:23-105`; `ManagementConfigurationController.java:20-51`).

The server distinguishes a successful runtime switch from failures before and after activation and exposes runtime, intended and fault fields (`RuntimeConfigurationService.java:153-259`). Current HTTP tests exercise many API lifecycle and concurrency paths, but there is no repository browser workflow test or editor UI yet.

## Current Behavior and Data Flow

1. **Browser entry and identity.** `/management/home` and `/management/configuration/current` render server-supplied HTML and load `/management/assets/console.js`; navigation has no authoring link (`ManagementPagesController.java:91-112`, `:142-153`). JS obtains the session role and CSRF token from `GET /api/management/session`, uses same-origin credentials and `X-CSRF-TOKEN` on writes, redirects on 401 and clears protected content on 403 (`console.js:18-50`, `:138-163`; `ManagementController.java:51-64`). Current snapshot content is placed in DOM text nodes, including complete skill YAML and REST YAML (`console.js:7-11`, `:65-83`).
2. **Activity and security.** The browser listens for click, keydown, input, paste and scroll, then calls `/session/activity` at most once per 30 seconds; it does not listen for mousemove (`console.js:51-58`). The server's activity report extends the login deadline only once per 30 seconds; passive requests do not do so (`ManagementSessionGuard.java:25-70`). The same session guard invalidates expired or changed-account sessions (`:25-38`). Management paths have a separate Spring Security chain: authenticated reads, editor draft/publish writes, admin-only takeover, CSRF and form login (`ManagementSecurityConfiguration.java:48-85`). Session destruction clears its draft and lease (`ManagementEditingSessionListener.java:7-16`); account changes clear affected drafts (`ManagementIdentityService.java:145-169`). Defaults are 30-minute login idle and 15-minute edit lease (`SidecarManagementProperties.java:7-22`; `application.yml:13-17`).
3. **Draft and ownership.** One in-memory `ManagementEditingState` holds drafts by server session ID and one global lease with session ID, tab ID, grant ID and expiry (`ManagementEditingState.java:11-53`). `GET /editing` reveals only held/mine/expiry; `GET /editing/draft` reads only the caller session's draft (`ManagementEditingService.java:47-69`). Acquiring requires an unheld lease, creates a private draft from the runtime-published snapshot when none is eligible, or resumes the same session's draft; takeover requires admin and starts that admin from runtime production (`:71-89`). Another tab in the same session cannot acquire while held. Release retains the draft, discard clears that session's state, and expiration removes the lease but leaves an eligible draft (`:121-146`, `:229-249`). A changed runtime base removes an old draft (`:233-240`). Status currently has no account label or tab identifier (`:27`, `:47-57`).
4. **Save and validate.** `PUT /editing/draft` accepts a complete list of `SkillDocument(sourceName,yaml)` and one `restRoutesYaml`; it validates envelope shape, checks tab/grant/candidate/base and replaces the entire authored configuration (`ManagementEditingController.java:25-29`, `:79-88`; `ManagementEditingService.java:105-119`). Every save rotates the candidate UUID and clears attached validation, even for equal content (`ConfigurationDraft.java:31-35`; `ManagementEditingService.java:113-117`). Validation captures an immutable candidate, calls framework `SkillReloader.validate` plus REST resource and route checks, and attaches results only if the same entry, candidate ID, frozen object, session and grant still hold (`ManagementEditingService.java:148-165`; `RuntimeConfigurationService.java:125-151`). Results retain error/warning severity, source label and optional skill/location (`ConfigurationValidationIssue.java:3-20`). A warning alone leaves `successful=true` (`RuntimeConfigurationService.java:149-150`). Validation does not submit or activate configuration.
5. **Publish.** `POST /configuration/publish` carries tab, grant and expected candidate ID (`ManagementConfigurationController.java:47-51`). After obtaining the publication lock, server admission rechecks live session activity, account/role, tab/grant, runtime base and exact candidate's successful validation (`ManagementEditingService.java:168-197`; `RuntimeConfigurationService.java:153-161`). The accepted frozen candidate then proceeds independently through preparation, REST staging, durable submission and framework publication. Successful framework activation switches the runtime snapshot and clears all old-base drafts/leases under the transition gate (`RuntimeConfigurationService.java:163-197`). Failure before activation keeps runtime on the predecessor and tries to revert the intended pointer; activation success followed by status/pruning failure retains the new runtime and exposes a mutation fault (`:198-235`). `current()` exposes published content separately from intended ID/status and fault (`:244-259`). Publication errors expose codes and runtime/intended IDs (`ManagementConfigurationController.java:53-76`). There is no cancel API.
6. **Authored configuration.** `ManagedConfiguration` retains exact skill YAML documents and REST YAML, requiring unique nonblank skill source labels (`ManagedConfiguration.java:10-28`). REST YAML root has `targets` and `routes`; target fields include base URL, auth, SSL bundle, timeouts and response cap, while routes include target, method and path (`RestRouteLoader.java:28-40`, `:60-112`, `:115-158`). Base URL placeholders are handled by the loader, while stored content stays authored (`RestRouteLoader.java:161-165`; `README.md:498-504`). The browser currently displays these values as text but supplies no editing controls.
