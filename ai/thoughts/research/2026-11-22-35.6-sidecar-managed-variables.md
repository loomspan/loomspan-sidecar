# Managed Sidecar installation variables research

## Research Question

Trace authored documents and encrypted values through management editing, validation,
publication, rollback, restoration, export and HTTP execution. Identify the public
Framework contract, safe verification lanes and affected consumer fixtures.

## Summary

The service uses Framework's explicit-map preparation overload, but builds that
map from legacy provider fields before validating the authored documents. It also
generates and persists a second execution YAML with encrypted HTTP records. The
application already has separate transactional draft and per-publication encrypted
records, a revision-bound validation proof, and Framework generation ownership.
Rollback currently loads historical records alongside the historical documents.

## Current Behavior and Data Flow

### Authoring, read and export

- `src/main/java/ai/loomspan/sidecar/management/ManagementEditingController.java:73`
  accepts a whole candidate. `content` at line 114 invokes
  `EffectiveExecutionConfiguration.assertNoDirectAuthoredCredentials` before
  saving. That scanner rejects many literal fields, even in structurally invalid
  drafts. The builder repeats the restriction and requires explicit managed
  Gemini JSON references at `EffectiveExecutionConfiguration.java:147`. Under
  Framework 35.4 the provider parser recognizes ordinary credential fields and
  rejects the old keys. Framework permits Vertex default credentials when JSON
  is omitted, so Sidecar's managed installation boundary and Framework's provider
  shape rules are distinct.
- `ManagementEditingService.java:116–215` gates candidate and write-only value
  edits under the same lease/base/revision checks. Value replacement and removal
  increment the revision and clear proof. The service and `storage/EncryptedCredential.java:18`
  restrict names to an ASCII identifier pattern capped at 200 characters. The
  controller request uses a JSON string, so `/` in a name does not affect routing.
  `ProviderCredentialCipher.java:23–75` keeps the AES-GCM key in process config
  and binds ciphertext to the full identifier and version via authenticated data.
  SQLite stores identifiers as `TEXT` with no case-insensitive collation in
  `db/migration/V1__configuration_snapshots.sql` and `V3__management_drafts.sql`.
- `storage/ConfigurationDraftStore.java:25–69` reads original YAML and creates a
  draft from a publication including its encrypted records. The requirement table
  currently mixes saved identifiers and identifiers from imported configuration.
  Ordinary YAML save preserves records, but source-based configuration-only load
  can remove encrypted records absent from source metadata (`:81–115`). Retained
  loads replace the draft records and set `retained_source`. A revised authored
  inventory and the installation's stored inventory can therefore differ.
- `ManagementEditingService.java:375–388` returns original configuration and
  configured names, while `/configuration/current` and `/configuration/history/{id}`
  go through `ManagementConfigurationController.java:51–121`. Bundle format 4
  writes authored execution YAML into `execution.json`, original skill YAML in
  individual entries, and optional encrypted records in `credentials.json`
  (`bundle/ConfigurationBundleV4.java:68–95`). Read checks the inventory and
  runs the same literal restriction at lines 210–239. `captureExport` holds the
  publication gate and checks authorization both before and after capture.
  The editor at `ManagementPagesController.java:305–338` and
  `src/main/resources/static/management/assets/editor.js:39–42,213–281` generates
  old reference keys and trims managed names. The existing statement that values
  are hidden refers to supplied encrypted records, while accepting literals
  expands what ordinary authored reads and configuration-only bundles contain.

### Validation, preparation and diagnostics

- `RuntimeConfigurationService.java:225–261` assembles a candidate before calling
  `SkillReloader.validate`. `ManagementEditingService.java:219–239` also reads
  `drafts.credentialVersions` before entering the service validation method.
  `EffectiveExecutionConfiguration.java:48–87` decrypts every stored value,
  checks the authored requirement inventory, inspects only three legacy provider
  key families, and injects HTTP ciphertext through the 35.5-removed helper.
  `RuntimeConfigurationService.java:438–451` already calls
  `prepare("default", unchangedSkillDocuments, execution, values)` using the
  result, but the execution text can be generated and the map ignores skill config.
- Framework's public `SkillReloader.java:10–29` separates authored validation and
  detached preparation. The explicit overload copies an exact-name map with zero
  Environment fallback. The Framework reference `agent-skills/loomspan-docs/references/java-api/skill-reload.md:86–105`
  documents literal and whole-node authored forms, boundaries and rejected unused
  entries. Internal source is evidence only. `SkillGenerationManager.java:161–190`
  stages structure, checks skills, substitutes, then checks resolved settings and
  creates clients. `PreparedCandidateVariables.java:21–92` collects discovery
  across execution and skill docs and dispatches explicit lookup by exact name.
  No public API exposes the occurrence inventory.
- Framework's raw YAML node selection is at
  `internal/serialization/AuthoredYamlVariables.java:129–153,186–208,304–349`
  in the sibling checkout. It descends from each connection value, namespace
  executor value and `config` mapping of a document declaring `executor`. It
  visits key nodes, value nodes and sequences. Marker recognition requires a
  one-entry map and a `$var` scalar tagged as a string. The name is also a string
  scalar, checked with `Character.isWhitespace` or `Character.isSpaceChar` at
  the ends. Its whitespace definition is broader than Java `String.isBlank`.
  Locations encode ordinary field names, indexed sequences, and `{key#N}` or
  `{value#N}` for complex keys. Generic Jackson YAML map binding is not equivalent
  to an authored node walk for complex keys. Framework uses SnakeYAML Engine
  CoreSchema (`internal/serialization/YamlValues.java:40–46`); Engine `3.0.1`
  is in the local Maven repository.
- `SkillValidationIssue` provides source, field path and message. A malformed
  variable marker yields Framework's fixed name reason and authored location in
  the message. Execution reports use `<configuration>` and the outer field path
  `configuration`; skill issues use the source label and outer `config` path.
  For detached prepare, `DefaultSkillReloader.java:80–89` wraps failures in
  public `SkillReloadException`; Framework's internal variable exception has no
  public structured subtype. Its fixed `key-collision` message lists the two
  authored locations without resolved keys. The current Sidecar helper at
  `RuntimeConfigurationService.java:506–520` recognizes only an obsolete
  missing-property message and otherwise deliberately reports a generic failure.
  Arbitrary preparation failures can contain provider causes or resolved input,
  so generic failure sanitization remains distinct from variable diagnostics.

### Publication, rollback, restart and invocation

- `ManagementEditingService.java:219–270` captures the exact draft, rechecks it
  and lease after validation, and requires a successful matching proof before
  admission. `RuntimeConfigurationService.java:269–374` reassembles with the
  latest draft records behind the publication and transition gates, compares the
  proof, prepares a detached replacement, and submits it as `PENDING` with a
  checked predecessor. It stages the generation, publishes, and then clears the
  draft and marks the snapshot `PUBLISHED`. Activation failure reverts selection
  and keeps the draft. A restart currently recovers even an intended `PENDING`
  submission when the prior process stopped before completing bookkeeping.
- `storage/ConfigurationSnapshotRepository.java:28–58,78–116` stores both authored
  and effective YAML and encryptions supplied for that publication. Snapshot
  metadata derives its identifiers from stored records. During startup
  (`RuntimeConfigurationService.java:89–137`), Sidecar loads the selected snapshot,
  uses its encrypted versions, prepares and stages a generation, and only then
  opens execution. `EffectiveExecutionConfiguration.restore` compares generated
  YAML against persisted effective YAML. Schema columns for effective YAML and
  retained source only serve the existing derived-settings and source proof paths.
- `ManagementConfigurationRollbackService.java:19–34` validates historical
  records and loads them into the draft. `RuntimeConfigurationService.java:443–464`
  also requires retained draft values to equal historical records when source ID
  and `retainedSource` are set, preventing value-only repair of rollback as
  written. `ManagementConfigurationImportService.java:27–54` separately
  authenticates included encrypted bundles before importing, and supports an
  explicit configuration-only load. Its source UUID can come from another
  installation. These two source types currently share the generic retained-load
  flag but have different origins and trust checks.
- `ConfigurationGenerationRegistry` associates the Framework generation with
  its Sidecar snapshot. `RuntimeConfigurationService.java:93,309–322,475–478`
  stages before publish, subscribes for retirement and protects nonretired
  generations from pruning. HTTP invocation now reads only captured target and
  skill settings. `http/HttpSkillExecutor.java:17–32` obtains passthrough JWT from
  request security context and applies auth/expiry checks at dispatch.

### Both startup modes with Framework 35.4

The paired 35.5 testing plan records two failures reproduced on unchanged
Sidecar `5899e2f` after the Framework install. In database mode
`ConfigurationModeConfiguration.java:20–66` installs an empty executor/skills
bootstrap and skips configured execution properties via the Boot bind advisor.
Framework's `internal/autoconfigure/ExecutorConfigurationBinding.java:24–33`
selects connections and executors in the root binding hook via
`StartupVariableResolution.java:34–78`. It reads the binding context's Spring
property sources directly, so skipping the ordinary child connection bind does
not isolate configured connections. Spring's `ConfigurableEnvironment` and
`PropertySource` APIs are already used by Sidecar. A single high-priority empty
connection map also leaves lower provider values visible because source selection
merges connections. Executor selection uses the first winning source.

In file mode, `RuntimeConfigurationService.startFiles` at lines 165–191 binds
the connection map a second time for management inspection. Framework's YAML
loader retains an opaque `Raw` value at the root and independently consumes it
when constructing clients. Standard Boot map binding for inspection cannot
convert it. The public `SkillCatalog` exposes generation/skill metadata but
does not expose provider settings. The failure occurs after Framework startup,
before Sidecar records its durable file admission identity. The known HTTP file
startup cases pass because they do not require reading a file connection map
for inspection. Adding imports from Framework internal packages would violate
the boundary and the architecture test.

## Open Questions

- The Framework public API has no structured detached variable diagnostic type
  and no file provider inspection API. Planning needs to account for both without
  depending on Framework internals or relaxing secret handling.
- The baseline schema stores generated YAML and historical loader metadata.
  Planning determines whether storage changes require a development database
  reset and documents its impact without touching deployed data.
- The external suite's artifact and Docker readiness for an isolated deployed
  replay is unverified. The inspected suite coverage exposes both a safe source
  fixture path and a separately provisioned end-to-end runtime path.
