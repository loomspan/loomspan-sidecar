# Publication History and Outcome Inspection Research

## Research Question

How does the checked-out Sidecar currently retain, inspect, authorize, and present
configuration publication history and runtime outcome state, and what current browser,
test, documentation, framework, and operational boundaries are relevant to PR 1.4.3?

## Summary

The server-side inspection contract requested by the ticket already exists. Every
authenticated management role can fetch the full runtime-published snapshot, the
intended SQLite selection and global mutation fault, an authoritative oldest-first
list of complete retained submissions, and a complete retained submission by local
UUID. Runtime inspection and history reads share the publication lock; each store
read is transactional, and immutable snapshot rows preserve local/source identity,
document order, original authored text, and recorded `PENDING`, `PUBLISHED`, or
`FAILED` status.

The embedded browser currently exposes only `/management/configuration/current`.
It renders the current runtime snapshot and raw intended/fault fields using DOM
`textContent`, but it has no retained-history page, history navigation, snapshot
detail interaction, expired-entry recovery, semantic explanation of pending and
fault states, or link to the existing operator recovery procedure. The edit page
does distinguish several immediate publish error codes and never retries a lost
connection automatically, but reconnecting users have no browser path to retained
submissions.

Existing storage, runtime, authenticated HTTP, session, and Playwright tests cover
most of the underlying contracts. Browser evidence is absent for retained history,
relogin/reconnect inspection, pending/failed/source identity presentation, expired
detail recovery, history-specific safe rendering and keyboard use, and idle expiry
while background history inspection occurs.

## Current Behavior and Data Flow

### Durable snapshot representation

`ConfigurationSnapshot` contains a stable local UUID, optional source UUID,
positive submission sequence, complete `ManagedConfiguration`, and status
(`src/main/java/ai/loomspan/sidecar/storage/ConfigurationSnapshot.java:6-18`).
`ManagedConfiguration` copies the ordered skill-document list and requires unique,
nonblank diagnostic labels and non-null YAML/REST text; it does not parse or resolve
authored content (`src/main/java/ai/loomspan/sidecar/storage/ManagedConfiguration.java:10-28`).

SQLite assigns the monotonically increasing `submission_sequence`, stores local and
nullable source UUIDs, complete REST YAML, ordered skill documents, and separate
status bookkeeping. Database constraints limit status to `pending`, `published`, or
`failed`, and update triggers make snapshot headers and documents immutable
(`src/main/resources/db/migration/V1__configuration_snapshots.sql:1-42`). There is
no stored submission timestamp, submitting account, durable operation record, or
per-snapshot fault field.

Insertion creates a fresh local UUID and a `PENDING` status, preserving every skill
document in ordinal order (`ConfigurationSnapshotRepository.java:22-46`). Reads
load the header/status and documents by one submission sequence, verify the exact
document count and contiguous ordinal sequence, and rebuild one complete snapshot
(`ConfigurationSnapshotRepository.java:61-90`). History selects sequence numbers in
ascending order and resolves each complete record (`ConfigurationSnapshotRepository.java:56-59`).
The optional source UUID is supported by the store and serializer, although ordinary
browser publication currently submits `null` provenance
(`RuntimeConfigurationService.java:173-185`).

### Publication, outcome recording, and faults

`RuntimeConfigurationService` maintains volatile runtime-published, intended,
intended-status, and mutation-fault state and serializes publication through a fair
`ReentrantLock` (`RuntimeConfigurationService.java:28-62`). A normal accepted update:

1. prepares and stages complete content;
2. atomically inserts pending B and moves the intended pointer from runtime A to B;
3. binds B's durable ID to its process-local framework generation and publishes;
4. sets in-memory runtime B and clears old editing state;
5. records B as published; and
6. prunes eligible history
   (`RuntimeConfigurationService.java:153-235`).

The stored status describes recorded bookkeeping, not runtime truth. Specific paths
are observable:

- preparation or commit failure stops before activation; commit failure creates no
  retained B (`RuntimeConfigurationService.java:163-183`);
- framework activation failure attempts an atomic pointer revert and marks B failed;
  successful revert leaves A running/intended and no mutation fault
  (`RuntimeConfigurationService.java:187-215`);
- failed revert leaves A running, pending B intended, and a mutation fault that stops
  later managed-configuration mutations (`RuntimeConfigurationService.java:198-214`,
  `326-328`);
- outcome-recording failure leaves B running/intended with stored `PENDING` and a
  mutation fault (`RuntimeConfigurationService.java:217-230`);
- pruning failure occurs after activation and possibly after published status was
  recorded; it sets a mutation fault and is surfaced as `history_pruning_failed`
  (`RuntimeConfigurationService.java:228-230`, `300-305`).

`current()` returns a full runtime-published snapshot separately from intended ID,
intended stored status, and mutation fault. It reloads the runtime snapshot from
storage so a successful status update appears, but falls back to the in-memory
published object if that lookup fails and records an inspection fault
(`RuntimeConfigurationService.java:244-258`). Consequently a runtime-published
snapshot may truthfully display `PENDING` when outcome bookkeeping is unknown.
`inspectLocked()` reads the current SQLite pointer; on inspection failure it reports
the last known intended fields and records a fault rather than substituting the
pointer for runtime identity (`RuntimeConfigurationService.java:273-282`).

### History consistency and pruning

`history()` and `history(UUID)` acquire the same publication lock used by the entire
publication attempt before entering transactional store reads
(`RuntimeConfigurationService.java:238-271`). Publication and its post-attempt
pruning therefore cannot interleave with one of these service reads. A detail lookup
returns the snapshot selected by that UUID or `null`; the repository resolves all
of its header, status, and content using its one submission sequence.

Pruning counts every status, protects the intended selection and caller-supplied
runtime/live-generation IDs, deletes oldest eligible snapshots first, and permits
protected overflow (`ConfigurationSnapshotStore.java:125-145`). Runtime pruning adds
the current published ID and generation/resource protection set
(`RuntimeConfigurationService.java:308-312`). A retired generation only becomes
eligible; pruning runs at startup or after another completed attempt rather than in
the retirement callback. A formerly retained UUID therefore legitimately becomes
absent and is not kept alive by a browser link.

The list API returns full snapshot content rather than a summary, while the detail
API independently reloads by UUID. A browser can therefore hold an ID from one list
response that has been pruned before a later detail request; the existing response
for that case is explicit absence, not a synthesized outcome.

### Protected management HTTP API

`ManagementConfigurationController` exposes:

- `GET /api/management/configuration/current` for the `Current` runtime/intended/fault
  representation;
- `GET /api/management/configuration/history` for the full ordered retained list;
- `GET /api/management/configuration/history/{id}` for one complete retained snapshot;
  and
- CSRF-protected `POST /api/management/configuration/publish`
  (`src/main/java/ai/loomspan/sidecar/management/ManagementConfigurationController.java:19-50`).

Unknown or pruned detail IDs return 404 JSON with `code: history_not_found` and the
message "Snapshot is unknown or no longer retained"
(`ManagementConfigurationController.java:40-45`). Publication failures return a
nonsecret code/message with fresh runtime/intended/status/fault inspection
(`ManagementConfigurationController.java:59-64`).

The management security chain requires authentication for every route not explicitly
listed. Account administration and editing/publication mutations receive narrower
role rules; configuration GET routes fall through to authenticated access, so viewer,
editor, and admin sessions can inspect them
(`ManagementSecurityConfiguration.java:48-64`). GET inspection needs no CSRF token;
unsafe requests do. Execution JWTs and observability credentials are handled by
other security chains and do not authenticate management.

Draft reads remain session-derived and return only the calling session's eligible
draft (`ManagementEditingService.java:61-69`). Admin takeover creates a fresh draft
from runtime rather than reading the former owner's content
(`ManagementEditingService.java:72-89`). A configuration fault blocks acquisition,
activity renewal, save, validation, and publish through `withEditingState(true)`,
while lease status, own-draft inspection, release, discard, configuration inspection,
and account administration remain available
(`ManagementEditingService.java:47-69`, `72-119`, `122-177`; `RuntimeConfigurationService.java:314-328`).

### Embedded browser behavior

The shared navigation currently links Home, Current configuration, Edit configuration,
Change password, and Accounts for admins. There is no history link or history page
route (`ManagementPagesController.java:164-171`). The current page shell contains an
ARIA live status, explicit Refresh button, and a content container
(`ManagementPagesController.java:107-111`).

`console.js` fetches the protected current API and displays:

- runtime local ID, stored status, source ID, and submission sequence;
- every skill document label and YAML body;
- complete REST routes/targets YAML; and
- intended ID/status plus raw mutation-fault text
  (`src/main/resources/static/management/assets/console.js:61-90`).

All authored strings are inserted through `textContent` or `createTextNode`, including
inside `<pre>` elements (`console.js:9-13`, `61-84`), so authored markup is displayed
as text. The same code does not currently interpret `PENDING` as outcome-unknown,
compare published and intended IDs, distinguish fault stages, state mutation
restrictions, or link to operator recovery. It labels the snapshot
"Runtime-published" but otherwise shows raw enum/fault values.

The edit page's immediate publication result mapping already distinguishes pre-
activation failure, reverted activation failure, failed revert, post-activation
outcome-recording failure, and pruning failure. A transport loss is labeled unknown
and no automatic retry is made (`editor.js:232-271`). It then fetches current runtime
state, but has no retained-history link. Its ten-second ownership/current polling is
read-only (`editor.js:172-200`, `303-323`).

The generic console script reports login activity only in response to click, keydown,
input, paste, or scroll events and throttles reports to 30 seconds
(`console.js:53-60`). API reads do not report activity. The editor similarly separates
user events from automatic save, validation, and ten-second status reads
(`editor.js:273-303`). On an API 401 the current console redirects to login; on 403 it
removes controls and authored content (`console.js:20-50`).

### Session expiration and response privacy

The session guard checks account activity/version and a Sidecar-owned idle timestamp
on every authenticated management request. Ordinary GET traffic does not update that
timestamp (`ManagementSessionGuard.java:25-39`). Only `report()` advances activity,
at most once per 30 seconds, and it cannot revive a session at or beyond the idle
deadline (`ManagementSessionGuard.java:40-74`). All application responses receive
`Cache-Control: no-store`; management pages/APIs also receive `Referrer-Policy:
no-referrer` (`src/main/java/ai/loomspan/sidecar/api/NoStoreResponseFilter.java:14-25`).

## Dependencies and Operational Constraints

- The public framework boundary remains closed. Sidecar currently uses public
  `SkillReloader`/`PreparedSkillUpdate` types only; the ArchUnit test enforces no
  `ai.loomspan.internal..` or `ai.loomspan.autoconfigure..` dependencies.
- Matching framework documentation states that generation IDs are fresh,
  process-local, opaque identities and that the application owns durable snapshots,
  staging, readiness, cleanup, and retries
  (`C:/opendev/code/loomspan-framework/agent-skills/loomspan-docs/references/java-api/skill-reload.md:42-62`).
  They are therefore not durable browser history identifiers.
- Snapshot retention defaults to ten and is configured by
  `loomspan-sidecar.snapshots.max-retained` (`application.yml:11-12`; `README.md:178-185`).
  Protected snapshots can make retained count temporarily exceed the target.
- One Sidecar instance owns one file-backed SQLite database; current operational
  documentation excludes shared replicas/network filesystems (`README.md:187-190`).
- Complete authored snapshots may include secrets and are intentionally returned to
  viewers. Browser/API responses are non-cacheable, but SQLite and stopped backups
  are unsanitized and require access protection (`README.md:106-116`, `614-620`).
- The documented operator procedure is offline: stop the sole instance, preserve a
  consistent full database-set copy, correct storage, and restart if the committed
  intended selection is wanted; an unreverted A/B fault requires restoring a known-
  good stopped backup to recover A. There is no online repair endpoint
  (`README.md:230-252`).
- Existing history/current inspection performs no live external action. Framework
  validation/publication and REST staging are outside read paths.
- Phase 5 owns import/export, rollback, and destructive cutover. There is no current
  cancel endpoint or durable job/operation-status subsystem.

## Open Questions

- The repository contains the operator recovery procedure only as a README section,
  not a stable fragment identifier or separate in-console help route. Planning must
  establish what browser link target can accurately satisfy the ticket without
  creating an online repair workflow.
- History list responses already contain full content while the detail API repeats a
  transactional lookup and can independently return expired. The ticket requires list
  and snapshot detail presentation, but the exact browser navigation/state model is
  not established by existing code.
- The server exposes a global free-text mutation fault plus current/intended/status,
  not a durable fault event tied to each historical row. Browser explanations must be
  derived only from those present fields and recorded statuses; older operation stages
  are not reconstructible beyond `PENDING`/`PUBLISHED`/`FAILED`.
- The schema supplies authoritative sequence but no time or actor. Any presentation
  that implies submission time or submitter identity would lack current evidence.
