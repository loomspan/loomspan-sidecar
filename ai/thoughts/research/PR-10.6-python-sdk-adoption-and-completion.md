# Python SDK adoption and completion research

## Research Question

What does the maintained equipment application currently own, where does the
installed SDK take over its execution boundaries, and which executable checks
and environments can establish the final interoperability and support target?

## Summary

The SDK already supplies async transport, provided-key issuance, current public
trust verification and an app-lifespan/prefix guard. The maintained suite still
signs, forwards and verifies execution credentials in its own Python code.
Keycloak remains the source of public request identity. The application owns
business authorization and the equipment workflow. The existing operator RSA
key is compatible with provided signing. Its SDK public export uses a derived
key ID, so Sidecar must consume the new public export while ownership remains
bound to the same execution issuer and subject.

The current consumer dependency lock cannot install the SDK extra unchanged.
The local environment exposes native Windows and Linux x86-64 execution and
the existing Java runner has provider-free direct HTTPS and paired Caddy
compositions. No macOS ARM64 execution surface was identified. Package
resolution in the Linux CPython 3.12 cache succeeded for declared direct
minimum and current SDK dependencies. That is feasibility evidence only.

## Key Components

- `sdks/python/src/loomspan_sdk/fastapi.py:83–187,265–312` owns one
  reusable async client, signer and verifier within the app lifespan.
  The outer middleware protects the literal prefix and descendants
  before routing, accepts verified GET and POST, and exposes a
  `CallbackPrincipal` dependency without interpreting record/role policy.
- `sdks/python/src/loomspan_sdk/_signing.py:102–190` loads unencrypted
  RSA PKCS#8 in provided mode, rejects unsafe export aliases, derives
  a SHA-256 public-key thumbprint as kid from RSA `n/e/kty`, and
  replaces the public file atomically in its directory. It does not
  write or regenerate the provided private key.
- Suite `scripts/prepare.py:9–23` generates an RSA-2048 PKCS#8 PEM and
  a literal-kid public file only when both paths are absent, keeps
  both existing files, and rejects an incomplete pair. Today
  `compose.yaml:19–31,44–53` mounts the private PEM only into Python
  and mounts the old public file read-only into both services. That is a
  provisioning/runtime boundary for the SDK's own writable public
  export. A single-file bind can pin the old inode when a publisher
  replaces the directory entry. Sidecar's current trust indexes by kid
  (`security/CurrentFileJwtTrust.java:53–59,93–102`,
  `security/ExecutionJwtDecoder.java:35–47`). A new token cannot validate
  against a legacy-only kid export, and an old token cannot validate
  against a derived-kid-only export even if the public RSA numbers match.
  No change to the private key or persisted issuer/subject is needed for
  this public trust change. Existing suite tests assert the old kid and
  file layout and consequently exercise superseded fixture assumptions.
- Suite `apps/python/Dockerfile:1–7` serves both Python app and fixtures,
  installs `requirements.lock` and copies suite sources. The image has
  no SDK artifact input. `scripts/package_runtime.py:17–43` exports the
  tracked/unignored source tree and two approved JARs. The supplied
  distribution omits a neighboring checkout by design.
  `scripts/install_runtime.py:14–61` verifies its manifest and refuses
  to replace an existing runtime. Source and supplied runtime paths both
  inherit the base Compose Python build. A locally built wheel therefore
  affects packaging/installation as well as application imports.
