# Validated Runtime Publication Research

## Research Question

What does the checked-out Sidecar currently do for configuration storage, startup, REST routing, execution handoff, retirement, and recovery, and which public beta 5 framework contracts and existing tests bear on PR 1.2.1?

## Summary

Sidecar has complete authored snapshot storage and transactional `submit`/`revert`/status/pruning operations, but the active framework generation and REST routes still come from mounted files at startup. There is no runtime publication coordinator or concrete framework-backed draft validation service. Execution already transfers ownership at the worker handoff, while its retained record has no durable configuration ID. The matching local framework checkout provides `SkillReloader.prepare(Collection<SkillDocument>)`, one-shot `publish`, current `snapshot()`, generation retirement notification, and generation IDs on admitted and REST invocations.

## Current Behavior and Data Flow

### Durable snapshot and draft state

`StorageConfiguration` constructs a file-backed SQLite source, enables foreign keys, WAL, FULL synchronous writes and a 5-second busy timeout, runs Flyway, then creates a `ConfigurationSnapshotStore`. Its bean factory calls `initialize()` and `prune(Set.of())` during context creation (`src/main/java/ai/loomspan/sidecar/storage/StorageConfiguration.java:27-59,62-94`). V1 schema separates immutable snapshot headers, ordered named YAML documents, mutable status, and the singleton selected pointer (`src/main/resources/db/migration/V1__configuration_snapshots.sql:1-42`).

`ConfigurationSnapshotStore.initialize()` creates one empty pending snapshot only for a genuinely uninitialized empty store; otherwise it loads the committed selected sequence without consulting status. Missing pointer/content fails (`src/main/java/ai/loomspan/sidecar/storage/ConfigurationSnapshotStore.java:34-69,143-159`). `submit` inserts a complete pending snapshot and guards an A-to-B pointer switch in one transaction; `revert` guards a B-to-A switch and marks B failed in one transaction; `updateStatus` is separate (`ConfigurationSnapshotStore.java:72-118`). `prune` protects the selected pointer and caller-supplied UUIDs while removing oldest eligible history above the configured count (`ConfigurationSnapshotStore.java:120-141`). Repository reads check status, document count, and contiguous ordinals; inserts retain `SkillDocument.sourceName()` and YAML text and REST YAML text (`src/main/java/ai/loomspan/sidecar/storage/ConfigurationSnapshotRepository.java:22-85`).

`ManagedConfiguration` copies the document list and requires exact unique, nonblank labels; it leaves authored YAML and REST text unparsed (`src/main/java/ai/loomspan/sidecar/storage/ManagedConfiguration.java:10-29`). `ConfigurationDraft` starts from a caller-supplied snapshot UUID, keeps a current `FrozenConfigurationCandidate`, invalidates validation on every replace, and accepts late validation only for the identical candidate object (`src/main/java/ai/loomspan/sidecar/storage/ConfigurationDraft.java:9-54`). `ConfigurationValidationResult` and `ConfigurationValidationIssue` hold a caller-supplied result, source label, message and optional location; they do not execute validation (`src/main/java/ai/loomspan/sidecar/storage/ConfigurationValidationResult.java:6-14`, `ConfigurationValidationIssue.java:3-17`). No application service currently calls `SkillReloader` or connects these draft primitives to running configuration (verified by source search and the classes above).

### Startup and active configuration

`application.yml` currently points `loomspan.skills.locations` to `/sidecar/skills/**/*.yaml` and `/**/*.yml`, and `loomspan-sidecar.rest-routes-location` to `/sidecar/rest-routes.yaml` (`src/main/resources/application.yml:1-15`). `RestRouteLoader` eagerly reads that resource in its constructor and keeps one parsed configuration (`src/main/java/ai/loomspan/sidecar/rest/RestRouteLoader.java:32-58`). `RestTargetClients` eagerly builds one client map from the loader (`src/main/java/ai/loomspan/sidecar/rest/RestTargetClients.java:24-43`). `RestRouteCatalogValidator.afterSingletonsInstantiated()` compares the mounted routes with the injected startup `SkillCatalog` (`src/main/java/ai/loomspan/sidecar/rest/RestRouteCatalogValidator.java:12-40`). Storage initialization has no corresponding `prepare`/`publish` call. Thus the database selected snapshot is durable but is not the source of active framework skills or routes in this checkout; README says this explicitly (`README.md:97-108`).

`ExecutionCoordinator` initializes its `open` flag to `true` and immediately starts its worker pool and sweeper (`src/main/java/ai/loomspan/sidecar/execution/ExecutionCoordinator.java:38-82`). Admission checks this flag, but there is no startup activation gate tied to storage or publication (`ExecutionCoordinator.java:84-108`). Its close listener flips the flag, publishes refusing readiness, and discards queued work (`ExecutionCoordinator.java:191-208`). Destruction later interrupts workers (`ExecutionCoordinator.java:213-226`). Existing handler lifecycle tests protect the previous startup-only resource lifetime (see tests below).

### REST parsing, clients, and routing

The REST document requires `targets` and `routes`; loader checks unknown keys, duplicate names, target references, methods, path variables, timeouts, response caps and optional Spring SSL-bundle names (`RestRouteLoader.java:60-179,211-304`). Except for syntax-specific checks, strings are resolved using `ConfigurableEnvironment.resolveRequiredPlaceholders`, including `base-url` (`RestRouteLoader.java:119-125,306-334`). The URL parser then requires an absolute HTTP(S) URI with host and without user-info, query or fragment (`RestRouteLoader.java:211-226`). There is currently no `loomspan-sidecar.url-variables` property or process-environment-only allowlist boundary. The authored REST text remains unchanged in SQLite because the repository stores it before parsing (`ConfigurationSnapshotRepository.java:25-46`).

`RestTargetClients` creates an Apache `CloseableHttpClient` per target, with configured timeouts, optional SSL context, no redirects/retries/cookies, and a bounded response cleanup interceptor (`RestTargetClients.java:60-107`). It closes all built clients idempotently, including partial construction failures, using the no-argument `CloseableHttpClient.close()` (`RestTargetClients.java:31-58,109-115`). `GenericRestSkillHandler` is the fixed `RestSkillHandler` bean, but resolves every invocation against its one constructor-captured route configuration and client map, without using `RestSkillInvocation.generationId()` (`src/main/java/ai/loomspan/sidecar/rest/GenericRestSkillHandler.java:25-75`). It forwards the captured JWT for caller passthrough and binds/validates paths and query/body data (`GenericRestSkillHandler.java:41-74,87-167`). Its `SmartLifecycle.stop()` closes that one client map (`GenericRestSkillHandler.java:77-85`).

### Discovery, execution, and retained records

`SkillCatalogController` and the execution POST precheck inject `SkillCatalog` and call its `skills()`/`skill()` methods (`src/main/java/ai/loomspan/sidecar/api/SkillCatalogController.java:14-25`, `ExecutionController.java:27-48`). The execution POST also calls `SkillTemplate.validate` before queue admission. The worker handoff remains inside `ExecutionCoordinator.handoff`, after queueing and immediately before invocation, under its gate and with the JWT restored in Spring Security context (`ExecutionCoordinator.java:135-162,300-315`). Queued work therefore has no framework generation until the worker reaches that handoff. The code does not yet read `AdmittedSkillInvocation.generationId()`.

An `ExecutionRecord` starts with a QUEUED `ExecutionSnapshot`; handoff changes it to RUNNING, and completion atomically stores result/failure plus selected observer events (`src/main/java/ai/loomspan/sidecar/execution/ExecutionRecord.java:8-22`, `ExecutionCoordinator.java:155-177`). The record and GET response have no `configurationSnapshotId` (`src/main/java/ai/loomspan/sidecar/execution/ExecutionSnapshot.java:9-15`, `src/main/java/ai/loomspan/sidecar/api/ExecutionController.java:54-67`). The worker releases a non-null admitted handle in `finally` (`ExecutionCoordinator.java:300-315`). Completed records expire as whole records by TTL (`ExecutionCoordinator.java:110-133`); history pruning is separate from execution retention.

### Failures and operator recovery

Store calls surface transaction and selected-load failures; selected-load error text directs an operator to stop Sidecar and restore a consistent full database backup (`ConfigurationSnapshotStore.java:143-159`). `README.md:184-235` documents stopped-instance full database-set backup/restore and notes runtime fault recovery is Phase 2 work. There is no runtime published/intended inspection service or mutation-fault state yet. README still documents mounted-file startup, restart-only changes, and current shutdown assumptions (`README.md:248-275,488-527`). Kubernetes sample mounts skill and route files; verification scripts assert or exercise those mounts (`examples/kubernetes/deployment.yaml:80-86`, `scripts/verify-image.py:72,153-162`).

## Dependencies and Operational Constraints

- Matching local framework documentation states the injected `SkillCatalog` is a permanent startup snapshot and `SkillReloader.snapshot()` is the current immutable catalog (`C:/opendev/code/loomspan-framework/agent-skills/loomspan-docs/references/java-api/skill-reload.md:8-10`; `catalog-and-validation.md:10-15`). Public Java signatures are in `C:/opendev/code/loomspan-framework/src/main/java/ai/loomspan/api/SkillReloader.java:7-32` and `PreparedSkillUpdate.java:4-8`.
- `prepare(Collection<SkillDocument>)` validates and freezes a complete authored replacement without activation; `publish` is one-shot and only valid for the preparing framework instance and active base. Empty documents remove YAML skills. Prepared updates have process-local generation IDs and candidate catalogs (`skill-reload.md:27-43`). Operational preparation/publication errors use public `SkillReloadException` (`src/main/java/ai/loomspan/api/SkillReloadException.java:3-8`).
- Framework retirement notification covers superseded published generations only after pending admissions, roots and physically running descendants finish. It may run before `publish` returns, concurrently, and on framework threads; shutdown may omit callbacks. Never-published candidates receive none (`skill-reload.md:47`; `SkillReloader.java:21-32`). Public `RestSkillInvocation` includes a trusted generation ID for the fixed handler (`C:/opendev/code/loomspan-framework/src/main/java/ai/loomspan/api/RestSkillInvocation.java:10-20`; `rest-skills.md:20-24`).
- Public `AdmittedSkillInvocation.generationId()` identifies the captured generation even if current publication changes before handoff returns; reading it does not retain ownership. The handle requires release if abandoned (`C:/opendev/code/loomspan-framework/src/main/java/ai/loomspan/api/AdmittedSkillInvocation.java:5-23,45-46`; `invocation.md:107-143`). Framework authorization at invocation remains authoritative; `SkillTemplate.validate` is advisory (`catalog-and-validation.md:17-33`).
- Deployment uses one local SQLite database and a single Sidecar instance. The current backup procedure copies the stopped database file plus WAL/SHM set, with no live service operation (`README.md:174-235`). Repository guidance requires supported `ai.loomspan.api` types only, the installed beta 5 snapshot, and no framework rebuild or release within this ticket.

PR 1.1.2 established database-first submit/revert/status and caller-supplied pruning protection, assigning runtime protection and publication recovery to Phase 2 (`ai/thoughts/tickets/2026-09-17-pr-1.1.2-snapshot-recovery-and-history.md:1-76`). The design lens names framework authority, one admission owner, trusted JWT propagation and the single shutdown budget as cross-ticket constraints (`ai/thoughts/design-lens.md:32-83`); the current ticket explicitly replaces its older startup-only configuration statement.

## Open Questions

- The current source has no startup/publication coordinator, so its concrete Spring lifecycle ordering and fault-injection seams are not yet established by Sidecar tests. The ticket specifies the observable ordering and fault outcomes.
- The current REST client code uses `CloseableHttpClient.close()` without a bounded close mode. The actual HttpClient API and shutdown timing behavior need direct verification during planning/implementation, as the ticket requires bounded cleanup.
- The checked-out test harness centers on mounted content; which fixtures remain useful after database-authoritative startup depends on the final production wiring. This is a test organization question, not a contract gap.
