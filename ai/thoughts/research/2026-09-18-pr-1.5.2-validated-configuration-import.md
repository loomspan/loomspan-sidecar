# Validated Configuration Import Research

## Research Question

How do the current format-1 bundle reader, management authorization, editing state, validation, and database-first publication work, and where does the requested import intersect them?

## Summary

The current application exports the runtime-published snapshot and reads format-1 bundles without activating them. The reader returns source identity, producer versions, and exact authored skill and REST content. There is no import endpoint or console import flow. Current validation checks complete skill documents with the public framework `SkillReloader.validate(...)`, then parses and checks REST resources; current draft publication separately prepares and stages afresh, commits a pending local snapshot, and publishes it. Ordinary publication clears drafts only after framework activation. The ticket specifies an earlier destructive cutover for import, after successful preparation and staging.

Management sessions use a separate security chain, form login, role authorities, and CSRF. Drafts and one lease grant are in-memory; published and intended identities and history are SQLite-backed. The existing runtime service has publication and editing-transition locks, while session and account invalidation directly synchronize on editing state. These are the current synchronization points relevant to an import confirmation and non-cancellable accepted attempt.

## Current Behavior and Data Flow

### Format-1 bundle and export

`GET /api/management/configuration/export` captures `runtime.publishedSnapshot()`, writes a temporary ZIP, and streams it with no-store headers; the streaming callback deletes the temporary file (`ManagementConfigurationController.java:41-62`). The bundle writer includes `manifest.json`, `rest.json`, and numbered skill YAML entries, with source snapshot ID, producer versions, source labels, and SHA-256 payload checksums (`ConfigurationBundleV1.java:65-103`). The writer bounds total entries, expanded bytes, and compressed file size. The existing reader stages up to 100 MiB compressed input in a temporary file and deletes it in `finally` (`ConfigurationBundleV1.java:111-123`). `read(Path)` checks the ZIP size and 10,000-entry count, paths and duplicates, manifest shape/version, payload inventory and checksums, UTF-8, YAML object roots, REST `targets` and `routes` object roots, entry size/CRC, and a cumulative 512 MiB expanded limit (`ConfigurationBundleV1.java:126-235`). The limits are inclusive: rejection uses `>` and `checkedTotal` permits equality (`ConfigurationBundleV1.java:65-103,111-123,241-244`). The returned `Bundle` has `sourceSnapshotId`, `sidecarVersion`, `frameworkVersion`, and `ManagedConfiguration`; reading neither validates against the destination framework nor publishes (`ConfigurationBundleV1.java:51-52,126-204`). The authored REST YAML and skill YAML remain strings. A parser test covers fixtures, round trips, empty content, corruption, entry and expanded boundaries, and compressed input accounting (`ConfigurationBundleV1Test.java:30-264`). No upload controller or multipart setting appears in the current `application.yml` (`application.yml:1-60`).

### Destination validation and REST binding

`ManagedConfiguration` copies the skill list and requires non-null REST YAML, unique nonblank source labels, and non-null skill YAML (`ManagedConfiguration.java:10-31`). `RuntimeConfigurationService.validate(ManagedConfiguration)` calls public `SkillReloader.validate` on the complete documents, maps framework issues, and, when skill validation succeeds, prepares REST resources and checks routes against the validated skill metadata; it releases temporary REST resources afterward (`RuntimeConfigurationService.java:132-151`). Draft validation freezes a candidate, validates it, and records the result against that frozen candidate (`RuntimeConfigurationService.java:125-130`). The matching local framework documentation states validation is advisory and does not allocate or retain a prepared update; subsequent publication must prepare current input anew (`C:/opendev/code/loomspan-framework/agent-skills/loomspan-docs/references/java-api/skill-reload.md`, “Two-stage skill updates”).

`RestRouteLoader` parses only `targets` and `routes`, requires known target fields, resolves and validates URLs, authentication, SSL bundles, timeouts, route targets, methods, and paths (`RestRouteLoader.java:65-194,217-370`). A REST `base-url` with `${...}` must be the entire value `${NAME}`, the name must occur in the exact `loomspan-sidecar.url-variables` allowlist, and its value comes from `System.getenv`, not Spring's property resolver. Missing/blank values and invalid final HTTP(S) URLs fail (`RestRouteLoader.java:40-59,160-178,217-236`; `RestRoutesProperties.java:5-17`). Other REST string placeholders use `ConfigurableEnvironment.resolveRequiredPlaceholders` (`RestRouteLoader.java:336-347`). The authored YAML is stored unchanged, so destination parsing determines the effective target (`ManagedConfiguration.java:10`; `ConfigurationSnapshotRepository.java:22-46`). The default URL allowlist is empty (`application.yml:18`).

### Editing and ordinary publication

`ManagementEditingState` holds session-keyed private drafts and one lease with session ID, tab ID, random `grantId`, and mutable expiration (`ManagementEditingState.java:10-52`). Acquisition creates a new grant and possibly resumes an eligible same-session draft; admin takeover starts a fresh draft. Activity may extend the same grant without rotating its ID. Save requires the exact candidate ID and rotates it even if saved content is equal. Validation captures a frozen candidate, validates outside the transition gate, and checks the entry/candidate again before attaching feedback (`ManagementEditingService.java:55-90,110-178`). Existing status exposes lease presence and whether it belongs to the current session, but does not expose the foreign owner's identity or grant (`ManagementEditingService.java:21-24,44-53`). Existing publication admission requires an active session, current account/role, owned lease, exact candidate ID, and validation of the same frozen draft (`ManagementEditingService.java:181-213`).

`RuntimeConfigurationService.publish` acquires its fair publication lock, runs the admission callback, checks the runtime base identity, and calls public `prepare` plus complete matching REST staging anew (`RuntimeConfigurationService.java:153-171,295-308`). It stages the generation, transactionally inserts a new pending snapshot and changes the intended database pointer, then binds the local ID and calls framework `publish` under the transition lock. Ordinary publication clears all editing state after framework activation (`RuntimeConfigurationService.java:172-198`). `ConfigurationSnapshotStore.submit` accepts a `sourceId` and expected predecessor ID; repository insertion generates a fresh `UUID.randomUUID()` and records `source_id` separately (`ConfigurationSnapshotStore.java:72-87`; `ConfigurationSnapshotRepository.java:22-46`). The present draft path submits with `sourceId = null` (`RuntimeConfigurationService.java:178-181`). Retained history is ordered by submission sequence and pruned according to configured retention, protecting selected/runtime and generation-owned IDs (`ConfigurationSnapshotRepository.java:56-60`; `ConfigurationSnapshotStore.java:126-145`; `RuntimeConfigurationService.java:313-323`).

If preparation/staging fails, `publish` returns `preparation_failed` before a submission. A commit failure discards staged resources and returns `commit_failed`; runtime and intended selection remain old (`RuntimeConfigurationService.java:163-187`). A failed framework activation attempts `store.revert`, which switches the pointer back and marks the submitted snapshot `FAILED`; failed reversion sets a mutation fault and leaves the intended selection pending (`RuntimeConfigurationService.java:199-218`; `ConfigurationSnapshotStore.java:89-108`). After successful framework activation, status-recording or pruning failure sets a mutation fault without undoing the active runtime (`RuntimeConfigurationService.java:220-235`). `requireHealthy()` blocks configuration mutations when faulted, while inspection and execution remain available (`RuntimeConfigurationService.java:238-294,325-340`). Startup activates the database-selected snapshot and marks it published before opening execution (`RuntimeConfigurationService.java:78-122`). `GenerationRestResources` stages and binds generation resources, discards rejected generations, and retires old resources after framework notification (`GenerationRestResources.java:22-112`). The local framework documentation says old admitted work retains its generation and `publish` freezes prepared content (`.../references/java-api/skill-reload.md`, “Two-stage skill updates”).

The runtime service's `publication` lock serializes publications and inspection. `withEditingState` uses the separate fair `transition` lock for editing operations (`RuntimeConfigurationService.java:54-55,153-155,325-334`). Most `ManagementEditingService` operations then synchronize on `ManagementEditingState` (`ManagementEditingService.java:44-215`). Session destruction synchronizes directly on that state to clear a session (`ManagementEditingSessionListener.java:12-16`), and account password/role changes also synchronize directly on it (`ManagementIdentityService.java:129-169`). The ordinary publication code holds `transition` only for the framework switch and editing clear, after preparation and database submission (`RuntimeConfigurationService.java:188-198`).

### Management API and console

The management security chain matches `/management/**` and `/api/management/**`; it uses form login, role authorities, and Spring Security CSRF. Lease/draft mutation and `/configuration/publish` require `MGT_EDITOR`, takeover requires `MGT_ADMIN`, and otherwise authenticated management users may inspect current/history/export (`ManagementSecurityConfiguration.java:42-84`). A separate execution JWT chain is covered by `ConsoleSecurityIntegrationTest.java:41`; the management session guard rejects stale account/session versions and idle sessions (`ManagementSessionGuard.java:25-67`). The session endpoint supplies role, permissions, CSRF token, and timeouts (`ManagementController.java:53-67`). `ManagementConfigurationController` currently exposes current, export, history, detail, and publish; there are no import mappings (`ManagementConfigurationController.java:27-112`). Its publication errors include `publishedId`, `intendedId`, intended status, and mutation fault (`ManagementConfigurationController.java:29-31,103-112`).

The server-rendered console has current, history, recovery, and edit pages, plus role-aware navigation; it has no import page (`ManagementPagesController.java:107-160,192-211`). `console.js` fetches current/history/export, renders authored values with `textContent` and `pre`, and distinguishes pending/failed/published recorded status from runtime identity (`console.js:12-122,160-248`). `editor.js` owns the draft, grant, candidate revision, validation and publication UI and uses `textContent` for messages/issues (`editor.js:1-100`). Existing browser tests exercise viewer export/history, safe content rendering, draft privacy, CSRF/session behavior, editor publication, disconnect and failure messaging (`ManagementHistoryBrowserIntegrationTest.java:59-289`; `ManagementEditorBrowserIntegrationTest.java:73-408`).

## Open Questions

- The current bundle format contains authored REST YAML, but not a parsed count. The review response's exact count convention for skill declarations versus documents and routes is not specified in existing API code.
- There is no existing import review candidate lifetime or upload transport. The ticket defines the binding and safety outcomes, while endpoint shape and ephemeral storage behavior remain to be determined in planning.
- The current status API hides a foreign lease owner's identity. Existing account lookup is available in management identity code, but the precise identity shown and privacy scope for import review are not established by current implementation.
