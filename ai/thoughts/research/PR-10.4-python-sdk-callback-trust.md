# Python SDK Callback Trust Research

## Research Question

What does the current Java callback receiver authenticate, what Python startup
state can supply the same verification inputs, and what evidence exists for the
trust and interoperability boundaries assigned to PR 10.4?

## Summary

- Python already owns a startup RSA signer, a thumbprint kid, a public export,
  and an issuance profile. It has no callback verifier or current-file overlap
  lifecycle at the baseline.
- Java validates exact execution claims and current local public keys. It fails
  on invalid initial overlap, withdraws even its own key on detected runtime
  invalidity, and restores the complete current set after correction.
- The Java timestamp rules include a strict expiry-after-issuance check when
  `iat` is present and inclusive 60-second expiration/not-before boundaries.
  Existing interop runs cover Python issuance into Java receivers. The opposite
  direction requires fresh evidence for this ticket.

## Current Behavior and Data Flow

### Python startup and issuance

`ColocatedSigning` and `ProvidedSigning` validate path types without I/O.
Constructing `ExecutionTokenIssuer` checks the issuance settings, loads or
generates the key, and atomically publishes its public JWKS. Colocated generates
an in-memory RSA-2048 signer and writes `jwks.json` in an existing directory.
Provided loads one unencrypted PKCS#8 RSA key and validates it before exporting
the configured path. `_initialize_signing` obtains the public key, performs a
sign/verify check, computes the RFC 7638 kid, and exports `e`, `kty`, `n`, `kid`,
`alg=RS256`, and `use=sig`. Its return value is the private signer and the kid.
The issuer stores both and the immutable issuance settings in private slots. It
has no current public trust accessor or callback setting. Own callback trust and
the public export are distinct concerns in the Java baseline.

`issue` captures an exact integer nanosecond clock reading and serializes its
time claims as JSON decimals. It uses an exact issuer, string-array audience
with Sidecar, issuer and optional audiences, exact allowlisted authority names,
and the standard execution purpose and JWS header. `AuthenticatedIdentity`
contains the authenticated subject and authority tuple supplied by the app.
`CredentialSnapshot` is opaque and keeps the token out of display and ordinary
serialization. Neither is a verified callback identity with issuer, subject and
authorities.

### Java callback validation

`CallbackSecurityAutoConfiguration` eagerly initializes trust in the servlet
application and closes it at destruction. It supplies the configured issuance
issuer to `CallbackJwtDecoder`. `CallbackProperties.audienceOrDefault` uses
that issuer when audience is absent and rejects a blank explicit value. There
is no independent callback issuer configuration. The filter layer maps the
decoder's roles to exact authorities. PR 10.5 owns Python routing, application
lifespan composition, authorization header handling and the admitted-request
behavior. PR 10.4 owns the callable verifier and refresh lifetime below that
layer.

`CallbackJwtDecoder.decode` parses a compact JWS, requires exact string
`alg=RS256` and `typ=loomspan-execution+jwt`, and accepts a nonblank string kid.
It requires an exact nonblank string issuer, a nonblank string subject, exact
`token_use=loomspan_execution`, and a roles array of nonblank strings that may
be empty. Exact names survive and `scope` adds no authority. Audience may be
one matching string or an array of strings containing the configured audience.
Other array entries need only have string type. Validation uses Java
`String.isBlank()` semantics without trimming accepted strings. Python has
existing equivalents in `_issuance._require_name` and `_protocol._java_blank`.

`exp` is required. Present `iat` and `nbf` must also convert to valid instants.
Present `jti` must be a string, with no nonblank check. The decoder gets one
trust snapshot for the kid and uses Nimbus RSASSA verification with that key.
The Nimbus verifier rejects unsupported critical headers and recognizes `b64`
as processed. JWS and JWT library defaults are therefore part of understanding
the observed boundary, separate from the explicitly checked profile. Unknown
uncritical claims are not interpreted as business policy. The Java decoder
reduces failure to `Invalid callback execution credential` without a cause.

#### Timestamp behavior

`CallbackJwtDecoder.numericDate` requires `Number`, converts through
`BigDecimal(value.toString())`, floors to integral seconds, moves the fraction
to nanoseconds, truncates sub-nanosecond remainder within that second, and uses
`Instant.ofEpochSecond`. The Java `Instant` range is represented by Python's
existing `_MIN_INSTANT_NS` and `_MAX_INSTANT_NS`. `Jwt` construction requires
expiration strictly after issuance when both instants are present. Spring's
timestamp validator then applies a 60-second skew to `exp` and `nbf`. It has no
independent future-`iat` skew rule and the decoder adds no `nbf`/`exp` ordering
rule. Sidecar's pre-forward expiry check is strict and independent of receiver
skew (`HttpSkillExecutor.java:37-38`).

A local source-launch probe against Spring Security OAuth2 7.1.0 and Nimbus
10.10 from the existing Java SDK test classpath verified the exact comparison
edges. With a fixed clock, `exp = now - 60s` is accepted and one nanosecond
earlier is rejected. `nbf = now + 60s` is accepted and one nanosecond later is
rejected. A future `iat` beyond 60 seconds is accepted if earlier than `exp`.
Equality of `iat` and `exp` is rejected at `Jwt` construction. This probe fed
instants directly to Spring to isolate its time comparisons from JSON rounding.

The same probe observed Nimbus parse the wire decimal `1792324800.123456789`
as Double `1792324800.1234567`. Nimbus rejects duplicate members, trailing JSON,
`NaN`, and `1e10000` in these probes, and parsed `1e-10000` as `0.0`. Existing
PR 10.3 tests document real Java receivers rounding fractional issuer output,
collapsing a one-nanosecond lifetime at a contemporary timestamp, or rounding
out of range near `Instant.MAX`. The PR 10.4 ticket explicitly requires
preserving fractional precision and rejecting nonfinite and overflow values.
The existing Python response JSON parser normally returns binary floats for
finite decimals, so its current wire-number behavior differs from that callback
requirement. Exact wire time, Spring comparison semantics and current Nimbus
representation quirks are distinct evidence.

### Java current-file overlap trust

`CallbackJwtTrust` takes its own public key and kid directly from `SigningKeySource`.
If overlap is absent, the initial snapshot contains that key and the trust
creates no scheduler and performs no reads. With overlap configured it loads and
validates synchronously before creating a daemon scheduler. Initial read errors
and validation errors throw category-specific safe startup diagnostics. The
property rejects blank or invalid explicit paths.

The reader validates strict UTF-8 and one JSON object with a nonempty `keys`
array. Each candidate must be RSA with a unique nonblank kid. Presence of any
of `d`, `p`, `q`, `dp`, `dq`, `qi`, or `oth` rejects the set, even when null.
Optional `use` and `alg` must equal `sig` and `RS256` if supplied. The modulus
and exponent use unpadded Base64URL and unsigned decoding. The modulus has at
least 2048 bits and is odd. The exponent is odd, at least 3 and less than the
modulus. Java constructs an RSA public key after these checks. An overlap
candidate with the own kid is accepted only when its public key is equal to
the startup key. No thumbprint recomputation is required for a supplied overlap
kid. The reader does not use extra metadata such as an X.509 chain to pick keys.

A fixed-delay one-second poll reads current bytes. Java avoids revalidating
identical bytes but does not trust file metadata to detect content changes.
A miss can trigger a synchronous reload guarded by the same monitor. One
monotonic attempt timestamp limits unknown-kid refresh across the entire trust
instance, irrespective of the kid. Known kids can take the current snapshot
without waiting for this monitor. Each publication replaces a volatile immutable
snapshot after validating and merging the full candidate. Unavailability or
invalidity publishes an empty snapshot including removal of the own key.
Correction restores own plus the current file's keys. Removing a key does not
keep it in historical trust. The startup issuer remains able to sign while a
receiver rejects new authentication during withdrawal.

Runtime category transitions to unavailable, invalid and ready produce fixed
log messages. Repeated failures in one category stay quiet, and a valid-to-valid
change does not produce a restoration message. `close` marks trust closed and
shuts down its scheduler. It serializes with reload, prevents new reloads and
does not rewrite previously acquired immutable snapshots. PR 10.4 explicitly
requires integration to start work rather than doing so at import or settings
construction. Java starts at bean initialization, and its synchronous miss
path is not an async I/O model.

## Dependencies and Operational Constraints

- The Python SDK already directly declares `cryptography>=48,<49`,
  `anyio>=4.16,<5`, and `simplejson>=4.2,<5` in `sdks/python/pyproject.toml`.
  Signing uses `cryptography` RSA PKCS#1 v1.5 with SHA-256. Existing async
  transport uses AnyIO and pytest is available through the dev requirements.
- The standalone Java SDK reactor targets Java 21 and enforces its dependency
  boundary in `sdks/java/pom.xml`. Its core pins Nimbus 10.10 and the starter
  imports Spring Boot 4.1.0 dependency management. A Java SDK fixture can be
  exercised locally without running a Sidecar server or external service.
  Existing root Sidecar verification uses the local Framework snapshot and
  remains separate from the standalone SDK reactor. The matching local
  Framework `docs/quickstart-executors.md:94-97,153-156` shows the supported
  `ai.loomspan.api` execution boundary, upstream of callback JWT reception.
- The local host reports Maven 3.9.6 with Java 21.0.2 via `JAVA_HOME`, Windows
  x86-64 CPython 3.13 through `py`, and Windows `uv`. Ubuntu WSL is available
  on x86-64. Prior PR 10.3 records list a WSL `uv` path that still exists as of
  this scan. Stage 1 did not run the project suites or recertify either platform.
  Full CPython/platform support evidence is assigned to PR 10.6.
- No operator keys, live services, data resets, sync or publication are involved.
  Poll/read synchronization has a local filesystem boundary. Java `close`
  acquires the same monitor as the read, so its source does not imply a deadline
  for an operating-system read that never returns.

## Open Questions

- The Python lifecycle and verifier interface, including how PR 10.5 consumes
  the startup issuer's public-only trust inputs, remains an implementation
  planning decision. The ticket does not select a public extension point.
- The existing tests distinguish Java receiver rounding from its underlying
  timestamp comparisons. PR 10.4 test planning owns how to prove exact Python
  precision, Java-compatible comparison/type behavior and actual Java issuance
  without treating incidental binary-float rounding as the wire contract.
- The lifecycle tests need an observable definition of bounded shutdown and
  miss handling during a local read. Existing Java synchronization supplies the
  normal behavior but does not establish Python cancellation or offload safety.
