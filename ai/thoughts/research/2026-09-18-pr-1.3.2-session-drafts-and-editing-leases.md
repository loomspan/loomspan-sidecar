# Session Drafts and Editing Leases Research

## Research Question

How do the existing management sessions, configuration drafts, snapshot storage, and runtime publication work, and where are their current authorization, lifecycle, and concurrency boundaries?

## Summary

Management already uses authenticated server sessions with a separate CSRF-protected security chain, role authorities, account-version checks, and a 30-minute effective idle clock. Drafts are currently independent in-memory objects whose caller supplies a snapshot; they have no session or tab owner and no HTTP operations. `RuntimeConfigurationService` tracks runtime-published identity separately from SQLite's intended pointer and serializes publication, but its current lock encompasses preparation through pruning; no draft or lease invalidation is connected to successful publication.

## Current Behavior and Data Flow

### Management identity and sessions

- The management filter chain matches `/management/**` and `/api/management/**`, permits setup/login/recovery paths, requires `MGT_ADMIN` for account routes, and authenticates every other management request. Its form login marks activity on success; logout invalidates the HTTP session. A second JWT chain handles `/v1/**` statelessly with CSRF disabled (`ManagementSecurityConfiguration.java:48-79`, `JwtSecurityConfiguration.java:88-105`).
- The principal carries database account ID, email, role, and account version. `viewer` has `MGT_VIEWER`; `editor` also has `MGT_EDITOR`; `admin` also has `MGT_ADMIN` (`ManagementUserDetailsService.java:17-53`). Account changes and password changes increment the version in storage, so the guard rejects old principals on a later request (`ManagementSessionGuard.java:24-37`, `ManagementIdentityService.java:126-159`).
- For authenticated management requests, the guard reads `management.activity` from the session and invalidates it when the account is absent/inactive, its version differs, the mark is missing, or the elapsed time reaches `sessionIdleTimeout` (`ManagementSessionGuard.java:24-37`). The mark is set on successful login and explicit `POST /api/management/session/activity`; ordinary GET/polling does not mark it (`ManagementSecurityConfiguration.java:59-63`, `ManagementController.java:51-69`). The configured default is `30m`, validated positive (`SidecarManagementProperties.java:9-17`, `application.yml:13-16`).
- The session API exposes principal identity, authorities, and a CSRF token. Unsafe requests are subject to the management chain's Spring CSRF behavior. API logout and both password-change paths invalidate the current session; other affected sessions are invalidated on their next guarded request (`ManagementController.java:51-69`, `ManagementController.java:99-103`, `ManagementPagesController.java:93-100`). A source search found no `HttpSessionListener` or session-destruction hook in current production code. No existing session state holds drafts or leases.
- Management responses receive `Cache-Control: no-store` and `Referrer-Policy: no-referrer` (`NoStoreResponseFilter.java:14-26`). This is response-cache protection, distinct from server-side draft privacy.

### Authored content and validation association

- `ConfigurationDraft` accepts a caller-provided `ConfigurationSnapshot`, captures its local UUID and complete `ManagedConfiguration`, and exposes synchronized replacement, freeze, validation recording, and validation lookup (`ConfigurationDraft.java:7-54`). Replacement creates a new `FrozenConfigurationCandidate` and clears validation even if content compares equal. A late result attaches only if its candidate is the same object as the current candidate (`ConfigurationDraft.java:25-54`). There is no public draft ID, candidate token, session association, or owner check in this model.
- `ManagedConfiguration` copies its skill-document list, requires distinct nonblank source labels and non-null YAML/REST text, and does not parse or resolve the authored text (`ManagedConfiguration.java:10-29`). `FrozenConfigurationCandidate` holds the base UUID and immutable content reference (`FrozenConfigurationCandidate.java:7-27`). `ConfigurationValidationResult` copies supplied issues (`ConfigurationValidationResult.java:6-14`).
- Internal `RuntimeConfigurationService.validate` freezes one candidate, calls framework `prepare`, prepares REST resources, checks route/catalog agreement, releases temporary resources, and records the result on the draft (`RuntimeConfigurationService.java:111-129`, `RuntimeConfigurationService.java:214-226`). There is currently no public validation endpoint. Matching local framework documentation says `SkillReloader.validate(completeDocuments)` gives editor feedback without candidate activation or staging; Sidecar currently uses the older preparation-based path (`C:/opendev/code/loomspan-framework/agent-skills/loomspan-docs/references/java-api/skill-reload.md:8-25`). PR 1.3.3 owns the public validation workflow.

### Runtime publication and durable selection

- Startup reads `ConfigurationSnapshotStore.current()` (the SQLite-selected snapshot), prepares and stages it, publishes to the framework, assigns `publishedId`, records `PUBLISHED`, prunes history, then opens execution dispatch (`RuntimeConfigurationService.java:64-108`). On normal publication, `publishedId` is the service's runtime identity, while `store.current()` is the intended pointer and may diverge during an attempt or after a fault (`RuntimeConfigurationService.java:131-212`).
- `publish(draft)` acquires one fair `ReentrantLock` before health, validation, and base checks; freezes the accepted candidate; prepares and stages resources; submits B to SQLite as intended production; then calls framework `reloader.publish(prepared)` (`RuntimeConfigurationService.java:45-50`, `RuntimeConfigurationService.java:131-164`). It currently holds that lock for the entire preparation and failure/success handling. The lock is private to this service and no draft/lease operation joins it.
- A commit failure leaves runtime A and discards staging. A framework-publication failure discards staging and attempts pointer reversion; successful reversion restores intended A, while failed reversion sets `mutationFault` with runtime still A. After successful framework publication, `publishedId` becomes B before status recording; status/pruning failure can set a mutation fault and `publish()` can throw even though B is running (`RuntimeConfigurationService.java:150-200`, `RuntimeConfigurationService.java:229-245`). `inspect()` returns runtime ID, intended ID/status, and fault, falling back to cached intended values if inspection fails (`RuntimeConfigurationService.java:202-212`).
- `ConfigurationSnapshotStore.current()` reads only the selected SQLite pointer under a transaction. `submit` compares the expected selected ID and changes the pointer in one transaction; `revert` restores a predecessor and marks rejected B failed (`ConfigurationSnapshotStore.java:56-107`). `prune` protects selected and caller-provided IDs (`ConfigurationSnapshotStore.java:120-141`). Runtime pruning adds the `publishedId` and IDs of live REST generations (`RuntimeConfigurationService.java:237-241`, `GenerationRestResources.java:81-87`). `ConfigurationSnapshotRepository` persists ordered complete YAML documents and REST text and reconstructs them by sequence (`ConfigurationSnapshotRepository.java:22-85`).
- Framework reload documentation states a successful `publish` activates the frozen candidate while old admitted/running work retains its captured generation; listeners can be selected before return and do not provide durable history (`C:/opendev/code/loomspan-framework/agent-skills/loomspan-docs/references/java-api/skill-reload.md:42-62`). Sidecar's execution dispatch uses the generation-to-snapshot resource mapping; a management lease is not currently part of execution admission (`GenerationRestResources.java:63-86`).

## Open Questions

- The ticket requires status and draft identity for later UI/publication responses, but no current draft/lease HTTP representation exists. Exact request/response fields and error mapping are therefore planning decisions.
- The ticket requires cleanup on session destruction, account-triggered invalidation, and restart. Current invalidation uses several `HttpSession.invalidate()` call sites and lazy account-version checks; there is no existing destruction callback or registry to observe a session that has made no later request.
- Current publication captures only a runtime UUID in memory and loads authored text through the intended-pointer store. The code has no operation that atomically reads the complete runtime-published snapshot while publication/pruning is in progress.
