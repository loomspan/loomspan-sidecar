# Management Accounts and Email Recovery Research

## Research Question

What management authentication, persistence, HTTP, configuration, deployment and test behavior exists before PR 1.3.1, and where does the requested account and email recovery behavior intersect it?

## Summary

The application currently has one servlet security chain. It disables CSRF, uses stateless sessions, permits the framework observability path and health paths, requires a JWT for `/v1/**`, and denies other requests (`src/main/java/ai/loomspan/sidecar/security/JwtSecurityConfiguration.java:86-103`). No local management account, form-login, password, recovery-token, SMTP, or management-session implementation is present in `src/main/java` or `src/main/resources`. The existing SQLite database holds managed configuration snapshots; its initialization flag is about configuration only (`src/main/resources/db/migration/V1__configuration_snapshots.sql:23-30`, `src/main/java/ai/loomspan/sidecar/storage/ConfigurationSnapshotStore.java:34-53`).

## Current Behavior and Data Flow

1. `LoomspanSidecarApplication` enables the execution, JWT, routes, storage and snapshot property classes; no management property class is enabled (`src/main/java/ai/loomspan/sidecar/LoomspanSidecarApplication.java:12-14`). The application YAML sets the SQLite path, snapshot settings, JWT defaults and execution defaults. It disables Boot's automatic Flyway integration (`src/main/resources/application.yml:8-30`).
2. `StorageConfiguration` creates a file-backed SQLite data source with foreign keys, a 5-second busy timeout, WAL journaling and FULL synchronous mode. It rejects an existing file without Flyway history and verifies pragmas (`src/main/java/ai/loomspan/sidecar/storage/StorageConfiguration.java:60-93`). Its `storageFlyway` bean calls `migrate()` and `validate()`; the snapshot repository bean depends explicitly on that bean, so snapshot repository use follows migration (`:32-42`, `:112-117`). A Spring `DataSourceTransactionManager` and `TransactionTemplate` back the snapshot store (`:44-57`).
3. Flyway V1 creates snapshot content, skill-document, status and store-state tables. `configuration_store_state.initialized` starts at zero (`src/main/resources/db/migration/V1__configuration_snapshots.sql:1-30`). `ConfigurationSnapshotStore.initialize()` creates/selects an empty authored configuration on first use and resumes the selected snapshot on later starts (`src/main/java/ai/loomspan/sidecar/storage/ConfigurationSnapshotStore.java:34-53`). This state is not an account-bootstrap marker.
4. The single `SecurityFilterChain` applies stateless JWT resource-server authentication, disables CSRF, and denies unmatched requests (`src/main/java/ai/loomspan/sidecar/security/JwtSecurityConfiguration.java:86-103`). The JWT decoder verifies timestamp, issuer, audience and required claims; role authorities use the configured claim and prefix (`:34-78`). `GrantedAuthorityDefaults` uses that same configurable prefix (`:81-84`). There is no configured form login, logout, session repository, or CSRF token endpoint.
5. `/v1/skills` reads the active framework catalog, while `/v1/skills/{name}/executions` and `/v1/executions/{id}` use `JwtAuthenticationToken`; execution admission captures the JWT and owner identity (`src/main/java/ai/loomspan/sidecar/api/SkillCatalogController.java:12-25`, `src/main/java/ai/loomspan/sidecar/api/ExecutionController.java:25-56`). The execution coordinator carries the JWT into workers (`src/main/java/ai/loomspan/sidecar/execution/ExecutionCoordinator.java:113-123`, `:171-173`); caller-passthrough REST routes require a JWT authentication in the worker security context (`src/main/java/ai/loomspan/sidecar/rest/GenericRestSkillHandler.java:47-52`).
6. A highest-precedence servlet filter sets `Cache-Control: no-store` on responses (`src/main/java/ai/loomspan/sidecar/api/NoStoreResponseFilter.java:14-22`). The existing API exception handler returns problem details containing exception messages for specified execution errors (`src/main/java/ai/loomspan/sidecar/api/ApiExceptionHandler.java:13-44`). There is no management-specific error mapping or account data serialization to inspect yet.
7. The distinct `management.server.port: 9091` setting is for Actuator. The exposed endpoint list is health only (`src/main/resources/application.yml:32-42`). The framework observability namespace is separately protected by its API-key filter when enabled; the current Sidecar chain permits that namespace to reach the framework filter (`src/main/java/ai/loomspan/sidecar/security/JwtSecurityConfiguration.java:92-96`, `src/test/java/ai/loomspan/sidecar/security/ConsoleSecurityIntegrationTest.java:41-53`). The ticket's browser/account management routes are not present.

## Dependencies and Operational Constraints

The app is on Java 21, Spring Boot 4.1.0 and the locally installed `ai.loomspan:loomspan-spring-boot-starter:1.0.0-beta.5-SNAPSHOT` (`pom.xml:12-19,39-44`). SQLite is configured for a single local database with WAL, FULL durability, foreign keys and a 5-second busy timeout (`StorageConfiguration.java:60-92`); README cautions against sharing it across replicas or a network filesystem (`README.md:182-189`). The Actuator port is a separate health surface, while the application HTTP port is the existing execution and observability surface (`README.md:376-389`). The current checked-in YAML and deployment examples have no SMTP/server mail values (`src/main/resources/application.yml:1-42`, `examples/kubernetes/deployment.yaml:26-44`). Research did not contact external identity, mail or model services.
