# Snapshot Recovery and History Research

## Research Question

How does the checked-out Sidecar store complete authored snapshots, choose its current snapshot on reopen, and handle status and startup today? What test and deployment evidence exists for the ticket's recovery, retention, and backup requirements?

## Summary

PR 1.1.1 left a file-backed SQLite store with one durable current pointer, immutable authored content, a separate mutable publication status, and transactional first-store initialization. Subsequent `submit` calls append pending history without changing that pointer. There is no A-to-B submission/reversion operation, retention pruning, backup procedure, or runtime-generation mapping in the current code. Spring constructs the store after Flyway migration and calls `initialize`, but mounted skill and REST configuration still drive runtime activation.

## Current Behavior and Data Flow

1. `LoomspanSidecarApplication` enables `SidecarStorageProperties` alongside other configuration properties (`src/main/java/ai/loomspan/sidecar/LoomspanSidecarApplication.java:11-18`). The default DB path is `/sidecar/data/sidecar.db` (`src/main/java/ai/loomspan/sidecar/config/SidecarStorageProperties.java:5-21`; `src/main/resources/application.yml:9-12`).
2. `StorageConfiguration` creates a SQLite data source, rejects an existing empty/unmigrated DB, applies connection foreign keys, WAL, synchronous FULL, and a five-second busy timeout, then migrates and validates with Flyway (`src/main/java/ai/loomspan/sidecar/storage/StorageConfiguration.java:58-115`). The repository bean depends on the Flyway bean; the store bean calls `initialize()` (`:31-55`).
3. V1 has snapshot header/content rows, ordered skill-document rows, separate status rows, and one `configuration_store_state` row with `initialized` and `current_snapshot_sequence` (`src/main/resources/db/migration/V1__configuration_snapshots.sql:1-30`). A new snapshot is inserted with a fresh local UUID, optional source UUID, sequence, complete REST YAML and ordered skill YAML, plus `pending` status (`src/main/java/ai/loomspan/sidecar/storage/ConfigurationSnapshotRepository.java:22-46`). SQL triggers reject updates to authored header or skill content, while FK cascades cover deletion (`V1__configuration_snapshots.sql:9-20,32-42`).
4. On a fresh migrated DB, `initialize()` transactionally inserts one empty snapshot and sets the pointer. If an uninitialized store already has content, or an initialized one has no current pointer, it throws. On reopen it reads the pointer's sequence and requires that snapshot (`src/main/java/ai/loomspan/sidecar/storage/ConfigurationSnapshotStore.java:22-41`). `current()` repeats the pointer read inside a transaction (`:44-54`). There is no status filter in that selection.
5. Repository loading fetches header/status and ordered documents. Missing header/status, document-count mismatch, or a gap in ordinals causes failure; `ManagedConfiguration` then checks nulls, unique nonblank labels and non-null YAML (`src/main/java/ai/loomspan/sidecar/storage/ConfigurationSnapshotRepository.java:56-85`; `src/main/java/ai/loomspan/sidecar/storage/ManagedConfiguration.java:10-28`). Raw authored YAML is retained without parsing or placeholder resolution. `SnapshotStatus` maps database strings to pending/published/failed (`src/main/java/ai/loomspan/sidecar/storage/SnapshotStatus.java:3-15`).
6. `submit(configuration, sourceId)` only checks `initialized` then inserts a pending snapshot inside a transaction; it does not change current (`src/main/java/ai/loomspan/sidecar/storage/ConfigurationSnapshotStore.java:56-65`). `updateStatus(localId, status)` is a separate transaction and does not change content or pointer (`:72-75`; repository `:88-98`). `findByLocalId` returns null for an absent header (`repository :49-54`). There is no compare-with-expected-current update, pointer reversion, history list, or pruning query in these store/repository classes.
7. The store currently is not read by the execution or REST code: searches for `ConfigurationSnapshotStore` references found its bean and storage tests, and no production consumer beyond `StorageConfiguration`. `application.yml` still supplies mounted skill locations and a mounted REST-route path (`src/main/resources/application.yml:1-12`); README explicitly says mounted files supply runtime skills/routes until Phase 2 (`README.md:99-107`). A DB pointer read therefore does not establish an execution's runtime generation or its export source.

## Affected Areas

| Area | Current behavior and evidence |
| --- | --- |
| Intended production | One `current_snapshot_sequence` FK exists. Only first-store initialization writes it (`V1__configuration_snapshots.sql:23-30`; `ConfigurationSnapshotRepository.java:117-126`). |
| Publication status | Insert starts `pending`; status update is independent bookkeeping. Status is not consulted when choosing current (`ConfigurationSnapshotRepository.java:43-46,88-98`; `ConfigurationSnapshotStore.java:44-54`). |
| Content integrity | Header records document count; loader checks count and ordinal sequence. SQLite constraints and `ManagedConfiguration` enforce additional shape, and database triggers reject in-place content updates (`ConfigurationSnapshotRepository.java:56-85`; `V1__configuration_snapshots.sql:1-42`). |
| Startup/load failures | Existing empty DB or missing migration history is rejected before migration; Flyway migrates/validates; selected snapshot reconstruction errors propagate from `initialize()` and bean creation (`StorageConfiguration.java:58-115,49-55`; `ConfigurationSnapshotStore.java:22-41`). |
| Retention | Submission sequence exists for ordering, but there is no prune operation or `loomspan-sidecar.snapshots.max-retained` setting (`V1__configuration_snapshots.sql:1-3`; `ConfigurationSnapshotStore.java:1-76`; `application.yml:9-26`). |
| Runtime boundary | Mounted sources remain the current runtime inputs; no snapshot-to-generation mapping or publication coordinator consumes the store (`application.yml:1-12`; `README.md:99-107`). |
| Deployment/backup | README requires a writable persistent local filesystem, single instance, and preservation of WAL files; it warns that copying only a live main DB is unsafe but defers operator backup/recovery steps (`README.md:133-142`). Compose mounts `sidecar-data:/sidecar/data` (`examples/quickstart/compose.yaml:32-46`); Kubernetes mounts a PVC there with `fsGroup: 10001` (`examples/kubernetes/deployment.yaml:48-50,80-106`). |

## Historical Context

The PR 1.1.1 ticket assigned complete immutable storage to that unit and explicitly deferred restart selection, retention, and backup/recovery to PR 1.1.2 (`ai/thoughts/tickets/2026-09-17-pr-1.1.1-durable-configuration-snapshot-storage.md:89-92`). The management roadmap says the future publication coordinator commits B and the intended pointer together, while runtime publication happens afterward; status remains separate and pending history may be outcome-unknown (`ai/thoughts/phases/2026-09-16-management-console-roadmap.md:601-644`). It assigns runtime protection and post-attempt pruning to Phase 2, with a default ten-snapshot target (`:648-663`). The current ticket explicitly confines this unit to storage behavior and database backup/recovery evidence; Phase 2 owns runtime fault, dispatch gate, and retirement verification.

## Open Questions

- The ticket specifies a stopped-instance backup but leaves its concrete operator commands and test mechanism for planning.
- The ticket defines storage startup pruning without a live-generation registry. Its placement relative to the existing `initialize()` bean call and selected-content verification is an implementation detail for planning.
- The current loader's general error messages do not consistently identify the selected snapshot or recovery action; planning must interpret the ticket's actionable, secret-free diagnostic requirement.
