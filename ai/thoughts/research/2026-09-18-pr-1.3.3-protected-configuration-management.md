# Protected Configuration Management Research

## Research Question

What current Sidecar and public framework paths govern private drafts, validation, runtime publication, retained snapshots, management authorization, and their concurrency/failure behavior for PR 1.3.3?

## Summary

The checkout contains real management accounts, sessions, session-private drafts and a single editing lease, plus the Phase 2 durable runtime publisher. It has no management HTTP endpoints for configuration inspection, history, validation, or publication. Its internal draft validation still calls `SkillReloader.prepare()` and collapses skill failures to one generic issue; the matching local framework now exposes side-effect-free `validate(Collection<SkillDocument>)`, structured issues, and candidate names/kinds. The publication coordinator has the real fair serialization lock and a separate short transition lock shared with editing, but its existing `publish(ConfigurationDraft)` accepts only a draft reference and does not itself recheck the management account/session/tab/grant at admission.

## Current Behavior and Data Flow

### Account, session, and draft entry

`ManagementSecurityConfiguration` selects `/management/**` and `/api/management/**` with an ordered browser security chain, protects account routes with `MGT_ADMIN`, takeover with `MGT_ADMIN`, reads of editing status/draft with authentication, and editing mutations with `MGT_EDITOR` (`src/main/java/ai/loomspan/sidecar/management/ManagementSecurityConfiguration.java:33-83`). The default Spring Security CSRF behavior remains enabled for this chain. Its API entry point returns JSON 401 or 403. A separate stateless execution chain disables CSRF for JWT-authenticated `/v1/**` (`src/main/java/ai/loomspan/sidecar/security/JwtSecurityConfiguration.java:90-103`). The principal is populated with hierarchy `MGT_VIEWER`, then `MGT_EDITOR`, then `MGT_ADMIN` according to stored role (`ManagementUserDetailsService.java:44-52`).

`ManagementSessionGuard` checks current account activity/version and the effective 30-minute idle deadline on each request, invalidating a stale session; only explicit `report()` updates activity, with a 30-second minimum interval (`ManagementSessionGuard.java:25-68`). The session endpoint exposes identity, permissions, and CSRF token; explicit session activity and logout have separate endpoints (`ManagementController.java:51-69`). Account alteration clears affected editing state (`ManagementIdentityService.java:162-169`), and session destruction clears that session's state (`ManagementEditingSessionListener.java:9-18`).

Editing HTTP is under `/api/management/editing`: status, own draft, acquire/takeover, activity, release, save, and discard (`ManagementEditingController.java:37-91`). `Save` supplies `tabId`, `grantId`, `expectedCandidateId`, complete authored skill documents, and REST YAML. Current conflict and invalid-body handlers return 409 and 400 generic error maps (`ManagementEditingController.java:94-102`). No validation or Publish mapping exists there. A draft read is available to its own session regardless of tab, while writes check the current grant (`ManagementEditingService.java:39-59,97-109`).

`ManagementEditingService` gates editing through `RuntimeConfigurationService.withEditingState`, then synchronizes `ManagementEditingState` (`ManagementEditingService.java:39-145`). It checks live account version and active session, and writes check lease session, tab, grant ID, expiry, draft base and expected candidate ID (`ManagementEditingService.java:149-181`). Acquisition copies the runtime-published snapshot, not the intended database pointer (`ManagementEditingService.java:63-79`). `ManagementEditingState` stores session-keyed drafts and one instance lease in memory; clearing all removes both (`ManagementEditingState.java:11-53`). The draft wrapper reports `draftId`, `candidateId`, base ID, authored configuration and validation result (`ManagementEditingService.java:19-22,193-197`).

`ConfigurationDraft` maintains a frozen candidate object; replacing even equal content creates a new object and clears validation. It records late validation only if the exact candidate object remains current (`ConfigurationDraft.java:25-54`). `ManagedConfiguration` copies the document list, checks unique nonblank source labels, and retains YAML and REST text without parsing (`ManagedConfiguration.java:10-29`). The current result model has only `successful` and a list of issues with `sourceLabel`, `message`, and optional `location`; it has no severity, skill name, or explicit stale/discarded state (`ConfigurationValidationResult.java:6-14`, `ConfigurationValidationIssue.java:3-17`).

### Validation and REST resource checks

`RuntimeConfigurationService.validate(ConfigurationDraft)` freezes the draft, invokes `prepare(candidate.configuration())`, stages REST resources, records a boolean success/empty issues or one converted exception issue, releases staged REST resources, and attempts to attach the result to the still-current draft (`RuntimeConfigurationService.java:118-136`). `prepare()` delegates to framework `reloader.prepare(skillDocuments)` (`RuntimeConfigurationService.java:228-230`). Skill preparation exception conversion chooses an authored label only by scanning exception text and reports a generic `Skill preparation failed`; REST conversion either extracts one bracketed route location or reports generic client staging failure (`RuntimeConfigurationService.java:273-298`). The return value does not say whether the result attached after a concurrent edit.

`GenerationRestResources.prepare` parses authored REST YAML and creates target clients; the resource is tracked until released, staged, or retired (`GenerationRestResources.java:19-61,91-109`). The parser checks target/route shape, allowed URL variables and resolved URL, SSL bundle, auth, timeouts and path/input binding (`RestRouteLoader.java:60-157,173-306`). `RestRouteCatalogValidator` currently compares routes with a prepared `SkillCatalog`: each REST skill needs a route, route names must resolve to a REST skill, and target names must exist (`RestRouteCatalogValidator.java:11-35`). `RuntimeConfigurationService.stage` releases resources when that catalog check throws (`RuntimeConfigurationService.java:232-241`). Authored placeholders remain in the stored `ManagedConfiguration`; client preparation uses the resolved values only in temporary resources.

The matching local framework README and `agent-skills/loomspan-docs/references/skill-authoring/validation-workflow.md` describe `SkillReloader.validate(Collection<SkillDocument>)` for a complete replacement set, including empty sets. The public interface defines both validate and prepare overloads (`C:/opendev/code/loomspan-framework/src/main/java/ai/loomspan/api/SkillReloader.java:7-24`). `SkillValidationResult.valid()` is true without ERROR issues; error results have empty metadata while warning-only valid results retain full metadata (`SkillValidationResult.java:10-28`). Public issues have `severity`, `sourceName`, optional `skillName`, optional `fieldPath`, and `message` (`SkillValidationIssue.java:8-20`); `ValidatedSkill` has immutable exact name and `SkillKind` (`ValidatedSkill.java:6-15`). The local framework documentation states validation allocates no generation, does not stage or publish, and does not test target connectivity. These framework sources establish the available contract, not completed Sidecar integration.

### Publication, reads, and history

Startup acquires the fair `publication` lock, reads SQLite's current intended snapshot, prepares/stages it, publishes, then records `PUBLISHED`, prunes, and opens execution dispatch (`RuntimeConfigurationService.java:71-115`). `published` is the runtime record. `publish(ConfigurationDraft)` takes the same fair lock before checking health, exact validation and runtime base; it prepares and stages afresh, submits a pending snapshot and intended pointer in one database transaction, then publishes under the shorter `transition` lock and clears all editing state in the same transition (`RuntimeConfigurationService.java:138-178`). Editing uses that transition lock but remains possible during preparation (`RuntimeConfigurationService.java:257-267`). A caller queued for `publication` has not yet passed the existing base/validation checks, but this method has no management identity or grant inputs.

If precommit preparation or staging fails, no submitted history is created. A commit failure discards unpublished resources. A framework publication failure discards resources, attempts a transactional revert to predecessor and marks B failed; failed revert sets `mutationFault` and leaves intended B. After successful framework publication, `published` becomes B and editing is cleared before status recording; failed status recording sets mutation fault while B remains running and intended (`RuntimeConfigurationService.java:150-210`). The method returns a reloaded snapshot on success and throws `IllegalStateException` for several distinct stages. Pruning failure also sets a mutation fault (`RuntimeConfigurationService.java:243-249`). `inspect()` reads intended from SQLite, returns published/intended IDs, intended status, fault, and on read failure falls back to cached intended fields while faulting mutations (`RuntimeConfigurationService.java:216-225`). There is currently no protected HTTP representation of that inspection or the full runtime content.

`ConfigurationSnapshotStore.submit` guards the expected intended pointer, inserts immutable content and pending status, then changes the pointer in one transaction; `revert` switches the pointer and records failure in one transaction (`ConfigurationSnapshotStore.java:72-108`). `findByLocalId` reads a retained snapshot or null (`ConfigurationSnapshotStore.java:110-113`). Prune removes oldest unprotected rows beyond the configured count and protects current selection (`ConfigurationSnapshotStore.java:120-141`). The repository has `snapshotIdsOldestFirst()` for pruning but no public history listing with content; `requireBySequence` reads header/status and documents in separate queries (`ConfigurationSnapshotRepository.java:49-86,117-126`). The schema assigns monotone `submission_sequence`, local and optional source IDs, immutable authored text/document rows, and mutable status (`src/main/resources/db/migration/V1__configuration_snapshots.sql:1-40`). `ConfigurationSnapshot` exposes all those fields (`ConfigurationSnapshot.java:7-19`). Runtime pruning protects staged/live generation IDs and current published ID (`RuntimeConfigurationService.java:251-255`), while `GenerationRestResources` retains generation-to-snapshot mappings until retirement (`GenerationRestResources.java:63-105`). A retained execution snapshot ID does not itself pin history.

## Open Questions

- The ticket leaves exact URI, payload, status and error response contracts for planning; existing editing/account HTTP style supplies nearby precedent.
- Current history load uses multiple repository queries, and the store lacks a listing method. Planning must account for consistency of full snapshot reads against concurrent pruning/publication; this research does not infer an existing transaction-level guarantee beyond the shown store methods.
- `RuntimeConfigurationService.inspect()` reads SQLite without the publication/transition lock and reports only the intended row's stored status. The requested current runtime content and stable cross-field management read require explicit analysis in planning.
- The current publisher conflates several thrown `IllegalStateException`s at its public method boundary. Planning needs to preserve the distinct observed activation/bookkeeping outcomes through HTTP without inventing a past outcome for pending history.
