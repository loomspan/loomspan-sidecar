# Durable Configuration Snapshot Storage Implementation Plan

## Overview
- Ticket: `ai/thoughts/tickets/2026-09-17-pr-1.1.1-durable-configuration-snapshot-storage.md`
- Research: `ai/thoughts/research/2026-09-17-pr-1.1.1-durable-configuration-snapshot-storage.md`
- Outcome: Store and reopen complete, immutable authored skill and REST configuration in one file-backed SQLite database, with an atomic empty initial current snapshot.

## Current State

`application.yml` points framework discovery at mounted skill YAML and `RestRouteLoader` at one mounted route YAML. The loader resolves placeholders and builds runtime objects, so `RestRouteConfiguration` cannot recover authored text. There is no database, migration, snapshot identity or current pointer in `pom.xml` or application configuration. `SupportedLoomspanApiArchitectureTest` already enforces the closed framework API. The checkout contains pre-existing developer edits listed in the research document; preserve them while editing overlapping files.

## Desired End State

A storage service can write and retrieve one complete configuration consisting of an ordered collection of `SkillDocument` diagnostic labels and exact YAML text plus one exact authored REST YAML document. Empty skills with `targets: {}\nroutes: {}\n` is a valid initial content set. Every persisted snapshot gets a fresh UUID local ID, nullable source UUID provenance, and monotonically allocated SQLite submission sequence. Its content is immutable; status (`pending`, `published`, `failed`) is separately mutable. A singleton initialized/current record references one snapshot. On a fresh migrated store, application initialization atomically creates one empty pending snapshot and sets the intended current pointer and initialized flag. Reopen preserves it and fails closed on inconsistent state. This ticket does not activate the framework generation; Phase 2 owns that integration.

The logical transfer contract reuses this authored content boundary. A future bundle envelope carries integer `formatVersion: 1`, source identity and informational producer application/framework versions. The destination allocates a new local ID, and imported status never proves local publication. Phase 5 will define archive layout, integrity and import/export operations.

## Active Project Guardrails

- Follow `ai/thoughts/design-lens.md`: smallest complete implementation; no speculative compatibility layer; framework remains the skill-validation/execution authority. Sidecar stores authored bytes and uses only `ai.loomspan.api.SkillDocument` for framework-dependent model types.
- Preserve existing execution, identity and shutdown authority. Storage must not claim to publish a runtime generation.
- Per ticket pipeline note, intermediate mounted-file startup and broad context tests can remain blocked until Phase 2. Record these failures explicitly rather than adding temporary bridges.

## Impact and Risk Analysis

- Exact authored text is necessary: current REST parsing resolves `${NAME}` and loses spelling, comments and literal values. Persist the raw route YAML string, not `RestRouteConfiguration`, and copy caller collections on input/output. Do not log stored text because it may contain secrets.
- SQLite transactions cover the multirow snapshot insert and first pointer, but do not cover framework publication. A foreign key and startup consistency check prevent an absent or incomplete current snapshot from being silently reseeded.
- Local SQLite files need writable parent directory, database and `-wal`/`-shm` side files. WAL relies on reliable local filesystem locking; use one owning Sidecar instance, no shared network volume or replica access. A finite busy timeout reports contention rather than waiting indefinitely.
- Migration must complete and validate before any repository read, initialization or write. Only V1 is supported in this ticket; no upgrade path from a previously released Sidecar database is claimed.
- Existing `README.md`, quickstart and Kubernetes examples describe read-only mounts. Add a separate writable data directory/volume while retaining legacy mounted files until Phase 2 replaces runtime loading. Do not imply that storage tests prove runtime activation.

## Implementation Approach

Use a dedicated `ai.loomspan.sidecar.storage` package. Represent content with a defensive-copy `ManagedConfiguration` value object (`List<SkillDocument>`, `String restRoutesYaml`) and a `ConfigurationSnapshot` carrying local UUID, optional source UUID, sequence, content and status. Reject null collection/elements/YAML/REST text and blank or exactly duplicate diagnostic labels before writing; allow an empty skill list. Preserve document order using `ordinal`; compare labels exactly, including case. A snapshot write always inserts new rows and never updates content. Read methods reconstruct detached immutable values.

V1 SQL tables: `configuration_snapshot` (integer primary key submission sequence, unique UUID local ID, nullable source UUID, document count and non-null authored REST YAML), `configuration_skill_document` (snapshot foreign key with cascade, ordinal, unique label per snapshot, non-null label/YAML), `configuration_snapshot_status` (snapshot foreign key/primary key, constrained status), and singleton `configuration_store_state` (fixed key, initialized flag and nullable current snapshot FK). The document count detects missing rows on reopen; triggers prevent content updates while allowing later pruning through deletes. Flyway inserts only the uninitialized singleton reference row. The application transaction inserts the canonical empty snapshot, its pending status, points state to it and flips initialized to true. A reopened uninitialized store is acceptable only when there are no snapshots and no pointer, allowing retry after a rolled-back initialization; any other mismatch fails. An initialized store must point to one complete readable snapshot. Use `UUID.randomUUID()` for local IDs; the SQLite integer key is solely submission order and foreign-key linkage. Source UUID never selects or overwrites local content.

Configure one SQLite-only `DataSource` for `loomspan-sidecar.storage.database-path` (default `/sidecar/data/sidecar.db`), a filesystem path rather than arbitrary JDBC URL. Create/check its parent directory before first connection. Configure each connection with `foreign_keys=ON`, `busy_timeout=5000`, `journal_mode=WAL`, `synchronous=FULL`; verify actual PRAGMA values, including WAL support, at startup. Use SQLite's JDBC datasource or a small datasource wrapper if needed to apply connection-local PRAGMAs; do not add a generic pool or engine layer. Run a single Flyway migration/validation path before exposing the repository, and use `NamedParameterJdbcTemplate` plus `DataSourceTransactionManager`/Spring `@Transactional` for application writes. A second Flyway auto-runner must be disabled if explicit migration configuration is used. Compare available dependency support during implementation and pin SQLite/Flyway modules as needed; use the local beta 5 framework artifact.

The alternative of JSON-serializing a whole snapshot into one row would make exact content easy but remove useful database constraints on labels and make partial-write/rollback and ordered-document behavior harder to inspect. The four small tables support required integrity without a generic persistence layer. The alternative of parsing/reserializing REST routes loses authored placeholders and literal sensitive values, so preserve one raw YAML document.

## Test Strategy

Start with a failing real-SQLite test that writes a complete snapshot, closes its datasource and reopens the same file to compare exact document labels/YAML and raw REST YAML including `${NAME}` and literal sensitive text. Add cheaper focused constructor validation tests only where they prove caller-mutation isolation. Use temp directories and separate datasource lifetimes for restart evidence. Force a failure after snapshot row insertion to verify transaction rollback; inspect all relevant tables, not merely an exception. Lock one SQLite write transaction on a separate connection to exercise the configured finite busy timeout. Corrupt singleton/pointer using a direct test connection to prove fail-closed startup. Verify V1 fresh migration and Flyway validation failure; no upgrade test is needed because V1 is the only explicitly supported schema. The detailed tests are in the companion testing plan.

## Risks and Rollback/Recovery

No development database migration is promised. If this V1 schema fails during development, discard only a disposable development database and recreate it; production restoration/backup policy is PR 1.1.2. A partially initialized but migrated database retries only when the singleton says uninitialized and has no content/pointer. Any inconsistent or unsupported database fails startup without reseeding. SQLite WAL files must stay with the database; copying only the main file while live is not a safe backup. Runtime integration and release verification remain blocked until the later tickets and framework publication.

## Implementation verification note (2026-09-17)

The four-table V1 migration includes a stored document count so startup can detect missing document rows, and update triggers protect authored snapshot content while status remains mutable. The Dockerfile creates `/sidecar/data` with UID/GID 10001 ownership so a new named volume can inherit writable permissions. Flyway's SQLite support is present in `flyway-core`; no separate SQLite Flyway module is published in the dependency management used here. The real SQLite, configuration-reference and ArchUnit focused classes pass with `.\mvnw.cmd -B -ntp '-Dtest=ConfigurationSnapshotRepositoryTest,ConfigurationSnapshotStoreTest,ConfigurationReferenceTest,SupportedLoomspanApiArchitectureTest' surefire:test` (12 tests). The ticket Pipeline notes place that integration adjustment in later Phase 2 work; no temporary bridge was added. Thus the exact planned lifecycle commands remain unverified, and the direct Surefire invocation is narrower evidence after the compiler emitted the focused test classes.
