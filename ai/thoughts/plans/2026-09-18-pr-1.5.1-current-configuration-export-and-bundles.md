# Current Configuration Export Implementation Plan

## Overview
- Ticket: `ai/thoughts/tickets/2026-09-18-pr-1.5.1-current-configuration-export-and-bundles.md`
- Research: `ai/thoughts/research/2026-09-18-pr-1.5.1-current-configuration-export-and-bundles.md`
- Outcome: Authenticated management users download the captured running configuration in a bounded, verified format 1 ZIP; a non-mutating reader prepares for later import.

## Current State
`RuntimeConfigurationService.published` is the running snapshot; `current()` additionally reads intended database state. `ManagedConfiguration` holds exact skill YAML and REST YAML. Management GET endpoints use authenticated session security. The current console page has no export control.

## Desired End State
A captured immutable published snapshot supplies only authored configuration to a deterministic archive. No database selection, history, draft, editing lease, or execution state changes. Missing runtime state and oversize content produce safe errors. Reader validates format and content without activation.

## Scope
### In scope
- Export endpoint, console download and notice, format 1 writer/reader, fixtures, tests, documentation.
### Out of scope
- Import, activation, rollback, signing, deployment settings, compatibility formats, release switching.

## Active Project Guardrails
Use the simplest complete design; only supported Loomspan API types. The framework remains skill execution authority; reader performs structural parsing only.

## Impact and Risk Analysis
ZIP input and decompression require actual-byte bounds, complete inventory and path checks. Export must capture `published` atomically without consulting intended state. Sensitive authored text must be downloaded only through management authentication and never logged. Export storage should avoid an extra archive copy.

## Implementation Approach
Add `ConfigurationBundleV1` as one writer/reader with fixed limits. Layout: `manifest.json` has integer `formatVersion`, `sourceSnapshotId`, `producer` (`sidecarVersion`, `frameworkVersion`), and `payloads` array with `{path,sha256,sourceLabel?}`; `rest.json` contains `{restRoutesYaml}`. Exact field names and types are documented as JSON Schemas at `src/test/resources/fixtures/bundles/v1/manifest.schema.json` and `rest.schema.json`, alongside a complete unpacked format fixture. Skill paths are generated `skills/00000.yaml` style; labels remain metadata only. Every non-manifest ZIP entry appears exactly once in inventory. Reader rejects unknown JSON fields, malformed structure, unsafe names, duplicate labels/entries, non-UTF-8, invalid YAML document structure, checksums, unsupported versions, and excessive actual bytes. It never extracts. Writer stages to a temporary ZIP file and checks both expanded and compressed sizes before returning it for HTTP streaming.

## Test Strategy
Use unit-crafted ZIPs for reader failures and a local Spring server for session enforcement and runtime capture. Browser test checks visible notice and download. Exercise limits with synthetic content and misleading metadata, without live services.

## Acceptance-Criteria Traceability
| Acceptance criterion | Planned code evidence | Planned test evidence |
| --- | --- | --- |
| Exact runtime, roles, empty/absent, no state change | capture API, endpoint | HTTP and runtime tests |
| Fidelity and exclusions | bundle writer | round-trip and fixture tests |
| Reader rejection and version independence | bundle reader | invalid archive matrix |

## Risks and Rollback/Recovery
No persistent schema change; revert this feature to remove endpoint and reader. Existing stopped-instance database backup remains the full installation recovery method.
