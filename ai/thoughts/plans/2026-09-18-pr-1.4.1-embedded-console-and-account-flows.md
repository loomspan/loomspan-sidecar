# Embedded Console and Account Flows Implementation Plan

## Overview

- Ticket: `ai/thoughts/tickets/2026-09-18-pr-1.4.1-embedded-console-and-account-flows.md`
- Research: `ai/thoughts/research/2026-09-18-pr-1.4.1-embedded-console-and-account-flows.md`
- Outcome: The executable Sidecar JAR serves an accessible browser console for account lifecycle, administration, and read-only inspection of the runtime-published configuration.

## Current State

`ManagementPagesController` serves minimal server-generated login, setup, recovery, password-change, and home forms. `ManagementController` owns the account/session JSON contract; `ManagementConfigurationController.current()` returns the full `RuntimeConfigurationService.Current` object. `ManagementSecurityConfiguration` isolates the stateful, CSRF-protected management chain from JWT execution. There are no application-owned static assets or browser tests. `pom.xml` already packages classpath resources into the Boot JAR. The research names the configuration HTTP test by its short name; its verified path is `src/test/java/ai/loomspan/sidecar/configuration/ManagementConfigurationHttpIntegrationTest.java`.

## Desired End State

Anonymous visitors can see whether first setup is available, locked by missing setup credential, reserved, or complete; only the existing one-time credential and reserved address can finish setup. Users can log in, log out, request recovery without account enumeration, redeem emailed set/reset links, and change their own password. Administrators can invite accounts and manage role/enabled state. Authenticated viewers can read the complete authored skill documents and REST catalog in the runtime-published snapshot, with `intendedId` separately labeled as restart selection. The console has usable labels, keyboard navigation, and textual feedback. Existing server security, draft privacy, and JWT execution boundaries continue to decide access.

## Scope

### In scope

- Browser pages, styling, and minimal client code for this ticket's account and read-only configuration flows.
- Security route rules needed for those pages/assets; no new account or configuration authority.
- Focused HTTP, browser, and packaged-asset evidence; README deployment and usage instructions.

### Out of scope

- Draft editing/publication, history/outcome screens, export/import, rollback, new framework APIs, external frontend hosting, and SMTP configuration in the UI.
- Final framework release checks, switching to the published dependency, release/tagging, or hosted CI before framework publication.

## Active Project Guardrails

- Use the simplest complete implementation; replace obsolete development UI directly without compatibility bridges or speculative abstractions.
- Framework execution/validation remains authoritative through supported `ai.loomspan.api` types; Sidecar must not import framework internals or autoconfiguration. Existing execution, startup, and diagnostic guardrails remain intact because this ticket does not change those paths.
- Keep JWT execution identity separate from management sessions. Management account/CSRF/session checks remain server-owned.

## Impact and Risk Analysis

- **Security and privacy:** Published configuration may include literal secrets. Keep its page and API authenticated with no-store/no-referrer headers; insert authored text only through escaped HTML or DOM `textContent`/`value`, never `innerHTML`. Do not request private draft/validation endpoints. Role-specific navigation is advisory; security filters continue to enforce every management request.
- **Session lifecycle:** A role change, disable, reset, or own-password change changes account version or invalidates the session. The browser must stop stale actions on 401/403 and send user-initiated activity only; initial load, data refresh, and passive time never call `/session/activity`.
- **Account recovery:** Anonymous forgot feedback stays identical for known/unknown accounts, including email failure. Setup/invite failures can explain delivery unavailability without exposing the credential or emailed token. Failed invites may leave a pending account; refresh the list and offer resend rather than implying no account was created.
- **Packaging:** Static files must be embedded under Boot's classpath resource path, served on the application port, and present in the repackaged JAR/Docker image. Avoid a Node build/deployment dependency for this small UI.
- **Compatibility:** Existing public routes/forms and JSON shapes are used as they stand. Preserve existing tests' form fields and key response wording where practical; account email remains immutable and last-admin protection stays in the SQL-backed service.

## Implementation Approach

Keep Spring-rendered HTML for anonymous login/setup/recovery and own-password forms, including native form POSTs and hidden CSRF tokens. Replace the minimal home with a shared console layout and add authenticated `/management/accounts` and `/management/configuration/current` pages. Use a small plain JavaScript file for JSON-backed account actions and current-snapshot display, and a CSS file under `src/main/resources/static/management/assets/`; no frontend package manager or build plugin is needed. `ManagementPagesController` renders trusted structure and escapes dynamic server values. Client code constructs DOM nodes and writes all API-provided text with `textContent` (including YAML, labels, faults and errors), not HTML parsing. Use the existing `/api/management/session` token for unsafe JSON calls and `GET /api/management/accounts` and `/configuration/current` for reads.

The plausible alternative is a single-page framework with a separate build pipeline. It adds dependencies and packaging work without meeting a current requirement the native forms and small client script cannot meet. No automatic polling is required for this ticket; use an explicit Refresh control for current configuration and accounts. Report activity on deliberate interaction through the existing endpoint, throttled at or beyond 30 seconds; do not report on page load or fetch completion.

## Test Strategy

Start with a failing authenticated GET test for the absent `/management/configuration/current` page. Use existing Spring Boot random-port HTTP tests with temporary SQLite and loopback SMTP for route, role, CSRF, account and session behavior. Keep server-policy tests at their existing service/HTTP level; add browser verification for UI-only behavior such as keyboard navigation, textual feedback, safe rendering, and paste/autofill. Inspect packaged JAR entries after `mvn verify`. No automated test should contact live SMTP, alter production accounts, or rely on an external frontend service.

## Risks and Rollback/Recovery

Browser code can accidentally turn authored YAML into executable markup or leak content into an anonymous route; guard via text-only DOM rendering, route checks, and browser inspection. UI state can become stale after account changes; every action relies on server authorization and 401/403 handling. Mail may fail after an account or token is persisted; present resend/retry guidance and refresh from the server. Roll back the Sidecar JAR/image and restore a known-good full database backup only if persistent state recovery is actually needed; this ticket adds no schema migration.
