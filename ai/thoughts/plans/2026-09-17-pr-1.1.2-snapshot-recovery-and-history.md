# Snapshot Recovery and History Implementation Plan

## Overview

- Ticket: `ai/thoughts/tickets/2026-09-17-pr-1.1.2-snapshot-recovery-and-history.md`
- Research: `ai/thoughts/research/2026-09-17-pr-1.1.2-snapshot-recovery-and-history.md`
- Outcome: Store a complete candidate and select it atomically, recover the committed selection on restart, retain bounded inspectable history, and verify stopped-instance database backup and restore.

## Current State

`ConfigurationSnapshotStore.submit` only appends a pending snapshot; `ConfigurationSnapshotRepository.setInitialCurrent` is the only pointer write. `initialize` and `current` load the pointer-selected snapshot without considering status. `updateStatus` changes only the status row. V1's single state row, foreign keys, immutable-content triggers, and submission sequence already support the intended transaction and oldest-first retention. `StorageConfiguration` runs Flyway before creating the store and calls `initialize` during bean creation. No production runtime consumer uses the store yet; mounted configuration still drives execution. The existing real SQLite tests use temporary files and Spring JDBC transaction managers. These observations match the research and current source.

## Desired End State

The caller supplies the expected current local snapshot ID when submitting B. One transaction inserts all B content and pending status and changes the pointer from A to B; a failed insert or compare-and-switch leaves A selected and no partial B. A guarded reversion changes B back to A and records B failed in one transaction, while a successful activation can record B published independently. Reopening selects the committed pointer even if B is pending. An initialized but damaged selection fails with secret-free recovery guidance. Startup prunes oldest eligible records to a positive configured target, protecting current and caller-supplied IDs. A stopped-instance copy of the full SQLite database set restores the same intended selection and retained history. The storage pointer remains an intended-production selection, not proof of runtime activation or export source.

## Scope

### In scope

- Transactional guarded A-to-B submission and B-to-A reversion; separate status recording and selected loading.
- Safe startup loading, retention property and pruning operation, storage-level recovery evidence.
- Real SQLite crash/interruption and backup/restore tests; operator documentation.

### Out of scope

- Framework publication coordinator, runtime generation tracking, completed-update pruning call, dispatch gate, retirement, management API, authored-configuration export, and account recovery. Phase 2/3/5 own these as the ticket states.
- New migration, compatibility bridge for the development-only append `submit` signature, online backup service, or automatic reconciliation.

## Active Project Guardrails

- The design lens requires the smallest complete change, direct use of existing storage primitives, and no compatibility shim for obsolete development code.
- Framework execution remains under the public `ai.loomspan.api` surface; no new framework integration is needed here.
- Preserve the one framework shutdown budget. This storage unit does not add shutdown hooks or a second drain.
- Diagnostic content may contain business data and secrets. Storage errors must identify the failed selection and recovery action without embedding authored YAML or SQL parameter values.

## Impact and Risk Analysis

- **Atomicity and concurrency:** A guarded SQL pointer update must participate in the same Spring transaction as candidate insert. A stale expected current ID or missing predecessor must reject the operation; no silent last-writer-wins switch. SQLite's configured busy timeout may surface a write conflict, which must propagate.
- **Crash selection:** A committed pending B is the restart choice. Status cannot be used as a selector or retroactively interpreted as failed. Reversion must retain B's content and identity.
- **Corrupt data:** The existing `initialize` distinguishes a genuinely new migrated database from existing content, but some reconstruction errors can leak low-level messages or lack recovery guidance. Selected-load errors must fail startup without reseeding or selecting older rows.
- **Retention:** Protected IDs count toward the target. The current pointer must be protected inside the prune transaction even when absent from the caller set. A deletion must cascade to document/status rows; the protected set's runtime completeness is a Phase 2 coordination responsibility.
- **Backup:** WAL may contain committed data absent from the main file. The documented procedure must stop the sole instance and copy/restore the database and any `-wal`/`-shm` files together, avoiding stale files on restore. It copies all database data, including literal secrets, without redaction or encryption.

## Implementation Approach

Use `ConfigurationSnapshotStore` as the transaction boundary and `ConfigurationSnapshotRepository` for guarded SQL. Replace append-only `submit` with a signature that takes `expectedCurrentLocalId`, rather than retaining an unsafe alternate publication path. In the submission transaction, verify the initialized selected state, insert B, then update the singleton pointer with a `WHERE` clause matching A's sequence; require exactly one updated row. Reversion takes expected B and predecessor A IDs, verifies A exists, performs a guarded B-to-A pointer update, and marks B failed in the same transaction. The existing independent `updateStatus` remains for recording successful startup/publication without rewriting the pointer or content. No status check chooses current.

Give the store a configured positive retention limit from a new `loomspan-sidecar.snapshots.max-retained` properties class (default 10), registered alongside current properties. `prune(Set<UUID>)` runs in one transaction, resolves the current pointer there, and deletes oldest eligible snapshots until the total is at most the limit or no eligible rows remain. This simple count-and-delete policy makes protected records consume capacity; it can exceed the target. Use V1's foreign-key cascades, with no storage-owned generation registry. `StorageConfiguration` calls `initialize` first and `prune(Set.of())` only after a successful selected load. Phase 2 later supplies protected runtime IDs and invokes pruning after completed attempts.

Keep the current V1 schema; it already has the needed pointer, ordering, status, and immutability constraints. Normalize selected-load failures at the store boundary to a message containing the selected sequence or local ID when available and a stopped-instance restore action, but no authored text or secret-bearing cause chain. Do not mask missing migration history or fabricate status. Document the distinction between intended selection and runtime activation and a concrete stopped-instance volume-copy procedure. A new online backup path would add operational complexity without a v1 requirement.

## Test Strategy

Use real temporary SQLite databases and repository-standard JUnit/AssertJ tests. Trigger insert/pointer/status failures to demonstrate rollback. Reopen with a new datasource after each committed transition. Include a forked-process open-transaction kill to verify crash recovery rather than relying only on mocks. Construct A and B with distinct skill and REST sentinels. Test corruption by SQL deletion/invalid status while asserting no selected-content values occur in the public exception message/cause. For retention, count all rows, status categories, and cascade results and verify `findByLocalId` returns null for expired IDs. Use file-copy backup/restore only while no SQLite connection is active; compare current pointer, authored content, and retained history after migration/validation. See the companion testing plan for individual cases.

## Risks and Rollback/Recovery

If a transaction fails, propagate its error and keep the committed pointer; do not retry with a different expected snapshot. SQLite corruption or invalid selected content requires stopping the instance and restoring a previously consistent full database backup; do not reseed or silently pick history. A restore rolls back all database records to the backup point, including status and history, and does not by itself prove which runtime generation executed before shutdown. Future Phase 2 integration must supply live-generation protected IDs, coordinate update completion with pruning, and verify runtime publication-fault recovery before deployment.

## Implementation Evidence

- The first acceptance test failed at compilation against the old append-only `submit` signature. That run also exposed a pre-existing test-fixture mismatch with the locally installed framework snapshot: `TestSkillInvocationHandoff` lacked `AdmittedSkillInvocation.generationId()`. One test-only method was added to match the public API so verification could run.
- A forked local JVM writes candidate content, status, and pointer inside one open SQLite transaction, signals readiness, and is forcibly terminated before commit. Windows needed a 500 ms handle-cleanup wait after child exit before reopening the same path; the test then verified A and absence of partial B.
- Focused storage/configuration tests passed (22 tests); full `verify` passed (121 tests) with the installed beta 5 snapshot. Later additions to binding and damaged-document assertions passed the focused suite again without changing production code.
- The stopped-instance copy test uses temporary SQLite files and existing WAL/SHM companions. The documented deployment-volume rehearsal remains an optional operator check, not an automated claim.
