# Management Accounts and Email Recovery Implementation Plan

## Overview
- Ticket: `ai/thoughts/tickets/2026-09-18-pr-1.3.1-management-accounts-and-email-recovery.md`
- Research: `ai/thoughts/research/2026-09-18-pr-1.3.1-management-accounts-and-email-recovery.md`
- Outcome: A local, email-verified management identity system with durable first-admin setup, account administration, session login, and email-only password recovery, isolated from execution JWTs.

## Current State

`JwtSecurityConfiguration.sidecarSecurityFilterChain` is the sole chain: stateless JWT, CSRF disabled, `/v1/**` authenticated, and all other requests denied. `ExecutionController` and `GenericRestSkillHandler` explicitly require JWT authentication. `StorageConfiguration` migrates the SQLite database before constructing the configuration repository, while `configuration_store_state.initialized` marks only snapshot initialization. There are no management accounts, sessions, forms, or SMTP integration. `application.yml` has no mail or management-identity properties. Existing integration tests use temporary SQLite files and loopback HTTP, and `ConfigurationReferenceTest` checks documented Sidecar property names.

## Desired End State

An operator presents a valid environment setup credential once to reserve the sole initial administrator email, receives a password-set email, and activates that account by choosing a compliant password. An invitation follows the same mailbox-control flow. Activated accounts log in with server-side sessions; admins manage accounts, while each user can change a password and anyone can request an email reset without revealing account existence. Management roles are hierarchical for later configuration APIs. Account state, bootstrap state, password hashes, and token digests survive restart in SQLite. Authentication changes end affected management sessions. `/v1/**` still requires JWT and framework observability retains its API-key boundary. Existing execution works when management setup or SMTP is unavailable. Phase 4 presentation, PR 1.3.2 editor/lease integration, PR 1.3.3 configuration operations, and Phase 5 exports are outside this ticket.

## Scope

### In scope
- SQLite migration, JDBC repository, transaction-owned account operations, setup reservation and token lifecycle.
- Spring Security management chain, local authentication, sessions, CSRF, account role authorization, bounded attempts, idle timeout, minimal forms and identity/account JSON APIs.
- SMTP sending and bounded waits, trusted link origin, deployment configuration and docs.
- Real SQLite, HTTP security, controlled local SMTP, and execution isolation tests.

### Out of scope
- Identity providers, JPA, public registration, email changes in place, admin-set passwords, offline recovery, durable mail queue, console SMTP editor, and extra framework SPIs.
- Drafts, leases, publication, complete console, configuration transfer, and release/publishing steps.

## Active Project Guardrails

- Prefer the smallest complete design; development schemas may be replaced without compatibility shims. Use the existing SQLite, Flyway, Spring JDBC, Spring Security and Spring MVC facilities.
- Keep framework skill validation/execution authority with public `ai.loomspan.api` contracts. Execution identity remains JWT-only, including queued work and REST passthrough. Management sessions never authorize `/v1/**`.
- Keep snapshot state distinct from account state. Preserve established execution lifecycle and diagnostics; no management change may cancel already accepted work.

## Impact and Risk Analysis

- **Bootstrap race and mail failure:** A durable one-row bootstrap reservation and unique initial-account constraint prevent competing admins. The setup credential can resend a fresh password-set link only to the reserved pending account, so an SMTP failure or ambiguous delivery does not strand it or reopen email selection. Completing the account reservation and consuming email selection are one SQLite transaction; email follows commit and failure is reported without rolling back the reservation.
- **Setup credential:** Read only `LOOMSPAN_SIDECAR_SETUP_TOKEN` from the process environment. Require unpadded base64url that decodes to exactly 32 bytes; document generating it from 32 cryptographically random bytes. Compare decoded bytes in constant time and never persist/log them. Missing, malformed or wrong credentials return the same locked-setup result. Keep the variable available until the reserved admin has received and used a link; after activation, it has no effect.
- **Account integrity:** A unique normalized-email index and atomic conditional write guard account duplication and last-active-admin changes. Count only enabled admins with passwords; pending invitations cannot substitute. SQLite write contention may return a retriable conflict, never an unguarded change.
- **Credential security:** PBKDF2-HMAC-SHA256 with a random salt and a recorded iteration count avoids bcrypt's 72-byte limit. A maximum of 128 Unicode code points, with an upper bound of 512 UTF-8 bytes, supports at least 64 characters without silent truncation. Password composition uses Unicode upper/lower/digit properties plus one non-whitespace, non-control punctuation/symbol; whitespace may appear but does not satisfy the special-character requirement. Apply to set/change/reset.
- **Email identity:** Accept a single ASCII mailbox address, trim surrounding whitespace, reject internal whitespace/control/display-name syntax, and lowercase the complete address with `Locale.ROOT` for storage, login and comparison. Limit normalized address to 254 characters. Document that this intentionally treats local-part case as equivalent; v1 addresses are immutable. Replacement means invite a new address, activate it, then disable the old account.
- **Recovery tokens and attempts:** Generate 32 random bytes with `SecureRandom`, encode base64url without padding, persist only SHA-256 digests with account id, purpose, expiry and consumed state. Password-set links expire after 24 hours; reset links after 30 minutes. Consumption, password update, recovery-token invalidation and credential-version bump happen in one transaction. Limit login to 5 failures per normalized account and 20 per remote IP per 15 minutes; forgot requests to 3 per address and 20 per IP per hour; token submissions to 10 per IP per 15 minutes. Use a bounded in-memory TTL counter table that fails closed at capacity, and use the socket remote address without trusting arbitrary forwarded headers. Successful login clears its account failure count. Application restart clears counters but not token/account state.
- **Sessions:** Store a credential version in each session principal and recheck current enabled/active/version state on management requests; expire registered sessions when password, role or enabled state changes. Set management idle timeout to 30 minutes by default, measured from login or an explicit authenticated user-action request; session/status polling must not refresh it. Container session timeout may expire sooner but cannot extend the security deadline. No cross-process session recovery is required.
- **Mail and configuration:** A missing sender/base URL or SMTP host makes email-dependent actions unavailable while retaining login and execution. Set finite SMTP connect/read/write timeouts; keep sender/base URL in `loomspan-sidecar.management.*` and transport in standard `spring.mail.*`. Construct URLs only from a configured absolute HTTPS external base URL (permit loopback HTTP in tests/development), never `Host` or forwarding headers. Return and log only fixed secret-free diagnostics. Mail credentials, accounts and tokens never enter managed snapshots.
- **Mail health:** Boot's mail starter also registers an SMTP health indicator. Disable that indicator so missing/unreachable SMTP does not mark Sidecar execution readiness down; email operations report availability themselves. The first full verification run exposed this interaction, and the separate health integration test confirms the correction.

## Implementation Approach

Use a small `management` package for repository, service, mail, web and security classes. Flyway V2 creates account, bootstrap and one-time-token tables separate from snapshot tables. `ManagementAccountRepository` owns SQL and conditional writes; `ManagementIdentityService` owns transactions and lifecycle rules. Keep outbound mail outside database transactions, with durable pending setup/invitation state and credential-gated resend. No queue is necessary: retries issue and email a new token, invalidating previous outstanding tokens for that purpose only after a new token is durably issued. A failed delivery never invalidates a usable existing password. The bootstrap retry path never changes its reserved email.

Split the current servlet security configuration into ordered chains: management browser/API routes use local form authentication, server sessions and CSRF; `/v1/**`, framework observability and Actuator paths retain the present stateless behavior. Keep JWT conversion and current execution authorities as-is. Management authorities use distinct `MGT_VIEWER`, `MGT_EDITOR`, `MGT_ADMIN` values; an account principal receives implied lower authorities on load, so role hierarchy requires no global authority-prefix changes. Management API authentication failures return fixed status/problem responses; browser pages redirect or show fixed messages. Explicit route namespaces are `/management/**` for pages/form posts and `/api/management/**` for later console clients; the separate Actuator port remains health-only.

API representation: `GET /api/management/session` returns id, normalized email, role, effective permissions and CSRF token for a logged-in account; `POST /api/management/session/activity` records an intentional user action. `POST /api/management/logout` ends the current session. Admin-only `GET/POST /api/management/accounts`, `PATCH /api/management/accounts/{id}` and `POST /api/management/accounts/{id}/resend-invite` list/invite, alter role/enabled state, and retry a pending invitation; no password or token fields are returned. `POST /api/management/password/change` requires current and new password and ends sessions. Anonymous setup/forgot/password-link operations have matching simple HTML forms; JSON operations may share service methods. Document concrete payloads/statuses in README during implementation. Spring form-login uses `/management/login` and default session-fixation protection. A CSRF token is rendered in every state-changing form, including anonymous login/setup/recovery; API clients send the session CSRF token as `X-CSRF-TOKEN`. Set HttpOnly, SameSite=Lax and HTTPS Secure cookie behavior and `no-store`/`no-referrer` response headers for credential pages.

### Rejected alternatives

Marking setup complete only after successful SMTP creates a race between database commit and an external side effect. Sending before commit can mail a link for a transaction that later rolls back. A durable pending reservation with restricted resend leaves one authority and permits safe recovery. A separate mail queue and Spring Session database add persistence and maintenance beyond the single-node requirement.

## Test Strategy

Start with a failing real-SQLite bootstrap test proving that configuration initialization does not consume management setup. Add repository tests for restart, token digests, transactions and concurrency, then loopback HTTP tests for security and sessions. Use a local in-process SMTP fixture that captures MIME messages and can fail/timeout, with no external addresses. Use an injected clock for expiry/idle limits and controlled simultaneous requests for races. Run focused tests after each phase and then full `verify`. Existing execution and observability tests must remain green; `SupportedLoomspanApiArchitectureTest` guards the framework boundary. The separate testing plan gives cases and exit criteria.

## Risks and Rollback/Recovery

The new migration is additive to the development database; no production release has been made. For a deployment failure, stop the application and restore a known-good full SQLite backup (including WAL state) before reverting the binary. Do not hand-edit accounts or tokens as a password-recovery method. An SMTP outage is handled in place: activated users retain login, and pending setup/invites/recovery can request a new link when mail returns. Local sessions are intentionally lost on process restart. A site that loses both its administrator password and email access needs full database backup/restore; the ticket explicitly excludes an offline bypass.
