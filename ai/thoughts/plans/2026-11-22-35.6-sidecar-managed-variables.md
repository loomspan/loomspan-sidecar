# Managed Sidecar installation variables implementation plan

## Overview

- Ticket `ai/thoughts/tickets/2026-11-22-35.6-sidecar-managed-variables.md`
- Research `ai/thoughts/research/2026-11-22-35.6-sidecar-managed-variables.md`
- Baseline Sidecar `3f6545fbb592059c131d312fed31766e38a17203`, Framework `03e7be1822102aed81f9187e797a1c9e285c89af` installed locally as beta.10-SNAPSHOT. The developer pre-approved the Full 5-Step Pipeline and separate local commits.

Keep the exact authored execution and skill YAML. Validate it with Framework first, assemble the exact installation value map from the selected revision, then prepare without activating. Publish a complete generation and encrypted inventory. Rollback selects historical documents and current values. Restart restores the selected publication.

## Current State

`configuration/EffectiveExecutionConfiguration` recognizes deprecated provider references, rejects literals, decrypts all records for assembly, and still calls the HTTP attachment method removed by 35.5. `RuntimeConfigurationService.validateWithCandidate` assembles before checking authored structure, and `ManagementEditingService.validate` loads draft records before calling it. The live generation and snapshot are already coupled by `ConfigurationGenerationRegistry`.

`ConfigurationDraftStore` mixes imported requirements and configured identifiers, and can discard records when YAML is loaded. `ManagementConfigurationRollbackService` loads older ciphertext from the source publication, and `RuntimeConfigurationService.candidateFor` can reuse the old effective settings. `ConfigurationBundleV4` preserves authored text and optionally includes encrypted records, but rejects direct literals on read. The browser builder emits the obsolete provider field names.

The refreshed starter also exposes two existing startup problems. Framework binds connections from the underlying configuration property sources before ordinary child bind handlers. In file mode Sidecar tries a second bind on a provider slice with Framework-owned representation, even after the correct Framework generation already started.

## Desired End State

Management reads and configuration-only ZIP exports expose authored YAML verbatim. Literal values are visible to those readers. Values supplied separately are encrypted, with markers remaining in the authored text. Variable name spelling and case survive exact round trips. Unrelated encrypted values remain stored and stay outside the preparation map. Failed validation or preparation keeps editable drafts and the current generation. Old admitted work continues with the previous captured settings.

## Scope

### In scope

- Exact variable discovery, management entry, lookup and diagnostics.
- Draft lifecycle, local snapshot storage, rollback and restoration, and existing bundle portability.
- Managed HTTP and provider examples, editor hints and fixture updates.
- Both startup-mode regressions against the installed Framework, full local verification and provider-free external fixture verification.

### Out of scope

- Framework API changes, release publication, remote sync, Cloud ZIP transport, Cloud variable-store access and tenant Vertex policy.
- Source changes to independent older Framework consumer applications. Their pins and standalone configurations do not participate in this Sidecar contract.

## Active Project Guardrails

Apply the [design lens](../design-lens.md). **Replace obsolete contracts, code and schemas directly. Preserve the authorized 35.5 and 35.6 split and avoid compatibility shims, legacy adapters, parallel readers and migration machinery.** Application and test code use the supported `ai.loomspan.api` surface and standard Spring APIs. Keep Sidecar's existing authorization, draft ownership, storage encryption and Framework-owned invocation lifetime. Framework alone substitutes variables, rejects collisions and prepares clients. HTTP operation correctness remains an invocation concern.

## Impact and Risk Analysis

- The same reference name can occur in both documents and several settings. Looking up every stored record can make unrelated entries block unrelated publications. Decrypt only referenced names for candidate preparation, keep the full encrypted inventory for persistence, and keep explicit encrypted import authentication.
- Authored validation may contain private-looking literals that editors deliberately saved. Preparation may carry resolved values. Return approved variable diagnostics and authored locations. Preserve generic safe errors for arbitrary provider preparation exceptions. Keep supplied values out of logs, serialized candidate objects, management output, and ZIP entries.
- Authored mapping keys are important input. A tree that normalizes keys before scanning would miss complex keys and could erase a collision before Framework sees it. Preserve original bytes and classify whole-node markers with YAML node tags.
- Publication and rollback touch both document selection and value versions. Apply the existing revision and lease gates, preserve exact revision validation and transaction boundaries, and store the encrypted set with the selected generation's authored snapshot.
- File mode must retain Spring Boot's Config Data, active profiles and variable lookup behavior. Database bootstrap needs source isolation before Framework's root binding and should preserve strict handling of process settings.

## Implementation Approach

Reuse the revision-bound management validation proof and keep encrypted records attached to the existing snapshot and draft owners. Narrow the existing candidate builder to reference discovery and direct value lookup. Store exact authored configuration and the encrypted set. Remove generated effective YAML and the historical value binding flag. Preserve source snapshot IDs as provenance.

Use SnakeYAML Engine's node API with CoreSchema for candidate discovery. The library is already present through Jackson YAML, with version 3.0.1 in the installed stack. Declare the direct dependency where needed so the source owns its parse dependency. Use Framework's documented authored boundaries and validate first through its public API. The Sidecar traversal need only identify names and authored locations. It does no substitution, settings binding, validation of YAML business rules, or provider/HTTP policy.

## Phase 1 — Authored validation and exact candidate preparation

### Changes

- [x] Replace the obsolete logic in `src/main/java/ai/loomspan/sidecar/configuration/EffectiveExecutionConfiguration.java`. Compose one YAML node document per original source. From `loomspan.connections` and `loomspan.executor-config`, scan each selected mapping value and exclude the section selectors. Treat additional keys as ordinary data and continue into them. Keep source and indexed authored paths for every occurrence. - [x] Keep a single exact-name rule for managed value entry and encrypted metadata in `EncryptedCredential` and `ManagementEditingService`. Keep record-version, ciphertext, encryption/AAD and request-size controls. Treat decrypted null/blank values as missing/blank failures with each authored location. The value input can continue to reject invalid blanks.
- [x] Build an exact deduplicated map with only referenced names. Retain all encrypted rows separately, including unused names. Preserve original YAML for `ExecutionConfiguration`. Preserve existing pending-publication recovery and the paired local 35.5 history. No deployed data operation is authorized.

## Implementation decisions

- Check ZIP mapping roots with YAML node composition so complex authored keys
  can round-trip without conversion to a JSON object. Framework validates and
  substitutes the original documents.
- Source the single configured-name inventory in each draft from its encrypted
  owner rows. Ordinary metadata reads query names only.
- Keep the plaintext value map scoped to preparation. The revision proof
  retains original documents and encrypted records. Publication checks both
  against the saved revision before reassembling the map.
- Framework requires the bundled TypeSafe executor's selected config path when
  the typesafe process profile is active, including on an empty catalog. The
  database bootstrap and initial snapshot include empty http and typesafe maps.
  Subsequent publications supply their authored maps. This allows the external
  packs to use the actual TypeSafe executor in both configuration modes.
