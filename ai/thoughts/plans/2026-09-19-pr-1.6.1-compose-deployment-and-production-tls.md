# Compose Deployment and Production TLS Implementation Plan

## Overview

- Ticket: `ai/thoughts/tickets/2026-09-19-pr-1.6.1-compose-deployment-and-production-tls.md`
- Research: `ai/thoughts/research/2026-09-19-pr-1.6.1-compose-deployment-and-production-tls.md`
- Outcome: One documented, verified production Compose deployment of the real Sidecar image with durable SQLite, direct HTTPS, non-root operation, customer SMTP, and isolated deployment evidence against the installed beta 5 snapshot.

## Current State

`Dockerfile` already runs Java as UID/GID 10001 and the application selects the database snapshot before opening execution dispatch (`RuntimeConfigurationService.activateAtStartup`). `examples/quickstart/compose.yaml` is an HTTP development fixture with an issuer/model stub, insecure cookies, and published health port. There is no production Compose file or inbound TLS configuration. `scripts/verify-image.py` checks that quickstart plus a Kubernetes sample, while `README.md`, `.github/workflows/ci.yml`, and `ConfigurationReferenceTest` still mention Kubernetes. `application.yml` already defaults cookies to Secure and exposes health only on management port 9091. The Boot 4.1.0 local web-server configuration metadata confirms `server.ssl.certificate` and `server.ssl.certificate-private-key` are available.

## Desired End State

The production Compose path starts one Sidecar image built from the locally built JAR. It serves the management console and JWT execution API over HTTPS on application port 8080, mapped to the operator's public HTTPS port. Actuator health remains HTTP on internal port 9091 and is not host-published. Read-only PEM certificate, private key, and JWT key mounts are readable by UID 10001; a persistent local data mount is writable by that UID. The configuration file names the required JWT, model, setup, SMTP, trusted external URL, and REST URL-variable values. A restarted initialized volume works after the one-time setup credential is removed; a fresh volume without that credential retains authenticated execution while management setup is locked. Quickstart remains clearly labeled loopback development HTTP. Kubernetes deployment support is explicitly deferred, and its sample and current support instructions are removed.

Acceptance criteria map to deployment startup/recreation, TLS/browser/mail, configuration and fixture isolation, lifecycle/health/shutdown, recovery instructions, and local snapshot evidence respectively. The application security and activation contracts remain owned by existing classes; this ticket verifies them through the deployment rather than replacing framework authority.

## Scope

### In scope

- Production Compose, sample operator configuration, container packaging adjustment if needed for volume/certificate readability, documentation, CI/image checks, and an isolated browser/application/container deployment test fixture.
- Removal of current Kubernetes sample and support assertions/references. Historical tickets and completed evidence stay intact.

### Out of scope

- Framework changes or rebuild, image publication, release tagging, hosted CI execution before framework publication, shared SQLite replicas, automatic mounted-file adoption, online backup, new recovery mechanisms, and production SMTP capture.

## Active Project Guardrails

- Use the simplest complete design; remove obsolete development or Kubernetes support artifacts directly, without compatibility shims.
- Framework remains the sole skill validation/invocation/shutdown authority. Sidecar keeps one dispatch gate and closes queued work promptly; the framework owns the budget for admitted work.
- JWT identity remains outside model input, and application/test Java references only the supported `ai.loomspan.api` framework surface. Keep ArchUnit enforcement.
- Snapshot activation is database-first and a restart reselects the committed database state; mounted files are never an alternate source.

## Impact and Risk Analysis

- **TLS and exposure:** Direct Boot PEM TLS avoids a second proxy/process and gives an unambiguous public endpoint. The production configuration must require explicit certificate/key paths and Secure cookies, never publish 9091, and document that the external URL equals the HTTPS origin reached by users. A certificate/key renewal requires a controlled container restart. A test certificate is confined to the fixture.
- **Persistence:** The image's `VOLUME ["/sidecar"]` can create an unrelated anonymous parent volume around a `/sidecar/data` mount. Remove or narrow it if deployment verification confirms it interferes with clear volume ownership. Bind-mounted host data requires UID/GID 10001 ownership; the test must check actual write/recreate/restore behavior on the same local filesystem.
- **Secrets and mail:** Production Compose should pass operator-supplied values without embedding fixture credentials. Keep its env file out of Git and readable only to the operator. SMTP capture is a test-only fixture, and test recipient domains remain `.test`.
- **Activation/lifecycle:** Health must represent startup completion and shutdown refusal, while an authenticated JWT request can still execute with management setup locked. Preserve `ExecutionCoordinator` and framework shutdown behavior; adapt deployment checks around it.
- **Release sequencing:** Use the installed snapshot for all local evidence. CI may be updated to the future published beta 5 path, but it cannot be claimed run while the release artifact is unavailable.

## Implementation Approach

Add `examples/production/compose.yaml` for one Sidecar service, plus a tracked example environment file and a production deployment guide. Use Spring Boot's `SERVER_SSL_CERTIFICATE` and `SERVER_SSL_CERTIFICATE_PRIVATE_KEY` with PEM files mounted read-only, `LOOMSPAN_SIDECAR_SECURE_COOKIE=true`, and the existing `LOOMSPAN_SIDECAR_EXTERNAL_BASE_URL`. Publish only `8080` as HTTPS; use Sidecar's in-container readiness healthcheck against port 9091. Set `stop_grace_period` above `LOOMSPAN_SHUTDOWN_TIMEOUT` plus cleanup margin. Use a named local SQLite volume and document the ownership preparation/inspection command for UID/GID 10001; avoid automatic chown in a root entrypoint. Mount the JWT public key or configure JWKS through existing supported properties. Use environment-driven model connections and `LOOMSPAN_SIDECAR_URL_VARIABLES` (comma-separated Spring binding) plus named process values for REST targets. Keep the quickstart as development-only HTTP.

Direct TLS is selected over a proxy because Boot already supports PEM and the ticket needs one small Compose target. A proxy would add another image, certificate propagation, and another health/exposure boundary without a current requirement. There is no application-level TLS rewrite.

Implementation observation: Boot 4.1 inherited `server.ssl` on the separate
management server during the first container run. The production Compose service
therefore sets the standard `MANAGEMENT_SERVER_SSL_ENABLED=false` property so
the unexposed port 9091 retains the documented HTTP health probe. This changes
no public application TLS behavior or Sidecar/framework authority.

## Risks and Rollback/Recovery

The highest operational risks are unreadable TLS/JWT keys, an unwritable SQLite mount, a wrong trusted external URL, and SMTP delivery failure. Compose should fail startup or management setup visibly rather than silently weaken security. The operator can stop the sole instance, preserve the full DB/WAL/SHM set, restore it with UID/GID 10001 ownership, and restart using the documented procedure. Configuration bundles cannot restore accounts or deployment settings. Revert the ticket's Compose/docs/check changes if needed; do not overwrite a release or alter framework publication.
