# Local Rollback and Recovery Implementation Plan

## Overview
- Ticket: `ai/thoughts/tickets/2026-09-18-pr-1.5.3-local-rollback-and-recovery.md`
- Research: `ai/thoughts/research/2026-09-18-pr-1.5.3-local-rollback-and-recovery.md`
- Outcome: An editor can review any locally retained snapshot and confirm a freshly validated destructive publication of its immutable content. Operators have a tested stopped-instance full-database recovery procedure.

## Current State
`ManagementConfigurationController` exposes exact history and import review/confirm, but no rollback mutation. `ManagementConfigurationImportService` binds review to session, content, runtime ID, and lease grant. `RuntimeConfigurationService.importConfiguration` holds publication and editing gates through fresh preparation, REST staging, draft cutover, database-first submission and framework publication. `ConfigurationSnapshotStore.findByLocalId` returns null after pruning; stored content is immutable. The history browser renders authored content with text nodes. The stopped-backup integration test restores selection/history but not a populated management identity.

## Desired End State
An editor or admin selects a retained ID, sees its recorded status and complete source summary, destination validation, runtime ID, lease owner/grant, and explicit draft-loss warning, then confirms that exact reviewed source. The server rereads that source under the publication gate, checks the same session review and runtime/grant observation, freezes its complete content, and enters the import publication path. Each accepted attempt creates a fresh local snapshot with `sourceId` equal to the retained source ID; original status/content remain historical. A missing source or changed review/runtime/grant returns a clear conflict or absence and preserves editing state. Lease renewal retains the grant and confirmation; replacement requires reconfirmation. The documented stopped database restore recovers both configuration and management identity from the committed backup point.

## Scope
### In scope
- Protected rollback review/confirm API and history-detail browser controls.
- Shared destructive publication behavior with local source lookup, fresh validation/preparation, and existing failure semantics.
- Stopped full database backup/restore verification and recovery documentation.

### Out of scope
- Remote history transfer, old-generation reuse, direct pointer rewind, durable jobs, cancellation, online/scheduled backup, encryption, automatic fault reconciliation, and Phase 6 deployment/release checks.

## Active Project Guardrails
- Choose the smallest complete design; reuse import's publication path and avoid compatibility shims or speculative abstractions.
- Framework validation and activation remain authoritative; use only public `ai.loomspan.api` types and preserve the ArchUnit check.
- Preserve the established shutdown budget, generation retirement, and database-first publication/fault policy.
- Use the developer-installed beta 5 snapshot; do not rebuild framework source or switch to the release dependency in this ticket.

## Impact and Risk Analysis
- **Authorization:** History reads are available to viewers, but rollback review/confirm are mutations and need explicit `MGT_EDITOR` routing plus Spring CSRF. The live account/session must be rechecked at acceptance, independent of lease ownership. Execution JWT routes remain separate.
- **Source and confirmation:** History can be pruned between list, review, and confirm. Only immutable content of the exact reviewed ID may be used; absence returns a clear response before cutover. A review held by another session, changed selected ID, runtime switch, or replaced lease grant must not authorize a destructive action. Recorded source status is informational, including `PENDING` and `FAILED`.
- **Concurrency and failure:** A valid review is advisory. Acceptance, source read, fresh preparation/staging, draft clearing, persistence, activation, status write, pruning and failure handling must use the existing publication/editing gates. Accepted work survives session loss. Drafts are lost after cutover even if commit/publication fails; before cutover they survive. A successful activation must not be reverted merely because bookkeeping fails.
- **Recovery:** A stopped copy must include the main SQLite file and whichever `-wal`/`-shm` files exist. Restore removes stale destination companions, preserves file ownership/write access, and startup follows the committed pointer. Backups contain accounts and sensitive persisted data; configuration ZIPs do not.

## Implementation Approach
Add a small `ManagementConfigurationRollbackService` to own the session-scoped review and confirmation, modeled on import's observation/admission behavior. Review loads an exact retained snapshot, validates its complete content against current destination bindings, and stores a random review ID bound to the source ID and observed runtime/grant. Confirmation requires the selected source ID and review ID, rechecks the active principal/session and validation, then calls a rollback entry point in `RuntimeConfigurationService`. That entry point acquires the publication and transition gates, rereads the source through `ConfigurationSnapshotStore.findByLocalId`, compares the reviewed ID and runtime/grant with live state, and passes the immutable `ManagedConfiguration` and `sourceId` to the existing destructive `publishCandidate` sequence. If source disappeared, return an explicit conflict/absence before draft clearing. Keep the confirmed operation independent of subsequent HTTP session events after admission. Extract only the admission/observation or cutover logic genuinely shared with import; do not introduce a generic job framework.

The browser extends exact history detail with a review button for editors/admins and a separate confirmation panel. Render source status/summary, validation issues, runtime and lease observation as text, disable confirmation when review is invalid or selection changes, show stale/missing feedback and refresh history/current state. Use the existing history revision guards and import outcome language for unknown/disconnected and bookkeeping outcomes. Keep viewer history read-only.

## Risks and Rollback/Recovery
The chief implementation risk is reading a source before the publication gate, allowing pruning or another publication between review and cutover. Reread under the gate, use immutable source content only, and fail before clearing drafts if missing. The existing database-first policy remains the recovery authority: after an unknown or faulted outcome, inspect runtime and intended state, preserve the database, and use a known-good stopped backup when needed. Do not make automatic retry or pointer rewrites.
