# Validated Configuration Import Implementation Plan

## Overview
- Ticket: `ai/thoughts/tickets/2026-09-18-pr-1.5.2-validated-configuration-import.md`
- Research: `ai/thoughts/research/2026-09-18-pr-1.5.2-validated-configuration-import.md`
- Outcome: Editors and administrators review a format-1 bundle against this destination, explicitly confirm the observed runtime snapshot and editing grant, and publish its complete authored content as a fresh local snapshot.

## Current State

`ConfigurationBundleV1.read(InputStream)` enforces the format and inclusive compressed, expanded, and entry limits, returning exact authored content and source metadata; only export calls the bundle writer. `RuntimeConfigurationService.validate(ManagedConfiguration)` uses public framework validation plus destination REST staging and route checks. `publish(...)` serializes ordinary publication and database-first failure handling, but clears drafts after activation. Editing operations acquire `transition` and then synchronize on `ManagementEditingState`; session destruction and account mutations currently synchronize directly on the latter. `ManagementConfigurationController` exposes current/export/history/publish, and the console has no import page. Storage already generates a new local UUID and accepts a separate `sourceId` on submit.

## Desired End State

An editor/admin uploads one format-1 bundle for review. Review reports source snapshot ID, producer versions, document/validated-skill/route counts, validation issues, the current runtime-published ID, and the current lease owner identity and grant (or absence), plus an explicit warning that confirmation discards every private draft and breaks the lease. Confirmation presents the same bundle again with its review token and observed runtime/grant IDs. The server accepts only the exact reviewed bytes and a valid destination candidate. It atomically checks the observed runtime/grant under publication and editing serialization; stale observations return fresh confirmation information without clearing drafts. After fresh public preparation and complete REST staging succeed, it clears editing state, submits a new local pending snapshot with the source ID as provenance, and follows existing activation, failure, restart, and retention rules. Browser status distinguishes a known failure from an unknown/disconnected outcome and directs inspection of current/history. Viewer export and inspection, JWT execution, installation settings, and account state retain their existing behavior.

## Scope

### In scope
- Multipart review and confirmation API, exact review binding, bounded temporary upload handling, destination validation, role/CSRF enforcement, and safe errors.
- Import publication admission, synchronization, cutover, provenance, failure outcomes, and regression tests.
- Embedded console import page, browser behavior, and user/operator documentation.

### Out of scope
- Merge, draft import, history/status transfer, rollback UI, persistent import jobs, retry/cancel API, framework SPI or internal dependencies, and release/version switching.

## Active Project Guardrails

- Keep the change proportional; use the existing bundle reader, validation, storage, and publication policy. No compatibility bridge or speculative import subsystem.
- The framework remains the sole skill validation and execution authority through `ai.loomspan.api`; Sidecar owns admission and REST resources.
- Preserve the existing generation lifetime and database selection model. Do not add a second execution or shutdown policy.
- Keep trusted management identity outside bundle content; enforce session role and CSRF through the existing management chain.

## Impact and Risk Analysis

- A bundle can be 100 MiB compressed and 512 MiB expanded. Do not retain parsed content or upload files across requests. Configure Spring multipart file/request bounds above any smaller default, use container-managed multipart cleanup plus the reader's `finally` deletion, and cap each review/confirm request to one required file. A confirmation reupload costs bandwidth and parsing but avoids a large, leak-prone per-session cache. Confirmed bytes are compared by streaming SHA-256 against a small session review record.
- Validation can become stale as the destination environment changes. Review is advisory; confirmation re-reads exact bytes and revalidates before acceptance, then fresh preparation and staging are decisive. Authored placeholders stay in `ManagedConfiguration`; the existing `RestRouteLoader` owns exact allowlist/process-environment resolution.
- Publication and editing gates have different lock order and session/account invalidation bypasses `transition`. Import must acquire `publication` then `transition`, check runtime/grant under the state monitor, and retain `transition` until its outcome, including failure cleanup. Session and account invalidation must use the same transition-before-state order. Do not make a callback that can reacquire `publication` while holding `transition`.
- Review and confirmation must use the runtime-published ID, not the intended pointer. The grant comparison uses its UUID, not owner identity; expiry is interpreted as absence. The review record belongs to one session and one upload; a second upload replaces it. Return an updated observation on conflict so the user can explicitly reconfirm. Do not expose another user's private draft content.
- Import clears drafts after successful preparation/staging but before database submit. All later failures leave them cleared. Reuse commit, activation/reversion, status, pruning, and mutation-fault behavior, and report whether a snapshot was submitted and whether the runtime changed. An HTTP disconnect or logout after admission must not interrupt server-side work.

## Implementation Approach

Use two multipart requests: `POST /api/management/configuration/import/review` with one `bundle` part, then `POST /api/management/configuration/import/confirm` with that same part plus `reviewId`, `expectedPublishedId`, and nullable `expectedGrantId`. The controller stores only one small review record in the current `HttpSession`: random review ID, byte digest, validation success, and source metadata; subsequent review replaces it. Stream the digest while the reader consumes the upload, or stage the bounded compressed bytes once and use the same temporary file for digest and `read(Path)`; whichever avoids redundant staging while guaranteeing `finally` cleanup. Never use a client-supplied source ID for persistence. Confirmation compares reuploaded digest to the server review record and re-reads the bundle; digest mismatch or changed review ID requires a new review. Successful or attempted accepted confirmation consumes the review record, preventing an accidental replay; repeated identical imports require a new review and produce a fresh local ID.

Build a dedicated `ManagementConfigurationImportService` for session review, owner observation, and admission. The review response identifies `skillDocuments` separately from validated skill count to avoid calling a YAML document a single skill. Obtain validated skill count from the supported framework validation result or catalog, and route count from destination parsed routes; if validation is invalid, report document count and any counts safely available without accepting confirmation. Use account email already visible to authenticated management users for lease owner identity. Add a narrow `RuntimeConfigurationService.importConfiguration(...)` path that owns `publication` and `transition` for confirmation through final outcome, reusing shared publication/failure helpers where doing so reduces duplication without changing ordinary publication timing. Accepted work uses the synchronous publication operation already used by ordinary publish; request connection and session validity are checked only at admission. The publication lock serializes ordinary publish/import; editing and invalidation defer under `transition` until import completes.

## Test Strategy

The first red test is an editor review upload returning source metadata and destination feedback without a history insert; the current API returns 404. Use existing temporary SQLite and test-auth/browser conventions. Add focused parser/upload limit tests, HTTP security and review-binding tests, runtime latch-driven concurrency/fault tests, two separately configured destination contexts for exact authored transfer and environment binding, and Playwright workflows. Assert both `published` and intended/persisted state after every failure; do not infer success from HTTP status alone. Keep live network calls and real production credentials out of routine tests.

## Risks and Rollback/Recovery

The two-upload design doubles transfer cost and requires the browser to keep the selected file until confirmation; it avoids persistent or large session storage. The review record is volatile and intentionally expires with the management session. A rejected pre-cutover attempt preserves drafts. After cutover, use current runtime and local history to determine the outcome; the existing database pointer is restart authority, and a mutation fault requires operator recovery rather than a blind retry. There is no import rollback endpoint in this ticket. Routine local builds use the installed `1.0.0-beta.5-SNAPSHOT`; final release dependency switch and hosted CI remain deferred by repository policy.
