# Sidecar HTTP variable settings testing plan

## Change Summary

Exercise resolved headers and a resolved route through a file-mode Sidecar
startup. Confirm the executor's authorization ownership rules on a real
receiver, and preserve captured generation behavior and caller JWT checks.

## Impacted Areas and Risks

| Category | Risk | Planned evidence |
| --- | --- | --- |
| File startup | Marker remains a map, resolves from the wrong property source, or route input is applied too early | Two startups over identical YAML, with distinct Spring properties and actual receiver observations |
| Fixed authentication | Duplicate Authorization, changed value, or dependence on a credential record or current caller | Full Authorization value list on the wire and fixed invocation with an independent authenticated caller |
| Invocation gating | Invalid header ownership or bad HTTP settings cause an outbound request | Loopback request counts for lowercase Authorization in none and passthrough; existing invalid HTTP configuration cases |
| Caller authentication | A stale or different caller's JWT is forwarded, or target headers override it | Two concurrent authorized callers, absence/expiry checks, role authorization and Framework handoff |
| Generation and dependency boundaries | Settings change for admitted work, or implementation uses unsupported APIs | Public prepare/publish/handoff checks, file restart coverage, ArchUnit, lifecycle checks |
| Commit split | Intermediate compile failure masks an unrelated defect | Actual checkout compile diagnostic, clean isolated compile and focused suite using only the bounded call-site block removal |

## Existing Coverage and Environment Constraints

Use JUnit/Surefire, the installed Framework snapshot, the current Java 21 Maven
environment, and the existing loopback `HttpServer` fixtures. Boot integration
loads files from JUnit temporary directories with process trust fixtures. The
HTTP tool case uses its own loopback model response fixture. No paid provider,
production environment, external endpoint, or deployed data is involved.

The real 35.5 checkout must retain the managed builder call even though removal
of the helper makes that checkout fail to compile until 35.6. Maven compiles
all sources before applying a Surefire method selector. Execute the focused
tests in a disposable copy after removing the exact obsolete attachment block
from that copy. Managed tests for legacy credentials are deliberately outside
this lane. Full Maven and affected external verification is required after
35.6. Record the isolation and every command actually run.

## Tests to Add or Update

- Type and location: The file-startup test above, with a temporary settings
  file, skill file and loopback receiver.
- Write a target under `loomspan.executor-config.default.http.targets` with
  `auth: {mode: fixed}`, literal `Accept: application/json`, and whole-node
  markers for `X-Region` and `Authorization`. Write the operation's path
  marker in top-level `config` and map `recordId` to `/recordId`.
- Boot with `--app.region=west`,
  `--records.lookup-path=/v2/records/{recordId}`, and
  `--service.authorization=<fixture scheme and value>`. Request record
  `42`. Assert `/v2/records/42`, singleton Accept and X-Region lists, and the
  singleton exact Authorization value. Record values by copying from the

  east, `/v3/records/{recordId}` and another full fixed Authorization). Assert
  the new values appear together on one network request. Use simple dummy
  credentials whose scheme cannot be mistaken for the JWT Bearer prefix.
- Re-run `fileStartupAcceptsInvalidHttpSettingsWithoutDomainChecks` and
  `fileInvocationUsesBootImportAndActiveProfileSelection` in the same class,
  and the startup and restart file tests in `ConfigurationModeIntegrationTest`.

## Step 4 verification

The local Framework starter was installed from
`03e7be1822102aed81f9187e797a1c9e285c89af`. The new file installation test
failed before the implementation with `Invalid HTTP header ownership`, as
expected. In the actual checkout Maven initially reused the pre-change
classes. Removing only the generated
`target/classes/ai/loomspan/sidecar/http/HttpExecutorConfiguration.class`
forced recompilation. `mvn -o -B -DskipTests compile` then reported one
error, the intentionally deferred `withCredentials` reference. The managed
builder file is unchanged.

The Windows sandbox interrupted Mockito's dynamic agent attach. Use the local
Mockito agent for the isolated JVM lane.

```powershell
$agent = Join-Path $env:USERPROFILE '.m2/repository/org/mockito/mockito-core/5.23.0/mockito-core-5.23.0.jar'
mvn -o -B "-DargLine=-javaagent:$agent" "-Dtest=HttpExecutorConfigurationTest,HttpSkillExecutorTest,HttpExecutorIntegrationTest,HttpExecutorTlsIntegrationTest,HttpExecutorLifecycleIntegrationTest,HttpExecutorArchitectureTest,HttpConfigurationIntegrationTest#file*,ConfigurationModeIntegrationTest#databaseSkipsNumericExecutionBindingButPreservesStrictProcessBinding+fileStartupDoesNotInitializeDatabaseSelectionAndRecordsDurableIdentity+environmentModeIsCapturedOnce+fileHttpConfigurationRemainsCapturedUntilRestart" test
```

The command above passed all 57 selected tests in the isolated copy. This
includes loopback wire coverage for both installations, singleton fixed
Authorization, lowercase rejection without dispatch, independent caller
passthrough, and file-mode restart. Both HTTP reference examples match. On
the actual checkout, `git diff --check` and the managed builder diff guard
passed. The builder call is the sole `withCredentials` hit in Java sources.

The broader isolated command with the entire `ConfigurationModeIntegrationTest`
class ran 61 tests and reported two errors. Both errors reproduced with the
same installed Framework snapshot on a separate clean archive of Sidecar
`5899e2ff1fb94c2ed93e31fab60f0bc05b861fd9`.

```powershell
mvn -o -B "-DargLine=-javaagent:$agent" "-Dtest=ConfigurationModeIntegrationTest#databaseModeBootstrapsDespiteInvalidDeploymentProviders+fileModelCredentialsChangeOnlyAtRestartAndPreserveDatabaseAuthority" test
```

- `databaseModeBootstrapsDespiteInvalidDeploymentProviders` fails at binding
  because Framework selects `loomspan.connections` directly from the Spring
  property sources before Sidecar's database binding advisor can exclude them.
- `fileModelCredentialsChangeOnlyAtRestartAndPreserveDatabaseAuthority` fails
  when Sidecar tries to bind the file inspection's `loomspan.connections`
  map. A diagnostic-only retry in the baseline copy shows Spring cannot
  convert Framework's opaque YAML node to the inspection map. The HTTP
  execution path does not use this inspection map.

These baseline integration failures require follow-through in 35.6's combined
verification of file startup and managed authority. They do not originate in
the changed HTTP settings or dispatch behavior. The full Sidecar build and
external consumer verification remain on the paired ticket.
