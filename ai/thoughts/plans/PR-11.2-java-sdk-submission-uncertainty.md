# Java SDK submission uncertainty implementation plan

## Overview

- Ticket: `ai/thoughts/tickets/PR-11.2-java-sdk-submission-uncertainty.md`
- Research: `ai/thoughts/research/PR-11.2-java-sdk-submission-uncertainty.md`
- Outcome: report uncertainty after a possible submission with no reliable
  outcome, while preserving local failures, HTTP status and status-wait context.
- Route: Full 5-Step Pipeline, confirmed by the developer after Step 0.

## Current State

`SidecarClient.submit` validates and encodes the request locally, then delegates
to `request`, which also serves discovery and execution reads. The SDK validates
the accepted UUID only after `request` returns a complete JSON value. Both body
overflow paths currently throw `ProtocolException` before status classification.
The early interrupt check and the transport failure handler both report
`WaitTerminatedException` on an interrupted submission. The status becomes known
to the SDK when `http.execute` returns a response and `request` reads its code.
The watchdog, `request.cancel()` and immediate response close bound and release
the local exchange without issuing a server operation.

## Desired End State

| Observation | Result |
| --- | --- |
| Invalid local arguments, known closed client, or submission interrupt detected before transport invocation | `LocalFailureException`; no transport attempt; interrupt flag stays set if present. |
| Submission after possible dispatch with no reliable acceptance or observed HTTP error | `AcceptanceUnknownException` with null ID and snapshot. Includes declared and streamed success overflow, malformed or lost responses, and interruption. |
| Observed non-2xx with unusable or oversized body | `HttpFailureException` with the status and no partial problem details. A complete, usable, bounded JSON problem still passes through the existing credential redaction. |
| Unusable successful discovery or status response | `ProtocolException`, preserving the requested ID and last snapshot when available. |
| Interrupted status read or elapsed explicit wait budget on a transport failure | Existing `WaitTerminatedException` and context. Existing non-transport wait checks also keep their behavior. |

For submission, an observed non-2xx status remains an HTTP outcome when an
interrupt or deadline makes its body unusable. For reads, preserve the existing
termination precedence when an interruption or explicit wait expiry ends an
incomplete transport operation. A response that reaches an overflow check is
classified by its observed status. Neither an HTTP error nor client-side
termination guarantees that server work had no effects.

## Scope

### In scope

- Blocking Java SDK request classification, focused loopback regression tests,
  and current SDK consumer documentation.
- Auditing the changed paths and confirming remaining production and test
  consumers before removing any obsolete code, fixture or dependency.

### Out of scope

- Server or wire protocol changes, TLS and signing configuration changes,
  callback trust startup, Python, recovery or retry features, public exception
  hierarchy changes, releases, and operational data changes.

## Active Project Guardrails

Apply the [design lens](../design-lens.md#simplicity-and-technical-debt). Replace
superseded behavior directly during development, without compatibility paths or
schema machinery. No data reset is needed. Keep the Framework boundary and the
Java reactor's independent dependency rules. Keep credentials and raw parser or
transport diagnostics out of exception messages. Document the executable SDK
contract in the README. Neither recovery nor reconnects may replay submissions.

## Impact and Risk Analysis

- The exception type drives what callers know after a possible side effect.
  Local failure requires evidence before entering the transport. A failed
  transport invocation alone cannot establish whether it sent the request.
- The shared method serves reads. Changing the catch order for every operation
  would also change read interruption and wait behavior. Preserve read priority
  explicitly when handling incomplete transport failures.
- A fixed-size declaration can fail before the stream opens. Chunked responses
  can fail only after reading the first byte over the limit. Keep the current
  limit plus one byte probe, avoid parsing an incomplete body, and keep cleanup
  inside the existing `finally` so neither case drains the remainder for reuse.
- The existing credential redaction is applied to complete bounded source bytes
  before exposing a parsed object. No partial, raw or unredacted body or cause
  should be attached on any new path.

## Implementation Approach

Keep `SidecarClient.request` as the only transport path. Retain the early
interruption check and check again immediately before invoking `http.execute`,
inside the cleanup scope once the watchdog is installed. Use `isInterrupted()`
so neither check clears the flag. A submission detected there fails locally;
an interrupted read keeps its current wait outcome. The second check narrows
the setup window. Once control enters the transport, classify conservatively
unless the SDK already knows the HTTP error status. Do not infer caller
interruption from an `InterruptedIOException` alone because that type can also
come from a socket timeout or local transport cancellation.

Share the body-failure classification for declared length overflow, streamed
overflow and transport failures after the existing read-termination check. The
classifier can use the operation, observed HTTP status and existing ID/snapshot:
non-2xx yields HTTP failure without problem, otherwise submission yields unknown
acceptance and reads yield protocol failure. Keep expected-status and JSON/UUID
validation, safe problem parsing, and the completion deadline check. Leave
the original one-attempt HttpClient configuration, watchdog scheduling, byte
budget, cancellation/close order and client close path in place. No new transport
state machine, dependency, cancellation endpoint or exception type is needed.

## Test Strategy

Exercise the public SDK against the existing counted ephemeral loopback fixture.
Gate in-flight interruption on observed POST receipt, bound worker waits, and
verify the caller's flag. Use valid-looking ID prefixes and headers for overflow,
an oversized problem with synthetic secrets for diagnostic checks, and existing
read/wait fixtures for regressions. Verify local recovery on the same client and
run the full SDK reactor after focused tests. Step 5 independently repeats
relevant verification before recording disposition.

## Risks and Rollback/Recovery

Code and docs can be reverted as a unit if required during development. There
are no configuration, schema or data changes. Local transport cleanup leaves any
already-admitted server execution to its existing lifecycle. If an unrelated
break permitted by the series is encountered, record its cause, resolving ticket
and the pending check before claiming completion of any affected verification.

## Step 4 implementation evidence

- `checkDispatchInterrupt` classifies interruptions detected at request entry
  and immediately before `http.execute`. After transport entry, the shared
  `responseFailure` preserves an observed HTTP error status and classifies an
  unusable submission response as acceptance unknown. The transport catch
  retains the prior termination precedence for reads.
- The old overflow classification and assertion were replaced. The reused
  fixture supports both fixed-length and chunked replies. A consumer audit found
  no newly orphaned declarations. The transport, TLS, JSON, signing and test
  dependencies still serve current SDK code and fixtures.
- The in-flight test held six received POSTs without sending response headers.
  The caller exited with uncertainty and its interrupt flag intact each time,
  and the same client could read afterward. This exceeds the transport pool's
  five default leases per route and checks cleanup without a new test hook.
- The exact commands and test counts are in the testing plan. The SDK reactor
  had no temporary series break. Combined series checks remain pending under
  the roadmap, and Step 5 owns the independent review disposition.
