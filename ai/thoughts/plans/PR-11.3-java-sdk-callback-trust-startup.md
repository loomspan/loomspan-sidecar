## Current State

`CallbackSecurityAutoConfiguration.callbackJwtTrust` creates the trust bean from the startup signer, and the SDK security filter chain consumes it. `CallbackJwtTrust` calls `reload` in its constructor and creates the scheduler afterward. The shared reload currently publishes empty trust on read or validation failure at startup and at runtime. Only runtime withdrawal is required. `CallbackJwtDecoder.decode` already turns failure into the generic authentication error without a cause. The filter chain exposes HTTP 401 with a bare Bearer challenge.

Spring Boot 4.1.0's `LazyInitializationBeanFactoryPostProcessor` honors a bean definition with an explicit lazy setting. Eager trust creation should be explicit at the trust bean to enforce the startup boundary even when an application opts into global lazy initialization. Servlet-only activation and the dependency on the existing signer remain the same.

Sidecar's separate `JwtSecurityConfiguration` and `CurrentFileJwtTrust` intentionally publish a waiting state if the colocated app has yet to produce the first export. The two loaders are in separate Maven builds and do not share trust state.

## Desired End State

A configured overlap file must be readable, valid UTF-8 JSON and a nonempty public RSA JWKS under the existing validation and merge rules before SDK callback security starts. Initial read failure names `loomspan-sdk.callbacks.overlap-jwks` and asks for a readable file. Initial validation failure names the same property and asks for a valid nonempty public RSA JWKS. Diagnostics contain only fixed safe text and no nested read or parse cause. The constructor fails before creating a refresh executor. If the option is absent, the initial snapshot contains the startup signer's key and no poller is required.

After startup, failed read or validation publishes empty trust. Restoring a valid file automatically publishes the entire merged snapshot. An unavailable or invalid transition emits a warning, and a transition from either failure to ready emits a restoration message. A change between the unavailable and invalid categories emits the new category once. Unchanged categories remain quiet even if invalid bytes or exception messages vary. A normal initial load and healthy-to-healthy key changes need no transition message. Callback callers keep the generic error, and admitted requests retain their already-established authentication.

## Impact and Risk Analysis

Creating a poller before initial validation can leave a live task because Spring cannot destroy a bean that never completed construction. Keep allocation and scheduling strictly after initial validation. The signer can already have published its own public export by then. It owns no ongoing resource, and there is no safe or required rollback of that prior atomic publication.

Splitting startup and runtime validation would risk drift. Use the existing synchronized reload path with a distinct first-load outcome and the same parser/merge. Keep the volatile immutable snapshot as the only reader-facing state. Perform state transition comparison under the existing reload monitor to avoid duplicate diagnostics during simultaneous polling and unknown-key refreshes. A known key can be accepted until replacement is detected, consistent with the current polling contract.

## Implementation Approach

Keep the change inside `CallbackJwtTrust` and its existing bean declaration. Replace the current unavailable-cache flag with a private ready/unavailable/invalid state for transition detection and read-result caching. Keep byte comparison separate from transition comparison so distinct invalid contents can be evaluated without producing repeated warnings. Use the logging facade already available to the starter, with constant messages and no throwable or interpolated file, key, or JWT data. No dependency declarations are expected to become unused. The audit should recheck Nimbus parser and decoder consumers, Bouncy Castle PEM loading, HTTP/TLS and SSL-bundle clients, and test fixtures, while replacing the obsolete startup expectation.

## Risks and Rollback/Recovery

An invalid initial file is a configuration error. The operator supplies a valid file atomically and starts the app. A healthy running app can recover on refresh as soon as valid content returns. The earlier tickets' temporary build exception cannot clear the final combined gate. A real verification blocker must be recorded with the cause and pending checks.

## Implementation Evidence

`CallbackJwtTrust.reload` owns initial validation and refresh. It routes an unreadable file and invalid contents through the same publication method as a healthy file. Failed construction publishes nothing and reaches no scheduler allocation. Later failure publishes empty trust in one volatile update. Log category comparison stays under the existing reload monitor and uses fixed diagnostics. The servlet bean explicitly opts into eager initialization. The Sidecar trust loader and SDK JWT decoder required no edits.

The old flag and the runtime test's initial empty-trust setup were replaced. Nimbus still supports signing, export, trust parsing and decoding. Bouncy Castle and the synthetic PEM/JWKS fixture still support provided signing and its tests. Apache HTTP client, Jackson, and Spring SSL bundles still serve SDK transport and data handling. No dependency declaration or fixture file became unused. All four pre-existing sibling PEM fixture edits were preserved.
