# Sidecar HTTP variable settings implementation plan

## Overview

- Ticket `ai/thoughts/tickets/2026-11-22-35.5-sidecar-http-variable-settings.md`
- Research `ai/thoughts/research/2026-11-22-35.5-sidecar-http-variable-settings.md`
- Outcome: File startup resolves installation-specific HTTP headers and operation
  paths through Framework. The annotated executor sends validated captured
  headers and obtains passthrough authorization from the current request.

## Current State

`HttpSkillExecutor.execute` already receives the two captured maps from
`SkillExecutorInvocation`. It validates them, maps input, and builds outbound
headers. Fixed auth currently decrypts records indexed by the credential IDs
in `HttpExecutorConfiguration.Target.headerRefs`. The caller-passthrough branch
requires an authenticated, unexpired JWT from Spring Security. The managed
`EffectiveExecutionConfiguration.assemble` is the sole production caller of
`HttpExecutorConfiguration.withCredentials`.

The installed Framework starter was refreshed from
`03e7be1822102aed81f9187e797a1c9e285c89af` with
`mvn -o -B -DskipTests install`. Framework file startup resolves whole-node
references from the effective Spring Environment and captures resolved executor
and skill maps together. Sidecar's tests must prove this behavior on their own
application startup and receiver.

## Desired End State

The same authored file-mode documents run in two installations with different
host properties. A real request sends a literal Accept header, the resolved
X-Region header and, in fixed mode, exactly one resolved Authorization value
including its authored scheme. Invocation maps a record ID into the captured
route. Fixed mode also supports an ordinary custom header with no Authorization.
Default/explicit none and caller-passthrough reject authored Authorization
case-insensitively before dispatch. Caller passthrough uses its admitted request
JWT and rejects missing or expired authentication. Startup and preparation
continue to leave HTTP-specific target and route validation to invocation.

## Scope

### In scope

- HTTP executor records, validation, request dispatch, and direct dependencies.
- Sidecar file-startup and HTTP executor fixtures, including the detached
  Framework fixture directly supporting the HTTP tool test.
- The product and packaged HTTP references and their file-mode examples.

### Out of scope

- Managed candidate assembly, deletion of its stale helper call, management
  authoring, managed fixtures and the external consumer-pack handoff in 35.6.
- Changes to Framework, provider authentication protocols, request input mapping,
  connection lifecycle, or the caller JWT authorization boundary.
- The pre-existing untracked 35.6 ticket is excluded from the 35.5 commit.

## Active Project Guardrails

Apply `ai/thoughts/design-lens.md` and replace obsolete HTTP credential fields,
records and helpers directly without compatibility readers or adapters. Framework
owns resolution, validation of its contracts, and execution. Use the supported
`@SkillExecutor` bean and `ai.loomspan.api` types. Keep request authentication
outside installation settings and model inputs. Keep validation network-free
until actual invocation and preserve admitted work under its captured generation.
Keep documentation about the supported consumer contract.

## Impact and Risk Analysis

Removing `withCredentials` leaves the managed builder with an unresolved method
call in the intermediate 35.5 commit. The ticket explicitly assigns removal of
that call site to 35.6 and accepts the temporary failure. Run the HTTP and file
lanes in a disposable copy with only the stale attachment block removed there;
verify the actual checkout exhibits the expected compile failure and retain its
managed source unchanged. A complete build and managed/external tests must pass
after 35.6 before release.

Authorization ownership is checked before mapping and dispatch. Keep values
out of validation messages and retain redacted string representations for
parsed settings and targets. A fixed Authorization value is supplied as one
header, so an authenticated request still cannot override that value through
its caller identity or model inputs. No data reset is needed in this unit.
Authored development file configuration using retired HTTP fields must be
replaced directly. The managed authoring and reset assessment belongs to 35.6.

## Implementation Approach

Reuse the existing executor and its validation flow. Parse target auth mode
before validating headers and give the header check permission to accept
Authorization only for fixed mode. Keep the case-insensitive uniqueness check,
transport-owned header exclusions, existing string/value checks and JSON
Content-Type validation. Remove the parallel header-reference map and encrypted
inventory entirely. The outbound header copy receives fixed values directly.
Maintain the separate caller-passthrough branch and its authentication and
expiry checks.

## Test Strategy

Use existing JUnit, loopback HTTP/TLS and local Boot integration. Add a receiver
test that fails against the old mode contract, followed by wire assertions for
file-started values and rejected requests. Retain the current direct-invocation
and public Framework handoff checks for request-owned JWT behavior, lifetime,
and local provider tool correction. The testing plan defines the isolated copy
boundary and expected intermediate failure.

## Risks and Rollback/Recovery

No shared environments or persisted data need changes. A local revert of this
commit should be paired with a revert of 35.6 if 35.6 has already landed.
If validation fails beyond the known managed helper call, diagnose and fix
ticket-scoped failures before treating 35.5 as complete. Keep both commits local
and do not release the intermediate checkout.
