# Session-owned configuration drafts implementation plan

## Overview

- Ticket: `ai/thoughts/tickets/2026-09-17-pr-1.1.3-session-owned-configuration-drafts.md`
- Research: `ai/thoughts/research/2026-09-17-pr-1.1.3-session-owned-configuration-drafts.md`
- Outcome: An ephemeral draft holds complete authored content from an explicitly supplied runtime snapshot, associates validation with a precise frozen candidate, and yields immutable publication input.

## Current State

`ManagedConfiguration` is an immutable value containing an ordered copy of named `SkillDocument` YAML and raw REST YAML (`src/main/java/ai/loomspan/sidecar/storage/ManagedConfiguration.java`). `ConfigurationSnapshot` carries durable local identity and complete content (`ConfigurationSnapshot.java`). `ConfigurationSnapshotStore.current()` instead reads the SQLite intended-production selection (`ConfigurationSnapshotStore.java`), which the README distinguishes from a runtime-published snapshot. There is no draft, managed-configuration validation result, or frozen candidate. The mounted-file REST loader is a runtime parsing path, not a draft validator.

The working tree has the research directory untracked; no pre-existing code edits were observed. Preserve that research artifact.

## Desired End State

A caller supplies the runtime-published `ConfigurationSnapshot` explicitly to construct each independent `ConfigurationDraft`. The draft retains that snapshot's durable `localId` as its base and the complete authored `ManagedConfiguration`. Replacing content allows invalid YAML and unresolved placeholders, invalidates any prior validation result, and leaves the source and other drafts unchanged. `freeze()` yields an immutable candidate with the base identity and authored content; later edits and loss of the draft reference cannot change it. A result can attach only to the exact current candidate used for validation. Source-labelled errors and their available locations remain available. The model has no storage, session authorization, lifecycle coordination, preparation, or publication side effects.

Acceptance criteria map to the model and tests below: independent complete drafts; explicit runtime base and no pointer dependency; stale-result rejection and diagnostic retention; stable frozen content; no persistence or independent coordination; and documentation that assigns integrated guarantees to later phases.

## Scope

### In scope

- One small in-memory draft model in `ai.loomspan.sidecar.storage`, next to the existing authored-content boundary.
- Immutable candidate, validation result, and diagnostic values needed by that model.
- Focused model tests and README documentation.

### Out of scope

- Editing APIs, server-session ownership, lease policy, draft registry, persistence, and browser behavior.
- Framework validation execution, YAML parsing, resource preparation/caches, REST client staging, runtime publication, and SQLite changes.
- End-to-end privacy, lifecycle, and concurrency claims. The ticket and roadmap assign those to Phases 2 and 3 (and transfer behavior to Phase 5).

## Active Project Guardrails

- Choose the smallest complete implementation; no speculative service, callback, registry, or compatibility shim (`ai/thoughts/design-lens.md`).
- Framework validation and publication remain authoritative through supported public `ai.loomspan.api` contracts. The model only stores a caller-supplied result; it must not interpret YAML or reach into framework internals.
- Continue to keep persisted snapshot selection distinct from runtime-published base identity. The one-admission-owner, trusted-identity, shutdown, and diagnostics guardrails are unaffected because this ticket adds no execution or management integration.

## Impact and Risk Analysis

- **Content fidelity and isolation:** Editing with a complete immutable `ManagedConfiguration` preserves document order, exact labels/text, REST text, unresolved references, and temporary invalid YAML. Its copied list, immutable `SkillDocument` records, and strings make sharing the source value safe. A draft replaces its own reference instead of mutating shared content.
- **Validation race:** Value equality alone would allow an old A result after edits A → B → A. Use a distinct candidate object per edit and identity comparison when recording a result. An old or foreign candidate is rejected even if content matches. A synchronized local edit/result operation can make that invariant atomic without claiming cross-session publication coordination.
- **Base identity:** The constructor accepts a `ConfigurationSnapshot` supplied by the future runtime service and reads only `localId` and `configuration`. It never calls `ConfigurationSnapshotStore.current()` or infers runtime state from `status`, `sourceId`, or history. The model trusts the caller to supply the runtime-published snapshot; Phase 2/3 must enforce that provenance.
- **Diagnostics:** A validation result defensively copies errors; each error stores its source label, message, and optional location string. The model does not fabricate locations or treat execution-input validation issues as configuration diagnostics.
- **Side effects and recovery:** No Spring bean, database migration/table, or publication call is needed. Losing a draft reference loses its ephemeral state; frozen candidates remain usable as immutable values. Phase 3 supplies actual session cleanup and privacy.

## Implementation Approach

Add `ConfigurationDraft` with a final base snapshot ID, a current immutable `FrozenConfigurationCandidate`, and an optional current `ConfigurationValidationResult`. Construct from `ConfigurationSnapshot`. `replaceContent(ManagedConfiguration)` installs a *new* candidate and clears validation on every edit, including equal-content edits. `freeze()` returns the current candidate. `recordValidation(candidate, result)` accepts only when the candidate is the current object; it returns whether the result attached. `validationFor(candidate)` exposes a result only for that same current object. Synchronize these small local methods to make replacement and result attachment atomic within one draft. This synchronization is an object invariant, not a session or publication coordination subsystem.

`FrozenConfigurationCandidate` contains the base ID and complete immutable `ManagedConfiguration`, with object identity semantics; do not override equality by content. `ConfigurationValidationResult` holds success/failure and a copied list of `ConfigurationValidationIssue` values. The issue value requires a nonblank source label and message; its optional location preserves the supplied diagnostic text. A failed result may have no structured errors if the future validator has only a general failure. The future Phase 2 service must check `validationFor(frozenCandidate).successful()` immediately before accepting ordinary Publish and prepare/stage afresh. This plan does not implement that service.

This approach is smaller than a per-document mutable editor, digest/version registry, or separate draft manager. Candidate identity handles both stale responses and A → B → A without hashes or extra revision bookkeeping. The candidate is internal and in-memory, so no serialized identity contract is introduced.

## Test Strategy

Use plain JUnit/AssertJ model tests with in-memory `ConfigurationSnapshot` fixtures; no Spring context, SQLite, network, credentials, or framework preparation. Preserve a mutable input list fixture to prove the `ManagedConfiguration` boundary copies it. Start with a failing test for the missing draft capability. Keep storage regression and ArchUnit checks in the related suite; run repository `verify` as the broad safe gate. Detailed cases and commands appear in the companion testing plan.

| Correct documentation and deferred integrated guarantees | README model section | Documentation review against ticket and roadmap; model tests make no end-to-end claims |

## Risks and Rollback/Recovery

The primary correctness risk is accidentally treating equal text or a stale response as current validation. The identity-gated test cases address it. The model's ephemeral state has no migration or persistent recovery operation; reverting the added classes/tests/docs removes the behavior. Session privacy, runtime-base invalidation, publication serialization, and transfer cutover require later integrated services and verification before deployment.
