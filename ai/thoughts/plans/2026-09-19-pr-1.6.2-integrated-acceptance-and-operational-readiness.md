# Integrated acceptance and operational readiness implementation plan

## Overview

- Ticket: `ai/thoughts/tickets/2026-09-19-pr-1.6.2-integrated-acceptance-and-operational-readiness.md`
- Research: `ai/thoughts/research/2026-09-19-pr-1.6.2-integrated-acceptance-and-operational-readiness.md`
- Outcome: Reproducible local evidence for the supported production Compose installation, including browser and mail journeys, two independent configuration stores, interruption and stopped-backup recovery, with an honest beta 5 release boundary.

## Current State

`scripts/verify-production.py` already brings up disposable production Compose with a test-only SMTP sink and deterministic JWT/model/REST host, checks first setup, HTTPS browser login, authored publication, execution, recreation, healthy backup restore and bounded shutdown. `ProductionComposeBrowserIntegrationTest` covers password links and Secure cookies, but not concurrent editing or import. `RuntimeConfigurationIntegrationTest` and `RuntimeConfigurationRecoveryIntegrationTest` cover many precise publication fault/restart boundaries with hooks, but the deployment script does not exercise an unusable volume or a second independent installation. The production Compose file contains only Sidecar; fixtures are added by a temporary verifier override. The working tree had only the Step 1 research artifact when planning began.

## Desired End State

The disposable deployment verifier and focused Sidecar tests collectively prove every acceptance criterion. Browser sessions traverse the real HTTPS console, while HTTP assertions check exact security and state transitions. Two separately stored deployments transfer only the authored configuration ZIP, each resolving its own URL binding. A stopped database backup restores accounts and the selected runtime after a deliberately unusable test volume. Deterministic Sidecar integration tests prove commit/publish interruption and generation/resource lifetime boundaries that cannot be reliably timed with container kills. The operator guide states exactly what was verified and what still awaits framework and Sidecar release work.

## Scope

### In scope

- Extend `scripts/verify-production.py` and `ProductionComposeBrowserIntegrationTest` with representative Compose/browser journeys and explicit assertions, reusing existing fixtures and APIs.
- Add only the small fixture controls and focused Sidecar regression tests needed for deterministic mail outage, publication boundary and recovery evidence.
- Align `examples/production/README.md` and `README.md` with verified steps, boundaries and actual acceptance results. Fix any defect exposed by these checks with a corresponding regression.

### Out of scope

- Production SMTP capture, new recovery or reconciliation APIs, online backup, Kubernetes, new framework SPI, framework rebuild/publication, dependency switch to released beta 5, release tags and Sidecar publication.

## Active Project Guardrails

- Favor the simplest complete change; no compatibility shim or general-purpose test platform.
- Framework validation, generation and skill execution remain authoritative through public `ai.loomspan.api` types. Sidecar owns transport, admission and retention; no internal/autoconfigure imports.
- Keep one execution admission owner, captured JWT identity and generation association, and the framework's single shutdown budget. Do not infer a complete diagnostic trace from observers.
- Use the locally installed `1.0.0-beta.5-SNAPSHOT` and matching framework checkout documentation.

## Impact and Risk Analysis

The highest risk is a verifier that passes on weak assertions or races. Use unique `.test` identities, separate cookie jars/browser contexts, explicit snapshot IDs, wait-for-state polling and bounded fixture coordination. Keep exact expected response classes and absence of state changes for negative cases. Never use a customer env file, real recipients or live services. Dispose of every Compose project/volume in `finally`, but retain failure logs long enough to diagnose. Volume corruption must be performed only on disposable stopped test data after taking a known-good stopped backup. Check `sidecar.db` and present WAL/SHM companions as a set and UID/GID after restore. The database-first publication contract does not promise recovery from arbitrary process kills; deterministic hook tests should establish selection outcomes at named boundaries, while Compose verifies startup and recovery behavior. A failed required check blocks any readiness claim.

## Implementation Approach

Extend the existing production verifier in stages. Its temporary Compose override, `send`/`login`/`execute` helpers and Playwright test entry point already own the deployment test. Add focused helpers for captured mail, isolated session/candidate operations, bundle multipart transfer, second project lifecycle, stopped-volume copy/restore and bounded status polling; avoid a separate harness. Use Playwright for interactions that specifically require a real browser (email links, HTTPS console, concurrent editor sessions and visible invalidation). Use direct HTTPS requests for exact API, CSRF, JWT, role, import/rollback and persistence assertions, while existing browser suites remain regression evidence for detailed UI behavior. Reuse the production image and host fixture for the second destination with its own Compose project, volume, ports, setup and `TARGET_URL`; its own host address/value must be observable in execution. Inspect ZIP content and history IDs to establish authored transfer without accounts/history. Prefer deterministic Java hook tests already present for accepted-update/disconnect and pointer fault timing; add a narrow missing case only if their assertions do not establish the ticket boundary. Do not add production hooks to induce faults.

## Test Strategy

Step 3 provides the exact test matrix. Start by running the current production verifier to establish the deployment baseline and first missing acceptance checkpoint. Use existing focused Java tests for deterministic fault injection and Playwright tests for browser semantics. Run the full Sidecar suite and disposable Compose verifier after changes. Every criterion needs executable evidence; a failed or unrun required check is reported as a readiness blocker.

## Acceptance-Criteria Traceability

| Acceptance criterion | Planned code/evidence | Planned test evidence |
| --- | --- | --- |
| Mail, HTTPS, setup, invitation, recovery, outage and lock | Phase 1 verifier/browser extension | Captured `.test` messages, link/cookie checks, outage/lock HTTP and JWT assertions |
| Authoring, execution, concurrent privacy/staleness, roles/CSRF and accepted updates | Phases 1–2 verifier/browser; narrow Java hook regressions | Browser contexts, exact management/API responses, REST/model results and publication IDs |
| Two-instance transfer, binding, invalid preservation, import and rollback | Phase 2 second project and ZIP assertions | Separate volumes/IDs/hosts, negative review/confirm, draft/lease and history assertions |
| Recreation, committed selection, invalid startup and shutdown generation | Phase 3 plus existing Sidecar fault tests | Container restart/failure, Java hook boundaries and `verify-shutdown.py` completion/cutoff |
| Stopped backup and unusable-state recovery | Phase 3 restore path and operator text | File-set/ownership checks, failed readiness, restored login, history and execution |
| Deferred checks, regressions and operator guidance | Phase 4 dated local evidence | Full Maven verification, image build and complete Compose verifier outcomes |
| Release boundary | Phase 4 readiness text | Review of pending gates and unchanged snapshot dependency; no publication/tagging |

## Risks and Rollback/Recovery

If a new integrated check exposes a behavior defect, repair the owning Sidecar path and rerun its focused regression and the relevant Compose flow. If Compose prerequisites are unavailable, report exact unrun commands and stop short of integrated readiness rather than replacing deployment evidence with framework tests. The test projects, volumes and certificates are disposable; restoration demonstrations use protected local copies of only their own stopped databases. No release or production state is changed.

## Implementation record (2026-09-19)

The conditional shutdown-script, runtime-hook and production-defect items
above were reviewed; their existing behavior provided the needed checks, so
no edits to those paths were necessary. Review #1 added a test-only Host
capture to the fixture so the destination binding is directly observable.
The verifier now waits for private
readiness after destination recreation and stopped restore: the public login
page can respond before selected-snapshot activation completes. No production
behavior change was needed.

The final `mvn verify` and `mvn package` runs each passed 260 tests with zero
failures/errors and three deployment-only browser methods skipped. The local
image build and complete disposable production verifier passed. The focused
recovery/runtime hook command passed 27 tests. The verifier's final shutdown
observations were SIGTERM exit 143 with admitted-work completion in 2.32 seconds
and cutoff in 4.46 seconds. The README contains the full local acceptance and
pending release-gate account. Framework publication and Sidecar release work
remain outside this ticket.
