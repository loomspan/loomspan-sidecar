# Protected Configuration Management Implementation Plan

## Overview
- Ticket: `ai/thoughts/tickets/2026-09-18-pr-1.3.3-protected-configuration-management.md`
- Research: `ai/thoughts/research/2026-09-18-pr-1.3.3-protected-configuration-management.md`
- Outcome: A logged-in management user can inspect the running configuration and retained submitted history; an editor or admin can validate and explicitly publish only the exact current candidate of their own leased draft, with truthful outcomes and fault gating.

## Current State

`ManagementEditingController` and `ManagementEditingService` own private session drafts, tabs, leases, and save/discard. `ManagementSecurityConfiguration` owns the CSRF-enabled management chain and role hierarchy; `/v1/**` uses the independent JWT chain. `RuntimeConfigurationService.validate(ConfigurationDraft)` currently calls framework `prepare`, stages REST resources, and reduces a skill failure to a generic issue. Its fair `publication` lock serializes the durable publication sequence, while `transition` and `ManagementEditingState` synchronize the brief activation/editing-state transition. The existing `publish(ConfigurationDraft)` checks candidate validation and base after acquiring `publication`, but cannot recheck management identity and grant. `ConfigurationSnapshotStore` offers current/detail/prune but no transactional retained-history listing. Internal `inspect()` exposes only IDs/status/fault and can read outside publication coordination. The `published` snapshot object can retain its original `PENDING` status after status recording, so HTTP must obtain current stored status separately. These findings match the research and were reread from the current checkout.

## Desired End State

Management GETs return one coherent runtime-published snapshot, retained submissions in sequence order, and distinct published/intended/status/fault fields. Only authenticated management users receive literal authored content. An editor/admin can request validation of their own leased exact candidate without activation or durable submission, and can publish only a currently successful validated candidate after live admission at the publication lock. Rejected publication leaves runtime unchanged; accepted work keeps its frozen content despite later session or draft changes. Responses distinguish pre-admission conflicts, validation failure, pre-activation failure, revert fault, and activation followed by bookkeeping fault. Existing execution authentication, dispatch, client retirement, and shutdown budget remain intact.

## Scope
### In scope
- Protected configuration GET, validation, and Publish HTTP contracts and access rules.
- Candidate diagnostics and lifecycle, public framework validation integration, REST checks and temporary resource cleanup.
- Serialized admission, coherent inspection/history, truthful publication outcomes and mutation faults.
- Sidecar tests, README/API/operator documentation.

### Out of scope
- Browser authoring UI, automatic-check scheduling/debouncing, transfer, rollback, cancellation, durable jobs, new framework contracts, framework rebuilding/release, and snapshotting account or deployment settings.

## Active Project Guardrails

- Use the simplest complete implementation; replace obsolete development paths directly without compatibility shims.
- The framework remains skill validation/execution authority. Production and tests depend on Loomspan Java types only under `ai.loomspan.api`; retain `SupportedLoomspanApiArchitectureTest`.
- Preserve trusted execution JWT identity, execution dispatch during update, and one framework shutdown budget.
- Keep authored text and useful public diagnostics intact while preventing foreign private-result and resolved-secret disclosure.
- Use the installed beta 5 snapshot and matching local framework documentation; no framework rebuild, dependency switch, release, tag, or live external service in this ticket.

## Impact and Risk Analysis

- **Admission race:** Security-chain authorization happens before waiting for `publication`; account version/role, idle session, tab/grant/lease, candidate ID, validation and runtime base must be checked again at the lock's admission point. The account mutation path already synchronizes `ManagementEditingState`; keep lock order `publication → transition → state`, release `transition/state` immediately after freezing, then prepare/stage/commit under `publication`. Never hold all editing through preparation.
- **Validation race:** `ConfigurationDraft` uses reference identity, including equal-content edits. Validation work may outlive a draft edit, discard, lease/session loss or successful publication. A late result must not attach or return old diagnostics as though current. No validation/status request calls activity reporting.
- **Publication truth:** The database pointer is intended production; the in-memory published snapshot is execution truth. A pending status is unknown even if a reconnecting client suspects an outcome. Stage-specific results and fault codes must not turn status-recording failure after activation into an activation failure.
- **History consistency and exposure:** Snapshot text can contain secrets. All new management responses need no-store behavior already applied to management APIs, role authorization and no public/JWT-only access. Snapshot list/detail and runtime/intended/status are captured under publication coordination; store list/detail use one transaction so multi-query header/document loads cannot mix with pruning. Missing IDs return absent, not inferred failure.
- **Resource ownership:** Validation calls public `validate` with the full proposed skill set and uses `ValidatedSkill` metadata only when valid. REST preparation remains temporary and must close even if route checks fail; Publish still prepares and stages afresh. Avoid logging authored YAML, resolved URLs, client exception messages or literal secrets.

## Implementation Approach

Use `/api/management/configuration` as the bounded new API root. GET `/current` returns `{published: <full snapshot>, intendedId, intendedStatus, mutationFault}`; GET `/history` returns retained full snapshot records in ascending `submissionSequence`; GET `/history/{localId}` returns a full snapshot or 404. Full records contain `localId`, nullable `sourceId`, `submissionSequence`, `status`, and `configuration` (`skillDocuments` and `restRoutesYaml`). Including complete history content satisfies viewer inspection without a second list/detail consistency protocol. A list is a point-in-time retained set; a subsequent detail may return 404 after pruning. GET is side-effect-free except the existing inspect-read failure may set a mutation fault.

POST `/api/management/editing/draft/validate` accepts `{tabId,grantId,expectedCandidateId}` and returns `{draftId,candidateId,baseSnapshotId,applied,validation}` on an attached result; `validation` has `successful` and issues with `severity`, `sourceLabel`, nullable `skillName`, nullable `location`, and `message`. A warning-only framework result succeeds. A stale, discarded, revoked or changed candidate returns 409 with a stable machine-readable code and no discarded diagnostics; no result is retained for another session. GET `/editing/draft` continues to expose only that session's current attached result. POST `/api/management/configuration/publish` accepts the same three capability fields and returns the published full snapshot on success. All POSTs require CSRF. JSON errors use `{code,error}` with no sensitive cause: 400 malformed input, 401 absent/expired session, 403 missing role/CSRF, 404 expired history, 409 stale grant/base/candidate or missing/failed validation, and 503 mutation fault/storage unavailable. Publication faults after acceptance use 503 and distinct codes `commit_failed`, `activation_failed`, `revert_failed`, `outcome_recording_failed`, or `history_pruning_failed`; include runtime/intended IDs and known status/fault from coordinated inspection where available. `activation_failed` means the attempted activation was rejected and revert succeeded; `outcome_recording_failed` states activation occurred and bookkeeping is unknown. Do not expose raw exception text. Treat a local HTTP disconnect as no cancellation of accepted synchronous work; it has no separate job token and a reconnect uses GET inspection/history.

The runtime service owns publication serialization and typed stage outcomes. The editing service owns session/account/role/tab/grant/candidate checks and supplies an admission callback to the runtime publisher; the callback runs only after the fair publication lock is acquired, while a short transition/state gate freezes an immutable candidate and its validated result. The runtime service then executes the existing database-first publication from that frozen value. This avoids moving account concepts into the publisher and avoids using a controller precheck as authority. Existing internal test-only calls should be updated to the revised service boundary rather than preserved with a compatibility bridge.

Implementation placement: the authenticated HTTP integration test lives in the `configuration` test package so it can use the existing package-private publication hooks for bounded race and fault cases. The publisher accepts an opaque validated-candidate token created only by `ConfigurationDraft`; direct service tests use that same boundary.

### Material alternative considered

Checking management access in the controller and passing its `ConfigurationDraft` to `publish` is smaller but allows a queued request to publish after its role, session, grant or base becomes invalid. Keeping the state/transition gate through preparation would block editing for the whole slow phase. Both violate ticket behavior.

## Acceptance-Criteria Traceability

| Acceptance criterion | Planned code evidence | Planned test evidence |
| --- | --- | --- |
| Role, CSRF, draft privacy and JWT separation; no implicit activation | Management controllers/security and pure validate | HTTP role/CSRF/session/JWT matrix; unchanged runtime/history after read/save/validate |
| Coherent published/history status and expiry | Coordinator read lock; store transactional list/detail | Latch publication/prune reads, pending/failed content, source/sequence, 404 expiry |
| Public framework validation, metadata, REST checks, resource release | `RuntimeConfigurationService`, `RestRouteCatalogValidator`, result records | Full-set additions/removals/kind, warnings/errors, route/URL/SSL/auth checks, no generation/history |
| Changed/discarded/expired validation never promotes newer draft | `ManagementEditingService` final recheck; `ConfigurationDraft` identity | Equal-content edit and late-result HTTP/service races; idle deadline unchanged |
| Lock-time Publish admission and accepted frozen work | Admission callback inside publisher lock; short transition/state gate | Queued role/session/grant/base races; post-accept logout/takeover/edit/disconnect |
| Database-first fault truth | Typed runtime stages and HTTP mappings | Real SQLite/framework success/commit/publish/revert/status injection; inspect execution truth |
| Invalidation, failed preservation, dispatch/shutdown | Existing transition clearing and generation lifecycle | Concurrent editing, failed attempt, execution during update, shutdown regression |
| Docs and broad Sidecar verification | README and architecture boundary | `verify` plus targeted suites, no framework-only substitution |

## Risks and Rollback/Recovery

These are development changes with no compatibility shim. Revert the ticket diff if the new workflow is rejected before release. At runtime, do not retry an ambiguous Publish after a connection loss or bookkeeping fault: query current/history, treat pending as unknown, and follow the existing stopped full-database-backup recovery procedure for mutation faults. An accepted operation is synchronous and not guaranteed across process crash. Preserve source YAML and database contents for investigation without echoing resolved secrets in errors/logs.
