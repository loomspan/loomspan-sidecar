# Python SDK adoption and completion testing plan

## Change Summary

Verify the maintained suite against the installed Python SDK and the real Sidecar, including the shared public API projection, key/trust deployment, business parity and the installed support matrix. The [implementation plan](PR-10.6-python-sdk-adoption-and-completion.md), [research](../research/PR-10.6-python-sdk-adoption-and-completion.md) and [ticket](../tickets/PR-10.6-python-sdk-adoption-and-completion.md) govern the work.

## Impacted Areas and Risks

| Category | Risk | Planned evidence |
| --- | --- | --- |
| Identity and routing | Raw login token reused on callbacks, wrong issuer/subject/roles, callback mount bypass or unusable trust | Authenticated public calls, real SDK middleware across the prefix, Java/Sidecar receivers and exact callback credential, negative principal tests |
| Output and side effects | Result text reserialized, omitted diagnostics confused with empty, duplicate poll or replay, approvals relabeled | Exact adapter fields, real deterministic replay and commitment/recovery, attempted-send and synthetic-effect counters |
| Runtime and packaging | Extra missing, stale private key replaced, old public inode pinned, portable install requires SDK source | Wheel/sdist installation and `pip check`, PEM byte preservation, atomic public directory change, verified and tampered portable archive cases |
| Platform and deployment | Missing native cell, trust disabled at one actual hop, hidden platform/dependency mismatch | Six native cells, representative lower/current dependencies, real direct TLS and paired Caddy mTLS with negatives |

## Existing Coverage and Environment Constraints

- Suite pytest, `scripts/smoke.py`, `scripts/run_suite.py mock` and `scripts/run_sdk.py` provide focused tests, PKCE/compose smoke, frozen replay and Java-only topology tooling. The current suite glue tests intentionally assert a literal kid and source expiry cap. Replace those superseded expectations. No model/provider traffic or use of the retained suite `.runtime` is permitted.
- SDK pytest already covers PEM, atomic replacement, TLS, transport, trust and lifespan. `verify_distribution.py` exercises external installs and examples. `verify_java_issuance.py` and `verify_java_callbacks.py` cover actual Java cryptographic boundaries. Run them with the final installed wheel, and separately prove HTTP composition. Sidecar Maven verify retains the Framework public-boundary check and uses the already installed beta.9 snapshot.
- Windows x86-64 with CPython 3.13 and Docker Desktop Linux amd64 are available. The Windows Maven repository holds the Framework snapshot. Native Linux x86-64 Python may run in WSL with a native uv and interpreter; execute Linux container recipe services through the shared daemon. Verify actual tool/interpreter availability. No macOS ARM64 machine is currently identified. Linux/Windows checks, implementation and review can proceed independently. Native macOS is still a mandatory support/sync gate.

## Tests to Add or Update

### 1. `test_sdk_execution_boundary` and callback prefix tests

- Type and location — App/wire tests in suite `tests/test_execution_identity.py`, with caller projection tests in `tests/test_suites.py`.
- Proves — A valid Keycloak request issues a distinct execution token. Exact role intersection, issuer/subject, type/purpose/audience, key derivation and configurable lifetime survive the real client exchange. Two owners get distinct credentials with no header crossover. The old callback alias is absent. Unauthenticated `/skills`, unknown descendants, wrong-key/wrong-purpose/expired credentials and Keycloak bearer tokens cannot reach business logic. Authorized callback token authenticates, and role/record denial still applies. Invalid role shape and unauthenticated public requests emit no Sidecar exchange. Startup fails for bad key or invalid lifetime with no replacement.
- Fixture and isolation — Synthetic PEM, locally signed login tokens or verified identity injection as appropriate, tmp_path databases and real SDK guard with no-network ASGI tests plus loopback transport. Test 900 seconds and a shorter explicit setting. Check generated routes still use `/skills` and only current declarations can dispatch.

### 2. `test_public_execution_projection`

- Type and location — HTTP contract integration in suite `tests/test_suites.py` with the installed SDK talking to a controlled local HTTP peer.
- Proves — 202 with string ID, unchanged one-poll 200 shape, exact whitespace/non-ASCII result text, timestamps and nullable keys, failure kind/message/issues, nested event details including large finite numeric values, absent versus empty events. Compare the wire-supported Sidecar problem object and status for validation, denial and missing owner. Missing problem body is safe, malformed read gives 502, malformed ID is rejected locally, and malformed or lost acceptance is explicit with one send. `resolveEquipment` success/failure and TypeSafe impact retain app-level semantics.
- Fixture and isolation — Replay real public response shapes from `ExecutionController` and `SkillExecutionEvent`, including optional/null fields. Capture request counts and ensure a successful status read is never replaced by a wait loop. Use controlled boundaries for HTTP errors and sanitized problem data; no real tokens in reports.

### 3. `test_runtime_sdk_artifact` and provisioning regressions

- Type and location — Suite `tests/test_runtime_build.py` and `tests/test_execution_identity.py`.
- Proves — Exact wheel staging/name/version/digest, missing and tampered wheel fail before portable initialization, and exported archive includes the authorized wheel and JARs but no private material or database. An existing valid PEM and existing operational state are preserved, public trust lives in a separately mounted directory, and a partial existing workspace never silently gains a new signer. Check fresh provision, repeated prepare, old public-only state, missing/invalid PEM and an SDK export replaced by atomic rename through a mounted directory.
- Fixture and isolation — Temporary roots and synthetic public/private fixtures; no touch of retained suite state. Finish with the real source-build and portable-install smoke, whose in-container `importlib.metadata`/`pip check` checks verify the staged wheel and dependency solution.

### 4. `verify_sdk_commitment` and retained replay

- Type and location — Provider-free business acceptance in suite `scripts/verify_sdk_commitment.py`, existing `scripts/smoke.py` and `scripts/run_suite.py mock`.
- Proves — Real Keycloak PKCE and each actual host execute the eight lookup bodies and the ninth nested approval. Existing smoke verifies role denial and invalid assessment rejection, mock all preserves the exact frozen equipment and TypeSafe results, and the focused commitment proves a valid approval creates one `PENDING_DISPATCH` record, ownership/recovery is correct, repeated exact explicit request returns its receipt and a changed or unauthorized request cannot commit. Verify data and fixture hashes before/after, exact accepted namespace identities, and zero provider/model access beyond synthetic fixture consumption. Do not promote new output into accepted packs.
- Fixture and isolation — Fresh isolated Compose workspaces, immutable accepted inputs and newly registered case IDs/approval keys. Compare both hosts after accounting only for generated identity fields and the intentionally different issuer representation. Check unchanged approvals/quote data and no prior-row mutation. Preserve original and namespaced packs.

### 5. `run_python_sdk` recipe scenarios

- Type and location — Suite `scripts/run_python_sdk.py` and `tests/test_python_sdk_runner.py`. Test preflight, generated topology, output uniqueness, provider isolation and failure/cleanup reporting locally. Run real recipes in the isolated Docker Linux environment.
- Local — Installed plain Python client, actual Sidecar and installed FastAPI callback fixture. Prove Python-issued credential signature, derived kid and exact JWT profile are accepted by Sidecar. Prove a Java-issued credential is accepted by the live Python verifier with explicit same-issuer public trust. Compare issuer/subject, role names including prefixed-vs-literal negatives, exact credential digest, zero body length on bodyless declared operations and authorized principal before effect. Test wrong owner, wrong role, expiry before dispatch, absent or malformed current file, trusted-key overlap and withdrawn/restored old-key validation. Use bounded poll and observable barriers; avoid fixed timing assumptions about asynchronous reload. The maintained equipment suite's ninth-operation commitment is evidenced separately.
- Standard — Run verified HTTPS invocation and HTTPS callback with positive and wrong CA/host cases. Verify correct actual endpoints, zero accepted application requests on rejected transport, and exact result/failure/diagnostic retention. Check known submitted token and JWT trust independently of the certificate chain.
- Hardened — Run positive paired Caddy mTLS, reject wrong client peers and untrusted servers in both directions as applicable and assert the private loopback backend is unreachable from unauthorized peers. Preserve authorized request headers and credential fidelity. No use of insecure SSL contexts or TLS verification disablement.
- Fault coverage — In one secure recipe, let each fault peer receive and forward once, lose submission response after admission and lose callback response after a synthetic effect. Verify client `AcceptanceUnknown`, real terminal callback failure, one observed attempt and one effect for each case, and no delayed retry after bounded observation. Use deterministic fixture or HTTP skill only. Capture sanitized counts and statuses. At all hops use provider-disabled runtime and fresh secrets/material only.

### 6. Installed distribution, native matrix and Java verifier tests

## Safe Verification Commands

Use new artifact and evidence directories outside retained runtime state. Run Sidecar Maven from the Windows host if only it has the installed Framework snapshot. Use absolute wheel, Sidecar checkout/JAR and artifact-directory paths in shell variables. All commands below are planned. Commands with the two new suite scripts or the distribution verifier's new options become executable when those changes land.

### Focused suite and final component checks

- Build wheel and sdist from Sidecar once per changed source state with `uv build --out-dir <new-dist-dir> sdks/python`. Identify the sole wheel and sdist by filename and hash. In a clean suite venv, install `python -m pip install -r requirements.lock "<absolute-wheel-path>[fastapi]"` and `python -m pip check`. For the red test before the updated lock, use the existing suite venv and SDK test fixture tooling separately if needed, so legacy dependency conflicts do not stand in for the intended assertion failure.
- Suite focused `python -m pytest -q tests/test_execution_identity.py tests/test_suites.py tests/test_runtime_build.py tests/test_python_sdk_runner.py` and full `python -m pytest -q tests` from the suite root. Install local Chromium with `python -m playwright install chromium` for actual PKCE checks if the test venv lacks it.
- Sidecar `mvn -B -ntp verify` and Java SDK `mvn -B -ntp -f sdks/java/pom.xml clean install`. Retain the production Maven configuration and use the installed snapshot. In Sidecar root with the final wheel installed, run `python sdks/python/tests/verify_java_issuance.py` and `python sdks/python/tests/verify_java_callbacks.py` where Maven and snapshot are available. Run `python -m mypy --strict sdks/python/src/loomspan_sdk sdks/python/examples/fastapi_app.py` with the pinned dev requirements and installed extra.
