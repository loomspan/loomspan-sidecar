# Java SDK Callback Trust Startup Testing Plan

## Change Summary

Exercise failed SDK callback trust initialization, safe runtime diagnostics and independent request authentication. Verify that Sidecar can still wait for the colocated application's first public export. The final checks cover the combined PR 11.1–11.3 baseline.

## Impacted Areas and Risks

| Category | Risk | Planned evidence |
| --- | --- | --- |
| Startup and cleanup | Servlet app starts with unusable trust or leaves a daemon after startup fails. | Web context failure matrix, actual Boot lazy startup, and deterministic reader counts and thread checks. |
| Runtime and request security | Own-key fallback remains after trust is withdrawn, recovery needs a request, or admitted work is interrupted. | Poller-driven HTTP status changes and a latch-controlled MockMvc callback in a single context. |
| Diagnostics | Parser or filesystem exceptions expose material, or repeated reads produce repeated logs. | Capture startup cause and log events with synthetic markers. Exercise polling logic and miss-triggered refresh against the same failure category. |
| Concurrency and retained behavior | Partial keys become visible, miss rate limiting regresses, or Sidecar adopts the SDK startup rule. | Existing immutable-snapshot and refresh tests, separate Sidecar tests, and provider-free recipe checks. |

## Existing Coverage and Environment Constraints

Use the starter's existing JUnit, AssertJ, WebApplicationContextRunner and MockMvc patterns, with generated RSA material and `@TempDir`. `CallbackJwtTrustTest` already has an injected reader and monotonic ticker plus an actual polling test. `CallbackJwtDecoderTest` covers generic errors, and the starter security tests exercise independent authentication, exact authorities and ordinary browser policy. The existing starter test dependency supplies Boot output capture and logging test support. The root `JwtStartupIntegrationTest` uses a real loopback server and a temporary database.

The SDK reactor and the root Sidecar build have separate Maven entry points. Use Java 21 or newer and the locally installed Framework `1.0.0-beta.9-SNAPSHOT` for Sidecar. Run the sibling lanes with their existing venv and Docker daemon. They start only isolated fixture services with synthetic keys, temporary databases and an offline provider. Do not pass through host provider configuration. The four existing sibling PEM fixture changes are part of the combined verification checkout and must be preserved.
