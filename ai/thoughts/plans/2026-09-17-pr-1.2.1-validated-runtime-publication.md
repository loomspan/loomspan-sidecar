# Validated Runtime Publication Implementation Plan

## Overview

- Ticket: `ai/thoughts/tickets/2026-09-17-pr-1.2.1-validated-runtime-publication.md`
- Research: `ai/thoughts/research/2026-09-17-pr-1.2.1-validated-runtime-publication.md`
- Outcome: activate the committed SQLite selection at startup and serialize complete, validated runtime replacements while preserving generation-matched REST resources and durable execution correlation.

## Current State

`ConfigurationSnapshotStore` already initializes the empty database, loads the intended pointer without filtering its status, atomically submits a pending replacement, atomically reverts and marks failure, records status, and prunes with caller-supplied protection. `ConfigurationDraft` distinguishes an exact frozen candidate by object identity, so even an equal-content edit invalidates validation. Neither has a framework-backed service. `StorageConfiguration` currently prunes with an empty protected set during bean creation.

The framework starts from mounted `loomspan.skills.locations`; `RestRouteLoader`, `RestTargetClients`, `RestRouteCatalogValidator`, and `GenericRestSkillHandler` construct one mounted REST configuration. Discovery and POST prechecks use injected, permanent startup `SkillCatalog`. `ExecutionCoordinator` starts open; its worker handoff captures a framework admission but does not retain the corresponding durable snapshot ID. The current README and deployment examples describe mounted configuration. These facts were rechecked against current source after the research handoff.

The matching local framework documentation and public API specify `SkillReloader.prepare(Collection<SkillDocument>)`, `publish`, `snapshot`, `onGenerationRetired`, and trusted generation IDs on admitted and REST invocations. The API provides no transaction with Sidecar's database. Apache HttpClient 5.6.1's `InternalHttpClient.close()` defaults to `CloseMode.GRACEFUL`, while `close(CloseMode.IMMEDIATE)` is available through its public modal-close API; use immediate close for bounded post-retirement and post-cutoff cleanup.

## Desired End State

Startup loads the selected complete authored snapshot, prepares it, stages its REST resources and generation mapping, publishes it, records `PUBLISHED`, prunes with live protection, and only then opens execution dispatch. An ordinary update validates an exact draft candidate without durable side effects; Publish rechecks its runtime base, prepares/stages anew, commits pending B, publishes B, and records B as published. All ordinary failures preserve A at runtime; fault states explicitly expose any intended/runtime divergence or failed outcome bookkeeping. Discovery and prechecks use `SkillReloader.snapshot()`. Each captured execution and nested REST invocation uses its own generation's resources, including after another generation becomes current.

Acceptance criteria are mapped individually below. The ticket's explicit Phase 3, Phase 5, and Phase 6 ownership boundaries remain in force.

## Scope

### In scope

- Startup gate, selected-snapshot activation, current catalog lookup, validation and serialized publication service, internal inspection/fault state, protected pruning.
- Generation-keyed REST routes/clients, process-environment-only URL bindings, retirement and shutdown cleanup.
- Execution snapshot correlation, startup/publication/fault/recovery tests, and direct replacement of obsolete mounted configuration/deployment guidance.

### Out of scope

- Management/UI endpoints, Phase 3 authorization/session/lease implementation, Phase 5 import/export and destructive cutover, online repair, new framework SPI, release/tag/CI publication.

## Active Project Guardrails

- Use only supported `ai.loomspan.api` types in application and tests; framework validation/invocation remain authoritative. Keep the ArchUnit prohibitions and no Java `@SkillMethod` skills.
- Preserve one admission owner/retained execution record and JWT context across worker handoff; observer diagnostics are optional and never an authority for correlation.
- Stop dispatch promptly on close, preserve clients through the framework's existing completion/cutoff, then clean up without a second drain.
- The ticket replaces the design lens's beta 4 startup-only configuration decision. Prefer a direct replacement over compatibility shims or another configuration source.
- Build against the developer's installed beta 5 snapshot; no framework rebuild, release, or source/artifact verification step.

## Impact and Risk Analysis

The nontransactional database/framework boundary makes commit, publish, revert, and status faults materially different. The service must order them and keep runtime truth separate from intended selection. A published B cannot be undone by a later status-write failure. Crash recovery is intentionally database-first, including committed pending B.

Framework retirement is concurrent, may occur before `publish` returns, and omits never-published candidates and possibly shutdown. Stage mapping and clients before publication, make removal idempotent, and enqueue close work without blocking the callback. Publication and pruning share a serialized boundary so a candidate or live generation cannot be pruned between selection and protection. Pending admissions and physically running nested descendants are protected by the framework's retirement decision, not a Sidecar TTL.

Resolved REST URLs are sensitive deployment values. Parse authored REST text in memory; log only source labels/field paths and safe reasons, never full resolved URLs or arbitrary exception messages. Other REST placeholder behavior, JWT passthrough, response caps, and SSL bundles remain as implemented.

## Implementation Approach

Add one internal runtime service, for example `ai.loomspan.sidecar.configuration.RuntimeConfigurationService`, as the serialization and state owner. It holds a fair lock covering update admission/base check, freeze, prepare, REST stage, commit, publication, status/reversion, and prune. Waiting attempts recheck all preconditions under that lock. Use an immutable inspection value with published ID, intended ID/status, and nullable fault reason/state. The service accepts `ConfigurationDraft` for ordinary Publish and exposes no public unchecked-validation bypass. A private common prepare/stage/publish path can later serve the separately authorized Phase 5 cutover. Phase 3 can join the same lock for real draft/lease admission and short post-success invalidation, without speculative registry or callback machinery here.

Use a small generation resource registry shared by the fixed handler and runtime service: key is trusted process-local generation ID; value contains immutable route catalog, target clients, and durable snapshot UUID. Its publication staging and mapping lookup are thread-safe. A retirement callback only removes/schedules close; a single owned cleanup executor performs immediate client close, with idempotent per-resource closure. During shutdown, let framework `SmartLifecycle` phase `Integer.MAX_VALUE` stop first; Sidecar cleanup's lower phase closes remaining clients after completion/cutoff. Stop execution on `ContextClosedEvent` as today and disable callback reliance once shutdown starts. Ensure cleanup executor shutdown does not wait beyond the framework budget. Do not cache validated candidates.

Replace the eager file loader with a parser accepting authored REST YAML plus a safe source label. Preserve the existing field parsing and Spring placeholder behavior except `base-url`, which is either a literal valid URL or exact `${NAME}`. Resolve that form only through `System.getenv(NAME)` after checking an exact `loomspan-sidecar.url-variables` allowlist; reject every other `${...}` form or composed template before URL validation. Persist only original `ManagedConfiguration`; never write resolved route data to the store.

Configure documented `loomspan.skills.locations` to a controlled empty classpath pattern such as `classpath:/sidecar-empty-skills/*.yaml`; include a non-YAML marker under that directory so the source exists in the packaged application, and assert `SkillReloader.snapshot().skills()` is empty before activating database content. Use a startup runner or equivalent after framework/context creation, with `ExecutionCoordinator` initialized closed and opened only after all required activation/bookkeeping succeeds. The port may be bound during Spring startup, but actual execution dispatch remains closed. Register retirement first. Move initial pruning out of `StorageConfiguration` into this initialized runtime lifecycle. Do not depend on internal framework lifecycle types in Sidecar.

### Publication state sequence

1. `validate(draft)`: freeze the current candidate, prepare its full documents, parse/validate REST routes against the prepared catalog, build clients, then close validation clients. Return safe labelled issues using public source/location information where available, with an aggregate candidate label when the public exception offers no document location; never echo resolved URLs or arbitrary exception text. Call `draft.recordValidation(candidate, result)`; stale results are ignored. No store write or retained prepared update.
2. `publish(draft)`, under the serialization lock: reject fault state, freeze and require that exact candidate's successful validation, compare `candidate.baseSnapshotId` with *runtime published* ID, prepare again, stage routes/clients under the new generation, then call guarded `store.submit` to switch intended A to pending B. B's durable ID exists only after submit; associate it with the staged generation before framework publication. Protect the accepted in-flight update throughout this interval.
3. On commit failure, remove and close unpublished staging; A remains runtime/intended. On framework publish failure after commit, call `store.revert(B,A)`; success leaves A intended/runtime and B failed. If revert fails, leave intended B, runtime A, preserve B pending/unknown, set mutation fault, and retain A's live resources. Clean up only unpublished B.
4. On publication success, set in-memory published ID to B before any later storage operation. Then `store.updateStatus(B,PUBLISHED)`. If this fails, retain B runtime/resources and intended B, leave pending unknown, set mutation fault; do not revert. A retirement may already have been enqueued. Successful transition is the future Phase 3 invalidation point, even if this status write fails.
5. Prune at startup and after completed attempts when the database is usable, using the union of staged/live generation IDs and in-flight A/B IDs. Coordinate this under the same lock and do not prune on retirement itself. If pruning fails, surface an operator-visible storage fault without changing published runtime. Do not misreport a published generation as rejected because bookkeeping failed.

No live external model, remote REST target, production database or management endpoint is required.

## Risks and Rollback/Recovery

If an update fails before commit, A remains selected and active; unpublished resources close. If publication fails after commit and revert succeeds, B remains immutable failed history and A continues. Failed revert is a mutation fault with active A and selected B; failed post-publish status is a mutation fault with active/selected B and pending outcome. Do not repair either online. Stop the sole instance, preserve a consistent copy of its full SQLite database set, correct storage, and restart when committed selected content is wanted. An unreverted A/B restart activates B. To restore prior configuration, restore a known-good stopped-instance full database backup, restart, and verify activation/readiness; every database table returns to that backup point. Startup records the selected snapshot as published but leaves unrelated pending history unknown.

Any startup load, preparation, REST staging, publication or status failure must abort readiness/dispatch with actionable secret-free diagnostics. A failed cleanup should be logged without deleting live resources or hiding the primary failure. The implementation step should inspect exact Spring lifecycle ordering as it wires the shutdown phase and verify it with real shutdown tests.
