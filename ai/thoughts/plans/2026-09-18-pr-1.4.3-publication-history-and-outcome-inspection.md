# Publication History and Outcome Inspection Implementation Plan

## Overview
- Ticket: `ai/thoughts/tickets/2026-09-18-pr-1.4.3-publication-history-and-outcome-inspection.md`
- Research: `ai/thoughts/research/2026-09-18-pr-1.4.3-publication-history-and-outcome-inspection.md`
- Outcome: Authorized console users can inspect complete retained submissions and accurately relate recorded outcomes, runtime state, restart intent, and mutation faults after reconnecting, without exposing private drafts or adding recovery mutations.

## Current State

The protected server contract is already complete for this ticket. `ManagementConfigurationController` exposes the runtime/intended/fault view, the authoritative oldest-first retained list, and exact UUID detail lookup. `RuntimeConfigurationService.history()` and `history(UUID)` serialize with publication and pruning, while `ConfigurationSnapshotRepository` reconstructs each immutable snapshot from one submission sequence. A detail ID can nevertheless expire between the list and detail requests, and the controller reports that as `history_not_found`.

`ManagementPagesController` currently serves current and editing pages but has no history or recovery-guidance route and no history navigation link. `console.js` safely renders authored current configuration with text-only DOM APIs, but it only understands current and account roots and displays raw status/fault fields without outcome semantics. The editor already avoids automatic publication retry after a transport loss, and session activity is reported only from explicit user events. `README.md` documents the protected inspection APIs and offline stopped-instance recovery, but not the completed browser history workflow.

## Desired End State

All management roles can reach a protected history page from any console page, including the editor after a reconnect or new login. The page presents the retained list in API order with local UUID, optional source UUID, sequence, textual recorded status, and an explicit marker when an entry matches the separately fetched runtime-published snapshot. Selecting an entry loads that UUID through the detail API and renders its complete skill and REST YAML as inert text; the response UUID must match the selected UUID before content is displayed.

The current and history views describe `PENDING` as recorded outcome unknown, never as failure or success. They distinguish the runtime-published UUID from the SQLite restart selection, explain match or mismatch, preserve the stored status even when a pending snapshot is running, and describe mutation-fault restrictions from current evidence only. A protected, read-only recovery-guidance page supplies a stable console link to the existing offline procedure: stop the sole instance, preserve the full SQLite database set, correct storage/restart when the intended selection is wanted, or restore a known-good stopped backup when recovering the prior runtime from an unreverted mismatch. It adds no online repair control.

An expired detail clears any prior detail content, explains that retention pruning removed the requested snapshot, and offers a refreshed list plus the current-configuration link. Inspection remains explicit/read-only and does not poll, renew a lease or login, retry publication, cancel work, pin history, expose another session's draft, or add rollback/import/export controls.

Acceptance-criteria mapping:

- Complete retained submitted content, identities, order, statuses, role access, and safe rendering are delivered by the protected history shell plus the existing list/detail APIs and text-only DOM construction.
- Runtime, intended, recorded outcome, and mutation-fault meanings are rendered from the existing current response without rewriting stored status or inventing an operation history.
- Global navigation, current/history cross-links, and recovery guidance make inspection available after disconnect/relogin without draft recovery or another publication action.
- Exact detail fetches and UUID validation prevent mixed identity/content; `history_not_found` becomes an explicit expiration state with refresh/current choices.
- authenticated HTTP and Playwright coverage proves permissions, keyboard/text feedback, private-draft separation, reconnect, and idle expiry.
- `README.md` becomes the user/operator reference for history, retention, unknown outcomes, state mismatch, restrictions, and recovery.

## Scope

### In scope
- Protected history and operator-recovery page shells and global console navigation.
- Browser rendering for retained list, exact snapshot detail, current/intended comparison, status semantics, mutation restrictions, and expired-entry recovery.
- Accessible native controls, focus behavior, live textual feedback, and safe rendering of authored content.
- Authenticated HTTP and Playwright regression coverage using the installed beta 5 snapshot.
- User/operator documentation for the completed inspection workflow and recovery boundary.

### Out of scope
- Changes to storage schema, retention rules, publication locking, inspection API payloads, or framework contracts.
- Durable jobs, reconstructed operation stages, automatic reconciliation, retry, or cancellation.
- Draft sharing/recovery across sessions or access to another session's validation results.
- Import, export, rollback controls, destructive transfer confirmation, or an online repair endpoint.
- Framework rebuild, release dependency switch, hosted CI, release, or tagging.

## Active Project Guardrails

- Choose the simplest complete implementation; reuse the existing page controller, static assets, protected APIs, and native browser controls rather than adding a frontend framework, new server DTO, or client state subsystem.
- Framework execution and generation identity remain behind the supported `ai.loomspan.api` boundary. Durable browser identity is the Sidecar snapshot UUID; no framework generation ID is exposed or persisted for this UI.
- Snapshot status is bookkeeping. The runtime snapshot and intended pointer retain their separate authority, and retained snapshot content/identity is not duplicated into a second browser-side history model.
- Preserve complete authored diagnostic/configuration text without interpretation or truncation; private drafts remain session-owned and outside history.

## Impact and Risk Analysis

The primary correctness risk is misleading users about an uncertain or faulted publication. Presentation rules must be based only on `published.localId/status`, `intendedId/intendedStatus`, and `mutationFault`: pending is always outcome-unknown; UUID equality says runtime and restart selection match but does not upgrade status; mismatch says execution and restart selection differ; and a non-null fault says managed-configuration mutations are stopped. Older rows have no actor, timestamp, or per-attempt fault data, so the UI must not imply any.

History contains literal sensitive values and authored markup. The existing management authorization and no-store/no-referrer filters remain the security boundary; all dynamic values must continue to use `textContent`/`createTextNode`, never HTML strings. Viewer/editor/admin access is intentional, while draft endpoints remain session-derived and are never consulted by the history UI.

List, current, and detail are separate locked reads, so a publication may occur between them. The client must treat each returned snapshot as self-contained, compare only UUIDs for labels, verify detail identity, and expose refresh rather than merge fields across responses. A detail can be pruned after listing and must become absence, not cached list content. No background polling should be introduced because it adds no correctness and complicates idle-session evidence.

The recovery procedure is operationally sensitive and installation-specific. A protected read-only page will summarize and link users into the documented console guidance while `README.md` remains the full deployment reference; commands that mutate storage remain documentation, not browser actions. This avoids an unstable source-host URL and keeps the runtime artifact useful offline.

## Implementation Approach

Extend the established server-rendered shell and shared vanilla JavaScript rather than introduce a new asset pipeline. Add `/management/configuration/history` and `/management/configuration/recovery` methods to `ManagementPagesController`; both naturally inherit authenticated access from `ManagementSecurityConfiguration`. Add History to shared navigation and explicit History links near the current/editor workflow. The recovery page will contain concise state-specific offline guidance consistent with the README and no form or mutation control.

Teach `console.js` to recognize a history root. Keep reusable snapshot/status/state renderers in that file so current and history use identical wording. On history load, fetch current state and retained history, render list metadata in the exact returned order, and mark the UUID matching `current.published.localId`. A native button or link for each snapshot will request `/configuration/history/{encoded UUID}` before rendering full content. Validate that `detail.localId` equals the requested UUID; otherwise show an error and no content. Represent non-2xx API responses with status/code metadata so `history_not_found` can clear stale detail, announce expiration, refresh the list/current state, and focus the refreshed status/selection area. Other 401/403 behavior stays centralized.

Use explicit prose derived from the current response instead of parsing free-text fault messages. Equality/mismatch and pending/published/failed status get textual explanations alongside any styling. When a mutation fault is present, state that acquire/save/activity renewal/validation/publication are blocked while inspection, release/discard of private state, and account administration remain available, then link to the protected recovery page. This is smaller and more truthful than defining fault codes or changing the API.

The realistic rejected alternative is rendering full content directly from the list response. Although available, it cannot exercise the required detail contract or explicit prune race and would encourage stale content after expiration. A separate SPA/router or server-generated per-UUID page would add routing/state complexity without improving the existing console.

## Test Strategy

Start with a Playwright test that logs in as a viewer, follows the new History navigation, and attempts to select a retained snapshot; before implementation the route/link or history root is absent. Build the browser suite around the real random-port Spring Boot application, temporary SQLite storage, and locally seeded accounts. Prefer real API/store/publication flows for order, content, permissions, reconnect, status, and fault truth. Use Playwright request interception only for a deterministic list-to-detail 404 race or another otherwise timing-dependent presentation branch; it must not replace the real authenticated access tests.

Keep server-shell/security assertions in `ManagementHttpIntegrationTest` and underlying inspection/publication concurrency assertions in `ManagementConfigurationHttpIntegrationTest`, `ConfigurationSnapshotStoreTest`, and `RuntimeConfigurationIntegrationTest`. The browser tests prove rendering, semantics, keyboard interaction, and session behavior. Authored HTML-like strings, sensitive literals, and placeholders are sanitized fixtures and must be visible as text without executing markup. A session-private marker saved by one user must be absent from another user's history until actually submitted.

The broad exit gate is the normal Maven `verify`; it uses local temporary files, loopback servers, the installed snapshot dependency, and headless Chromium, with no external credentials or destructive live target.

## Risks and Rollback/Recovery

The change is additive UI/documentation over existing read APIs. If browser presentation regresses, reverting the page/asset/test/documentation changes restores the existing current/editor console without data migration. No durable state format or publication path changes, so database rollback/recovery is unnecessary for this feature itself.

The main implementation hazard is stale DOM state after an error. Every reload and detail failure must replace or clear the affected containers before announcing state. The main semantic hazard is overclaiming outcome; tests should assert exact user-facing distinctions for pending, failed, matching, mismatch, and generic faults. The main security hazard is DOM interpretation of authored text; all fixture values should be asserted both visible and non-executable.
