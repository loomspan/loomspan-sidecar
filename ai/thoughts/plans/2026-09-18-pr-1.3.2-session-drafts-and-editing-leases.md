# Session Drafts and Editing Leases Implementation Plan

## Overview
- Ticket: `ai/thoughts/tickets/2026-09-18-pr-1.3.2-session-drafts-and-editing-leases.md`
- Research: `ai/thoughts/research/2026-09-18-pr-1.3.2-session-drafts-and-editing-leases.md`
- Outcome: authenticated sessions own private drafts; one expiring instance lease and one tab capability govern editing; actual framework publication atomically changes the runtime base and invalidates old editing state.

## Current State

`ManagementSessionGuard` checks account version and a 30-minute explicit activity mark, and management routes already use CSRF and role authorities. `ConfigurationDraft` retains exact authored content and associates validation by candidate object identity, but it has no session owner or HTTP surface. `RuntimeConfigurationService` keeps runtime `publishedId` separately from SQLite's intended pointer and holds its publication lock through preparation, framework publication, and pruning. No draft operation joins that coordinator. `ConfigurationSnapshotStore.current()` reads the intended pointer, so it cannot seed a runtime draft during a pending publication. Existing HTTP integration tests provide real sessions, cookie clients, CSRF and a replaceable clock; runtime integration tests provide publication fault hooks.

## Desired End State

An editor or admin can acquire the sole lease for one browser tab and obtain a private draft copied from the complete runtime-published snapshot. Saves retain exact YAML/REST text, do not prepare or activate configuration, and replace the candidate identity even for equal content. A second tab or session cannot write through the active grant. Other sessions, including admins and another session of the same account, see only safe lease status. Lease release/expiry preserves an eligible session draft; reacquisition gives a new grant and resumes only against the unchanged runtime base. Admin takeover revokes the former grant and starts a new draft from runtime production. Effective login and lease deadlines advance only on explicit meaningful activity reports. Invalidation, logout, and restart clear relevant private state. A successful framework publication invalidates the previous base under short synchronization, including if later bookkeeping fails; failed publication/reversion does not. Faulted configuration allows inspection/cleanup but blocks editing.

## Scope

### In scope
- Server-session draft storage, lease/tab/grant authority, explicit activity and expiry, cleanup, runtime-base capture and publication transition.
- Protected JSON draft/lease endpoints and documentation; real HTTP and runtime integration evidence.
- A positive `loomspan-sidecar.management.edit-lease-timeout` property, default `15m`.

### Out of scope
- Public validation execution, Publish and configuration-history endpoints (PR 1.3.3); editor UI and event detection (Phase 4); import/rollback (Phase 5).
- Durable drafts, cross-instance lease coordination, account-supplied ownership, new framework SPI, and compatibility bridges for discarded development code.

## Active Project Guardrails

- Choose the smallest complete direct implementation; replace development code without compatibility shims.
- Use only supported `ai.loomspan.api` framework types in production and tests. Framework controls skill preparation/publication/execution lifetime; Sidecar controls its transport and editing state.
- Preserve execution admission and retained diagnostics behavior. Do not let a management lease gate dispatch or interrupt accepted frozen work.

## Impact and Risk Analysis

The security boundary is the authenticated server session, with trusted principal ID/role taken from Spring Security. A tab identifier and server-issued grant are capabilities scoped to that session; the API must never accept account ID as authority. Status cannot include foreign draft content or validation results. Session invalidation includes explicit logout, idle expiry, account version changes, password changes, and container session destruction; a listener and account-change cleanup must release idle owners without waiting for their next request. Sessions and drafts are memory-only and disappear on restart.

The concurrency boundary must keep preparation outside editing synchronization. SQLite may point at pending B while runtime A still executes; draft creation must use a cached complete immutable runtime A snapshot, rather than `store.current()` or a lookup that pruning can remove. A short shared gate encompasses `reloader.publish`, replacement of the cached runtime snapshot, and invalidation of old drafts/lease. Creation, save, acquisition, activity renewal, and cleanup join that gate. If framework publication throws, no base transition occurs. If status/pruning fails afterward, invalidation has already occurred. Publication's existing long lock still serializes concurrent publication attempts, while preparation allows editing and execution.

Activity reports are explicit browser events, not inferred from polling or automatic validation. The server cannot distinguish a genuine click from a forged activity request within the same authenticated session; the Phase 4 client must send reports only for the listed meaningful events. The server enforces the 30-second reporting interval and both deadlines, and never revives an already expired login/lease. Browser tabs are isolated by opaque per-tab capabilities stored by the client per tab; the cookie alone confers read access only to that session's draft.

## Implementation Approach

Keep `RuntimeConfigurationService` as the sole runtime snapshot/fault owner. Replace `publishedId` with a cached `ConfigurationSnapshot` published by startup or successful framework publication, using its `localId()` for existing inspection and base checks. Add one short editing transition lock and a scoped operation for management editing that supplies the cached runtime snapshot while holding it. A small `ManagementEditingState` holds only session draft entries and the current lease; it does not own runtime state. `RuntimeConfigurationService` calls its invalidation operation under that same gate immediately after successful `reloader.publish`. `ManagementEditingService` implements session/role/tab/grant checks and state transitions under the gate; runtime does not depend on the management service, avoiding a bean cycle.

Keep `ConfigurationDraft`'s exact-candidate object association. Wrap it in a session entry with server-generated `draftId` and `candidateId`; rotate `candidateId` on every replacement. These IDs let a later validation response and current UI detect stale results without a global or cross-user revision scheme. A write supplies its expected candidate ID and current grant/tab; mismatches return conflict without mutation. Lease grants use fresh random UUIDs on acquisition/reacquisition/takeover and retain the same ID on renewal. A request for an already held lease conflicts rather than silently rotating ownership.

Use dedicated `ManagementEditingController` routes beneath `/api/management`: `GET /editing` for public-safe owner/expiry status, `GET /editing/draft` for this session's draft, `POST /editing/lease` for acquisition with a client-generated opaque `tabId`, `POST /editing/lease/activity` for throttled meaningful activity, `POST /editing/lease/release`, `POST /editing/lease/takeover` (admin), `PUT /editing/draft` with complete `ManagedConfiguration` fields plus `tabId`, `grantId`, and `expectedCandidateId`, and `DELETE /editing/draft` for discard. Acquisition creates a draft from production if none exists; release/expiry retains it. Takeover always replaces the taker's own draft with production and never transfers the prior owner's draft. Discard requires the current grant if this session holds the lease, but the owning session may discard its retained draft after release/expiry. Fault state blocks acquire/save/activity, while release/discard/status continue. Model 401/403 through the security chain, 409 for contention/stale base/capability/candidate, and 400 for malformed content. Public status gives `held`, `mine`, and `expiresAt` without foreign draft text, validation, tab capability, or grant secret. Private draft responses include `draftId`, `candidateId`, `baseSnapshotId`, authored content and own validation state; lease responses include the grant only for its owning session and expiry for the later warning/confirmation flow.

Register servlet session-destruction cleanup and clear editing state after committed account version changes. Keep the existing guarded per-request version check as the final authority, and recheck current account version/role on private reads and editing mutation to close the in-flight account-change race. The existing `/session/activity` remains explicit login activity and shares the 30-second per-session report limit; the editing activity operation renews both login and lease at an accepted report, while status/GET/save/validation execution does not. Document that the UI must send no more than one meaningful report per 30 seconds and must not call the activity endpoints for polling.

Implementation detail: servlet destruction and account-change cleanup synchronize on the private state monitor, nested beneath the short runtime transition gate for editing and publication. Each editing operation rechecks its live servlet session while holding that monitor. This prevents a request already in flight from recreating state after invalidation, without retaining session-ID tombstones.

## Test Strategy

Start with one failing real HTTP acquisition/privacy test. Use focused service tests for clock and grant state transitions, real management HTTP tests for session/CSRF/role/privacy, and the existing real runtime test context and publication hooks for pointer divergence, failure phases, races and execution continuity. Use latches rather than sleeps for concurrent transitions; use a mutable clock for deadlines. Keep all SQLite databases temporary and avoid SMTP/network services. See the companion testing plan for named cases and commands.

## Risks and Rollback/Recovery

The most sensitive change is moving the publication boundary: preserve the existing durable pointer and framework failure/revert order, and only shorten editing synchronization. A missed successful-publication transition would leave stale private state; verify the post-status-failure path explicitly. An overly broad lock would block preparation; verify edit completion while preparation is held. If the implementation fails locally, revert this ticket's code and tests together; no database migration or durable draft data requires recovery. A mutation fault still requires the existing operator database recovery procedure.
