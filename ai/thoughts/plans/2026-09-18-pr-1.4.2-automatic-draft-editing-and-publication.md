# Automatic Draft Editing and Publication Implementation Plan

## Overview
- Ticket: `ai/thoughts/tickets/2026-09-18-pr-1.4.2-automatic-draft-editing-and-publication.md`
- Research: `ai/thoughts/research/2026-09-18-pr-1.4.2-automatic-draft-editing-and-publication.md`
- Outcome: Editors author complete skill and REST YAML in the console, save and validate quietly, then explicitly publish the exact validated draft with accurate lifecycle feedback.

## Current State

`ManagementPagesController.current` and `console.js` only render the runtime snapshot. `ManagementEditingController` already exposes private draft, exclusive tab/grant lease, save, validation, release, discard and takeover endpoints. `ManagementConfigurationController.publish` admits an exact validated candidate; `RuntimeConfigurationService` separates runtime activation from durable selection/bookkeeping. `ManagementSessionGuard` extends login only on explicit activity; `ManagementEditingController.activity` can renew both login and lease on the same qualifying report. Existing HTTP tests cover most server admission and publication invariants, but there is no browser workflow test. The current working tree has only the untracked Step 1 research directory.

## Desired End State

The configuration console shows runtime content to all management roles and authoring controls only to editors/admins. A writable tab edits a list of complete YAML skill documents and one complete REST YAML document; add/remove skill documents, source labels and all REST targets/routes remain textual, preserving placeholders byte-for-byte through the draft. The UI starts from runtime content on acquisition, resumes only an eligible same-session draft, and never displays another session's draft. Saving and validation are separate, quiet effects; Publish is enabled only for the locally current, server-acknowledged, successfully validated candidate. Lost leases preserve still-valid local text and drafts but stop writes. Expired sessions, discarded drafts and changed runtime bases clear invalid edits. Publish results describe runtime versus intended state and never imply failure from a disconnect.

## Impact and Risk Analysis

Autosave can acknowledge content after further keystrokes, and even equal-content saves rotate the candidate ID. Thus the browser must serialize PUTs per tab, coalesce intervening edits, and compare a local edit revision and captured text with each response before showing Saved or publishing. Validation must run only for a fully acknowledged complete draft and retain the candidate ID/revision it checked; any edit immediately makes the visible result stale. Server admission remains authoritative for competing tabs, changed roles, base changes and queued publication.

One server session can have multiple tabs, while `editing.status.mine` means session ownership, not tab ownership. A grant stays only in the live page's memory; no browser storage copies capabilities into a duplicated tab. A new tab may read the session draft but cannot claim the existing lease. Reloading the writable tab loses its grant; its lease can expire naturally (or an administrator may take over). The page should explain this tradeoff. Session-private draft text must stay in the current document only during transient failures or lease loss; no localStorage/sessionStorage persistence. Server responses and page DOM remain no-store/text-only.

The server uses configured lease and login durations. The UI needs the lease expiry returned by existing endpoints and the configured durations for labels; it should not synthesize a fixed 15-minute deadline. Timer/status GETs never report activity. Only user input, paste, click, scroll or an explicit Continue editing report at most once per 30 seconds. The current broad activity listener must avoid a duplicate `/session/activity` call when `/editing/lease/activity` already reports both deadlines. Mutation faults stop authoring, while current configuration remains inspectable.

Publication has three distinct outcomes: known admission rejection, known phase failure with runtime/intended fields, and transport/unknown response. A request may be accepted before the connection is lost, so the UI cannot retry it blindly. After a known failure or uncertain response, inspect `/configuration/current`, display runtime/intended/fault truth, and require a fresh explicit decision before any new publish. This ticket supplies immediate results; PR 1.4.3 supplies retained outcome inspection.

## Implementation Approach

Use native textareas for full YAML and a small skill-document list with source-name inputs, add and remove buttons. This avoids a new editor library and YAML grammar duplication. Put the authoring state machine in a dedicated `management/assets/editor.js`, reusing the existing console API/activity helpers through a minimal shared entry in `console.js` or a small exposed module. Keep all state in memory: local revision, last acknowledged revision/content, candidate/base IDs, grant, validation revision, timers, and publish-in-flight/unknown flags. A short idle debounce (about 600 ms for save and 900 ms for validation after the last edit) starts work; at most one PUT is in flight, with the newest complete content sent next. Do not auto-retry a failed PUT without a new edit or explicit Retry save. A validation request is sent only after the current revision's save has been acknowledged and editing has paused. The response applies only when candidate ID and local revision still match. Later text never gets replaced by a save or validation response.

The editor's status band reports Unsaved, Saving…, Saved, Save failed, Checking…, Out of date, Valid or Validation errors. A native `details` element starts closed and only user action expands it. Validation issues render with text nodes, preserving severity, source label, skill name, location and message. Use a lower-left compact save status bar, accessible text and `aria-live=polite`, without focus changes. Publish, release, discard, resume, takeover and Retry save remain explicit buttons. Admin takeover uses the existing server endpoint and replaces the admin's candidate with production; show a clear confirmation of discarding that admin's current draft before calling it. For discard, clear local text only after server success. On status/conflict rechecks, compare current published base and own draft before deciding whether to retain local text or explain invalidation.

Add only the necessary session response fields for configured inactivity durations. For ownership, show “You are editing”, “Another tab in this session is editing”, or “Another editor is editing”; these can be derived from existing `status.mine`, `held` and this page's in-memory grant without exposing an account identity or draft. Existing endpoints continue to enforce permissions.

## Test Strategy

Start with a browser test that edits YAML and observes a missing Save status/PUT on the current page. Add Playwright Java JUnit tests against a random-port Spring Boot fixture with seeded management accounts; use request interception only where deterministic delayed responses or disconnects are needed. Keep server authority cases in existing HTTP integration tests and use framework fixtures for full YAML/REST publication. Test all browser text rendering with markup-like values and keyboard controls. Install Chromium in the test environment as a declared setup requirement; browser setup is not a production dependency. The broad Maven suite remains the final gate, supplemented by focused browser tests.

## Risks and Rollback/Recovery

Playwright adds a test-only browser binary/setup cost; it is justified by the explicit browser workflow acceptance criterion and cannot be replaced by HTTP tests. If browser setup is unavailable, report that gate as unrun rather than claiming browser proof. Production rollback is a code revert; a published configuration remains governed by the existing snapshot recovery process. An uncertain publish requires inspection, never automatic resubmission. No framework or release migration occurs.
